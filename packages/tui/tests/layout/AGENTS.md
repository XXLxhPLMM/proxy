# tests/layout/ — `@/app` 整屏的**真渲染**断言（假 TTY + 真 Ink）

本目录回答「几何层给的那一套坐标，呈现层画出来的那一帧**逐格相同**吗」。判据全部跑在**真的排版结果**上：
假 TTY 喂进真 `Ink`，故每一条都在量「屏上到底长什么样」，而不是「某个纯函数返回了什么」。

## 为什么这一档非有不可

下面十件**只有真渲染才看得见**的事，散在纯函数档里全部恒绿。编号就是各档 `describe` 标题里那个 circled
number（改编号要连本表一起改）：

| # | 只有真渲染才看得见的事 | 档 |
| --- | --- | --- |
| ① | **Ink 对过宽的 `<Text>` 是静默软换行** —— 一换行**后面所有行都往下移**、边框随之错位（症状是「侧边栏里有一个名字把整块框顶歪了」）。而它**只在长名字那一档出现**：中文名的显示宽度是 ASCII 的两倍，纯 ASCII 的用例对「按 `length` 算」与「按显示宽度算」**零鉴别力** | `frame` / `sidebar` |
| ② | 侧边栏那一列的全套（项的行位 / 顶部留白 / 项间空行 / 裁剪预算 / 悬停那枚 ✕ / 记号位） | `sidebar` |
| ③ | 选中态是「最亮的那一档 + 加粗」且**没有反底色**。底色那一列归 hover，而「拆成三段」的高亮在别的实现里照样通过「开没开底色」那种判据 —— 故本目录的探测器**真的解析 SGR 参数**（`sgrColorAt` / `sgrStateAt`） | `selection` |
| ④ | **折出来的输入行与框**对不对得上：框高是几何层按折行数给的，而画面上是 Ink 按它自己的布局画的，两者不一致的症状是「输入串第二行跑到框外面去了」。且状态行必须在框**外**（在框内时与输入串抢同一行，那一帧的 `notice` 会盖住它） | `frame` |
| ⑤ | 命令面板与会话菜单**浮在别的区之上**，而**背后照旧亮着**（它们不是模态、不铺遮罩） | `overlay` |
| ⑥ | 模态窗口：绝对定位的后画兄弟，坐标全对而**画不进上层**时症状是「窗口内容被主区盖掉」；`esc` 那一枚真的压在标题那一行上；遮罩**逐格**盖住整个可视区域 | `window` / `history` |
| ⑦ | 引导屏与那块艺术字标记的居中、逐行一色、放不下就不画 | `welcome` |
| ⑧ | 弹窗里**焦点那一格**的插入符落在第 `cursor` 个字上，而**非焦点格**与**下拉格**一个都没有 | `field-cursor` |
| ⑨ | **呈现层不许自己裁**只在喂违约输入时看得见（`history.test.ts` 那一条实测绿过一次）：守约的 `label` 装得下 ⇒ 「裁了」与「没裁」渲染结果**逐字相同**。故那一档**故意**喂一个比预算长的 `label`，而**同一帧**里那句 `note`（它**没有**「已裁好」那份承诺）**必须**看见 `…` —— 那是「找 `…` 的探测器看得见」的反向自检 | `history` |
| ⑩ | 两个「已」不许同形同色：`at`（高亮）与 `pinned`（已在侧边栏上）渲染成同一个东西时，操作者分不出「它已经在了」与「我现在正指着它」；分组标题**再吃一次高亮**就分不出它是标题还是一条可选会话 | `history` |

⚠️ ⑥ 那一半（遮罩）特别值：**Ink 没有半透明**，遮罩是「重新铺一层不透明的底色」，而任何自己带底色或
带边框的盒子都会盖在它上面或把它挖空 —— 症状是「整屏压暗了而侧边栏没压暗」「屏最底下横着两条亮线」，
**两者都不让任何 `includes` 断言变红**。故判据是**逐格**比两帧。

## 假 TTY 而不是真终端

`render()` 要一个 `stdout.isTTY`（否则 Ink 退化成逐帧输出、不排边框）与 `columns` / `rows` —— 这三个都能
**注入**，故不需要真 pty。⚠️ 本目录**测不到**「真终端退出后干不干净」那一半；「鼠标上报」「拉宽拉窄会不会
闪一帧旧布局」只能手验，清单见 `packages/tui/AGENTS.md`。

## 共用的那半边

- **`_harness.ts`（造帧）**：假 TTY + `renderFrame` / `renderScreen` / `renderRaw` 三种取帧 + `stripAnsi` +
  喂 `Layout` 的 `props` / `geoInput` + 三格样本。⚠️ **全目录只有它 import `ink`**，而 ink 一旦加载完
  chalk 的 level 就定死了 —— 故「这一帧到底有没有颜色」由下一节那条纪律决定。
  ⚠️ `stripAnsi` 住 `_harness` 而不是 `_probe`：`renderFrame()` 的返回值**就是它剥过的**，它是造帧那一步
  的一部分，不是读帧那一步。
- **`_probe.ts`（读帧）**：把一帧读成「哪一格是什么色 / 哪一列 / 哪一行」—— SGR 扫描、按显示列切、逐格底色、
  行号。依赖方向只有一条：本模块 → `_harness`（`sidebarScreen` 要先取帧再切列）⇒ 不成环。
- ⚠️ **收件门槛是「两个以上档真用到」**：只被一档用到的东西留在那一档里 —— 搬进来就成了一份没人能单独
  删掉、也没人说得清谁在用的间接层。⚠️ 而这两个模块的收件门槛**今天已经是九个档**（本目录八档 +
  `tests/render/` 那四档转发它们）⇒ 它们**本来就住在错的地方**，正解是提到 `tests/` 根；搬动要一次改九个档
  的 import，故那一刀留给集成那一轮，不夹在一次呈现层改动里。
  ⚠️ **共用模块内部的私有件不算例外**（`toolTurn` 只被 `entryOf` 用，它就不带 `export`）。
- ⚠️ **每次取帧各起各的流**（`fakeStdout()` 是工厂而不是单例）：共用一条流的话两帧会互相追加，而症状是
  「比较两帧的那几条断言偶尔读到上一帧的尾巴」。
- ⚠️ `geoInput()` 喂给 `geometry()` 的那个形状自带一组自检（`probes.test.ts` 那一族）：
  `GeometryInput.window` 是 `readonly WindowSlot[]`，而喂 `true` 的话运行期**不响**（`true.length` 是
  `undefined`）—— 破口表现为「后面几条断言空解引用」而不是「一炸就响」，而那种失败看上去像「断言写错了」。

## ⚠️ 每一档都自带 `vi.hoisted` 那一句，而它**搬不进**共用模块

`FORCE_COLOR` 必须在 **ink（因而 chalk）被 import 之前**设好，否则 chalk 按「本进程标准输出不是终端」
把 level 定成 0，而那样 Ink **根本不生成任何转义序列** —— 于是③那两条判据变成恒真的空断言（没有序列 =
没有裸格子）。

⚠️ **`vi.hoisted` 只在入口模块（也就是档）里被提升到 import 之前**：把它放进 `_harness.ts` —— 一个
**被 import** 的模块 —— 它就是一句普通调用，跑在 ink 之后。实测（搬进去那一轮）：13 条着色判据一起红，
而症状是 `sgrColorAt` 恒给 `null`，**看着像「实现没上色」而不像「装载顺序不对」**。

⚠️ 故每一档在 `import { …, vi } from "vitest"` 之后自带那一句（`tests/input/` 那七个档是同一形状）。
⚠️ 新增一档而漏掉它，那一档不是「少一点覆盖」，而是**它整档的着色判据全恒真** —— 而真正被上色这件事
只有 `window.test.ts` / `selection.test.ts` 那几档顺带验到，其余档看不见。

## 探测器自检

`probes.test.ts` 那一档测的是**这两个共用模块的探测器本身**（含 `geoInput()` 那份入参形状），不是界面。
⚠️ 少一条，一个「什么都没渲染出来」的实现会让本目录每一条 `includes` 都绿 —— 而那恰恰是这一类界面最可能的
失败形态。

⚠️ 同一条纪律散在每一档里：**每个探针下标先自检**（`expect(at).toBeGreaterThanOrEqual(0)`）。理由是
`sgrColorAt(line, -1, …)` 恒给 `null`、`columnOfIndex(line, -1)` 恒给 `-1`，而在 `null` / `-1` 上
「≠」「<」「>」「一切拿它当期望值的比较」全都恒成立 —— 一条恒绿的断言是「护栏在生效」的假象。
⚠️ **「越界」与「落在范围内」两头都要钉**（`probes.test.ts` 那一条合成样本）：一个**越界**的下标若返回
行尾那一列或 `0`，它在屏上仍像个坐标，于是每一处「相等 / 小于预算」的比较恒成立。
⚠️ 而**「越界」按入参域分档，钉的是各自可达的那一段**：**字符下标域**（行号 / `indexOfText` 那一族）的
入参天生可能收进负数，故「找不到 → `-1`」那一档必须钉；**显示列域**（`rawIndexOfColumn` 与包装它的
`bgAtColumn` / `bgRgbAt`）的入参**恒 ≥ 0**，故负值在那条路上**不可达**（给它加分支是给一条走不到的路写
代码），而它要答的越界是「**超出这一行画到的宽度**」，那一档同样必须给 `-1`。

## 一条被实测否掉的假设（留在这里是因为它很容易被重新加回来）

「`<Text backgroundColor>` 漏了 → 字形那里被戳一个洞」**是错的** —— Ink 的 `<Text>` 从**最近的带底色的
祖先 `<Box>`** 继承（`BackgroundContext`），故删掉 `<Text>` 那一份**渲染结果逐字相同**（实测）。真正
load-bearing 的是**外层那个 `<Box backgroundColor>`**：删掉它，那一枚就继承到侧边栏的 `surface`，于是在
hover 那一档底色上真的出现一个两格宽的洞。
