# `users.json` 逐项说明

配套 `cfg/users.json.example`（把它 `cp` 成 `cfg/users.json` 即可用，`cfg/users.json` 已被 `.gitignore` 忽略）。

> **为什么逐项说明在这个文件里、而不在 `users.json.example` 里**：`users.json` 是**机器读**的
> `JSON.parse` 输入，**不支持注释**（`//`、`/* */` 都会让整份文件解析失败 → 启动即 abort）。
> 所以「每个键是什么意思」只能写在这里，示例文件保持逐字可 `cp`。

## 账号形状

| 键 | 必需 | 说明 |
| --- | --- | --- |
| `username` | 是 | 非空、不含 `:`、不重复 |
| `password` | 是 | string（`authType=uid` 时也仍然必需——形校验不因鉴权类型放松） |
| `acl` | 否 | 该用户专属的**目标名单**，形状与全局 `cfg/acl.json` 的 `target` 组**完全同形**：`{ "target": { "whitelist": [...], "blacklist": [...] } }` |
| `quota` | 否 | 该用户专属的**流量配额**，见下 |
| `expiresAt` | 否 | 该账号的**有效期截止**（ISO 8601 时刻），见下 |

**未知顶层键一律判整份文件非法 → 启动 abort**。所以新增可选字段必须先加进白名单，
复制一份 key 列表到别处就会出现「我配了但它没生效」这种要读源码才查得出的问题。

`acl` / `quota` / `expiresAt` 各自独立校验，但**一个非法就让整份文件作废**（不是「只丢非法的那一个」）——
后者会造出「我配了名单但它没生效」。

## `expiresAt`（账号有效期）

| 键 | 含义 |
| --- | --- |
| `expiresAt` | 账号**有效期截止**的 ISO 8601 时刻。**必须带时区偏移**（`Z` 或 `±HH:MM`） |

四条语义，读之前必须知道：

1. **`now >= expiresAt` 即拒**（恰好等于到期时刻也拒，差一毫秒仍可用）。审计
   `auth.decided` 带 `user=<该账号>` 与 `reason=account-expired`。
2. **判定在认证点**：到期后新连接一律进不来。**已建立的隧道不会因此被切断** ——
   CONNECT / SOCKS 会话一次连接只认证一次，会跑到断为止；HTTP keep-alive 的**下一个请求**
   会重新认证，于是被拒。刻意如此：身份是**建立时**授权的。
3. **`authType=jwt` 下这个字段不生效** —— jwt 的身份来自 token 自身（`sub` 给用户名、
   `exp` 给过期），**判定根本不查账号表**。jwt 模式下的账号有效期**只能由 token 的 `exp`
   声明表达**。这种部署下配了 `expiresAt` 会在启动时告警一条
   `[account-expiry-inert]`（配了不生效 = 假安全感），解决办法是把 `AUTH_TYPE` 切成
   `basic` / `uid`。
4. **与 `quota` 完全正交**：配额是「用量」的时间窗（`quota.window`，滚动即清账），
   本字段是「账号」的有效期（到点即拒）。两者互不影响，**账号过期也不清已用流量**
   （重新延长 `expiresAt` 后，那段用量仍然计入配额）。

**必须带时区偏移，不是可选讲究**：`"2026-10-01"` 会被 `Date.parse` 读成 **UTC 午夜**、
`"2026-10-01 00:00"` 会被读成**本地午夜** —— 同一份配置在 UTC 机器与 `+08:00` 机器上差 8 小时，
而你写它时心里想的一定是本地零点。所以无偏移 / 空格分隔 / 只有日期**一律判非法** →
启动 abort。写成 `"2026-10-01T00:00:00+08:00"` 或 `"2026-10-01T00:00:00Z"` 都可以。

**已经过期的时间戳是合法配置**（那正是这个字段要表达的状态），只有**形态**非法才 abort。
日历上不存在的日（如 `2026-02-30`）也判非法 —— `Date.parse` 会把它静默滚成 3 月 2 日。

## `acl`（每用户目标名单）

- `acl.target.whitelist` 非空时，目标**不在**名单里就 403；空/缺省 = 不限制。
- `acl.target.blacklist` 命中即 403，**优先于**白名单。
- 条目收 `IP` / `CIDR` / `域名` / `*.域名`；**不支持端口、不做 DNS 解析**。
  `*.a.com` 只匹配子域、**不含** `a.com` 本身（要放行请另写一条）。
- **只允许 `target` 一个组**：`clientIp` / `upstream` / 任何未知键都判非法。
  理由：客户端名单判定发生在**鉴权之前**，那时还不知道用户是谁；`upstream` 是路由名单，
  与「你是谁」正交。收下永不生效的字段 = 给假的安全感，不如启动期报错。
- 判定在 `core/access-control.ts`，与全局 `target` 名单**合流**：
  `放行 ⇔ 全局 target 组放行 ∧ 该用户 target 组放行`（先全局后个人、全局短路）。
- 拒绝时日志带 `source=global|user`，据此知道该改 `acl.json` 还是 `users.json`。

## `quota`（每用户流量配额）

| 键 | 含义 |
| --- | --- |
| `window` | 配额窗口的**重置周期**，只认 `"day"` / `"month"`。**缺省 = `month`（按月重置）**。其它取值（`"week"` / `"hour"` / 大小写变体 / 非字符串）整组非法 → 启动 abort |
| `bytes` | **上传 + 下载算在一起**的合计上限（一个窗口内） |

**只有这一个上限，刻意不分方向。** 想「只限上传」在这里得不到：耗尽判定是**账号级封禁**
（见第 2 条），分方向上限的实际效果是「整号断网，且要先把那个方向撞满才触发」。真要分方向
限流是限速问题，见下面「刻意没有 `rateBps`」那条。

六条语义，读之前必须知道（它们都能踩坑）：

1. **缺省、或 `bytes` 为 0 = 该用户不限流**。
   **没有上限 ≠ 不计量**：用量照常累加，`usage(user)` 恒为真用量，将来加上限即刻按真账判定。
   **剩余 = `bytes - usage(user)`**（库调用方拿得到 `TrafficAccount.usage`；没有单独的
   `remaining` 出口——那是纯减法，而「不限流」时它该返回什么没有好答案）。
2. **上限被突破 = 该账号在当前窗口内彻底不可用**（两个方向都拒，不是只封撞顶那个方向）。
   否则用户可以上传撞顶后改走下载继续白嫖。
   代价是**硬切**：连接当场断（HTTP 未发头回 **507**，其余 destroy —— 客户端实际看到什么见第 6 条），不给「用尽后只拒新请求」留缝。
   **撞顶之后没有「前置拒绝」**：判定挂在字节流上，请求入口**不查账**。所以账号已经超限了，
   **再发请求仍然会先建链、并真的传出去一段字节**，才在下一个数据块上被切断。实测：撞顶后
   连发两次各超 5000B 的请求，两次都真的建立了连接、各记满一整块。这是**产品决策**而不是
   漏做——留「用尽后只拒新请求」这个缝，一条长连接隧道就能永远不触发判定，配额直接成摆设。
3. **恰好等于上限放行**（判据是「累计 **>** 上限才拒」）。`bytes: 100` 允许用满 100 字节。
   配额是**上限**，不是「额度 + 1 的坑」——写 1GiB 的运维最难受的就是「差一个字节传不完」。
4. **用量**不跨窗口继承**：卡在边界前用满的用户，等窗口翻页**不会**再白拿一份。
   上一窗口的耗尽状态也随新窗口解除（新窗口给完整额度）。
5. **计量按数据块（chunk）计，判定粒度是「整块」** —— 配 `bytes: 1000` 的账号实际能传
   约 **64KiB**。原因：计量挂在字节流的 `data` 事件上，一次事件就是一整块，**整块计入、整块
   判定**（超限的那一块也整块记下）。故实际可过量级是 `max(N, 一个数据块)`，严格上界是
   `N + 一个数据块`。**块的大小不是本项目的常量**，由传输层决定——源码里没有任何
   `highWaterMark` / 64KiB 常量，计量只读 `chunk.length`：
   - 裸 TCP（明文入站 / 明文上游）**实测单块最大 65536 字节**（底层每次读的分配上限）。
     HTTP 路径的首块还要减掉被 HTTP 解析器从同一块里摘走的请求行+请求头：
     **实测 `bytes: 1000` 撞顶时 `usage` 落在 65280**（= 65536 − 256，那次请求的头部共 256 字节）。
   - 走 TLS 的一跳（`https` / `sockss4` / `sockss5` 入站、TLS 上游）单块受 **TLS record ~16KB** 约束。
   **两条排障含义**：① `[quota-exceeded]` 日志里的 `usage` **明显大于 `limit` 是正常的**——
   那是「撞顶的那一整块」被如实记了下来，不是记账出错；② 别指望用小配额卡住「只上传了一点点」
   的客户端，它一次就能过掉一整块。
6. **两个方向在客户端的表现不同**（这条最容易在排障时被误判成「代理崩了」）：
   - **上传方向**（`up`）撞顶时响应还没开始 → 回 **507 Insufficient Storage**，
     **状态行能到达客户端**（`curl` 明确看得到 `507`）。
   - **下载方向**（`down`）撞顶时响应体已经开始流动（响应体只在 `writeHead` 之后流动）→
     直接 `destroy()`，尚在写缓冲里的状态行一并丢掉 → 客户端表现为
     **`curl: (52) Empty reply from server`** / HTTP 状态 **000（连接被重置）**，
     **不是** 200 + 截断。
   - **CONNECT 隧道**因为 `200` 在建隧时就已收到，反而能**看清截断**。
   两个方向都是硬切的正确表现，**不要**为了「让状态行一定送到」把它改成延迟 destroy。
   排障口径：看到 `(52)` / `000` 时去日志里找同一时刻的 `[quota-exceeded]` 行；
   **找不到就别归因到配额**（源站自己断连等长得很像）。

字段值的合法性：`bytes` 必须是**非负安全整数**（`Number.isSafeInteger` 且 `>= 0`）。
负数 / 小数 / 字符串 / 布尔 / `null` / `NaN` / `±Infinity` / 超 `2^53-1` / **未知子键**
一律「整组非法 → 启动 abort」。**刻意没有 `rateBps` / `maxConnections` / `concurrency`
这类字段**：限速必须 `pause()`/`resume()` 整形，会与既有守卫的半关闭联动形成第三层流控；
连接数限制也不在本期。写它们进来会让整份文件作废（不是「被忽略」）。

### 围绕配额的三个运行参数（在 `.env` / CLI，**不在** `users.json`）

| Env | 缺省 | 说明 |
| --- | --- | --- |
| `QUOTA_LEDGER_DIR` | `<configDir>/cfg/quota` | 配额账本目录（**startup**，改了要重启）。没配任何非 0 的 `quota.bytes` 时**不会创建** |
| `QUOTA_RESET_HOUR` | `0` | 窗口重置小时 `0..23`（**本地时区**）。`window=day` 且设为 `3` 时，当天 `01:00` 仍算前一天 |
| `QUOTA_FLUSH_INTERVAL` | `5000` | 增量落盘间隔 ms。**停机必落盘**，不依赖这个间隔 |

### 账本（重启后用量不丢）

用量会被**持久化**到 `<QUOTA_LEDGER_DIR>/worker-<slot>.jsonl`（单进程 slot 恒为 `0`；
cluster worker 由 master 在 fork 时分配 `1..N` 的**稳定序号**——不是 PID，否则每次重启
换文件名、恢复就永远不生效）。两件事要知道：

- **没配非 0 的 `quota.bytes` 时账本完全不存在**：不建目录、不开文件、不起后台任务。
- 写盘失败（磁盘满 / 权限被改）时**服务照常跑**：内存计数继续、配额判定继续、未落盘的
  增量留待下次重试，同时发一条 `[quota-ledger-error]` **error** 级日志。
  **看到这条不要重启**——重启会把队列里未落盘的增量一起丢掉，正确处置是修好那个文件/目录的写权限。
