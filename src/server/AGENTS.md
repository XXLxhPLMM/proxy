# src/server — 服务端编排

`index.ts`（`ProxyServer`：进程与编排）+ `cluster.ts`（多进程）+ `log/`（结构化日志）。协议内部状态机归 `src/core/AGENTS.md` 的 `BaseProxy`，本层不管。

CLI 的单进程/worker 启动由 `src/runtime/` 的 Cordis adapter 接管；本目录的 `runServer()` 暂保留为库兼容入口，cluster master 仍由 `cluster.ts` 直接管理。

## ProxyServer（`index.ts`）

- `ProxyServerOptions.allowProcessExit`：库/公共 `runServer()` 默认 `false`，只做 stop、回滚 ownership 与可观测日志，不调用 `process.exit`；CLI 与显式宿主传 `true` 才由 server-owned rollback/stop/signal 路径执行 `process.exit(0/1)`。cluster master 的 fork/worker IPC/listener 管理始终照常，退出 gate 不关闭通信。
- `createProxy()`：读 store（`proxyProtocol/host/port/upstreamTimeout/tls/auth`）组 `baseOpts`，经 `core/server/factory.ts` 建 `ProxyCore`。
- `start()`：先登记请求代际并保留稳定 core 结果，再在异步阶段绑定具名 signal/cluster message listener（worker 尽早接住 shutdown）→ 显式 `initConfig()` → `setupProcessGuards()` 取得可释放 lease → 非 worker 打掩码配置（`logConfig()`，关键事实走 `notice`：默认 error 级控制台也可见）→ 订阅 `stateChange` / proxy 事件 → `proxy.start()`；正常完成仍返回 `ProxyCore`，重复 start 只复用当前代际的 in-flight/已运行 core。真正进入 `core.start` 的执行单独登记，stop 只等待该集合；每个新的 start 意图与**首轮** stop 推进 generation，较新 stop 使旧 start 以模块私有、固定 code `ERR_PROXY_START_CANCELLED` 的错误 reject，不能返回 core 伪装成功，且不会被后续 start 复用；重入 `stop()` 不再推进 generation（first call wins，见下条），它复用同一轮等待视图即可，在途旧 start 已被首轮 stop 取消。`BaseProxy.stop()` 仍等待在途 start。
- start 与 stop 不排队互等：只要 full `stopPromise` 尚未释放、pending hard-exit round `stopHardExitRound` 尚未收口、清理票据 `cleanupOwner` 未归还、真实 core stop 的 `coreStopOwnership` 仍持有，或保留 core 仍为 `stopping`，新 start 就立即以模块私有、固定 code `ERR_PROXY_STOP_IN_PROGRESS` 的 `ProxyStopInProgressError` reject；若上一次 core stop 已 full settle 但结果为 rejected/state=error，`settledCoreStop` 失败记录也保持闸门，必须先再次 `stop()` 重试，不能走 start 快捷路径伪装成功。该拒绝不推进 generation、不创建/替换 core、不调用 `core.start()`。调用方应在 full stop settle（必要时先 `waitForStopSettled()`）且 pending hard-exit 已收口后显式重试，重复 stop 本身复用同一轮公开等待视图。
- 清理 ownership 状态机（start 失败回滚与 stop 共用一把锁）：`cleanupOwner`（`{kind, generation}` 票据）+ `cleanupQueue`（串行临界区队列）+ `runCleanupExclusive(owner, operation)`。规则：**票据在清理入口同步 claim、在临界区退出前 release**（`releaseCleanup` 以 identity 比对，迟到结果只能释放自己的）；临界区由队列串行，前一个 owner 的成败都不阻断后一个；owner 为 `null` 时仍受队列互斥保护，只表示本轮不持有标记。`claimCleanup`（start-failure 额外在函数内复查 generation）、`releaseCleanup`、`runCleanupExclusive` 全部无 await，因此「catch 入口判定」与「取得 ownership」之间没有 TOCTOU 窗口——这是 stop 与 start 失败回滚不并行清理的全部依据。传入 `runCleanupExclusive` 的 operation 必须是**完整清理**而不是有界视图：视图超时由调用方处理，队列与 ownership 要占到 operation 真正 settle。
- 真实 `proxy.stop()` 的唯一入口是 `beginCoreStop(proxy, late)`：同一个 core 只会有一份 `CoreStopOwnership`（`token` + `settled` + `late`），已存在时**返回既有 ownership 而不是再发一次 stop**（不同 proxy 实例则直接抛错）；full settle 后清 active token，并把同一 proxy 的 settled 结果留作 `settledCoreStop` join 记录。join 只对 `stopped/stopping` 生效；`error`/失败结果会清掉旧记录，下一次 stop 必须重新触发真实 `proxy.stop()`，且在重试前 start 闸门持续拒绝，不能并发重试或释放仍 listening 的 core。`finishCoreStop` 在 full settle 后按 identity 清 token、记录迟到失败、再尝试释放 core。因此任何有界视图（回滚视图、公开 stop 视图）超时只允许调 `markCoreStopLate`，禁止直接 `proxy.stop()` 或清 token。
- 释放 core 引用的唯一判据是 `releaseCoreIfDiscardable(proxy)`，三个条件同时成立才清空 `proxy`/`proxyEventsBound`/`lifecycleLogBound`：`this.proxy === proxy`（identity，防误删新一代）、**当前没有任何 ownership**（`coreStopOwnership`/`stopPromise`/`stopHardExitRound`/`cleanupOwner`/`startPromise`/`activeStartExecutions` 全空）、state 为 `stopped` 或 `idle && !isRunning()`。`starting/running/stopping/error` 一律保留引用；同一 proxy 的 `settledCoreStop` join 记录也随之清掉。释放尝试只发生在 `finishStopRound` 清空 `stopPromise` 之后、start execution 落地回调或回滚 full-cleanup continuation 中；`stopInternal` 不提前触碰 core 引用。pending hard-exit round 存在时即使 full stop 已 settle，也不得释放 core 或放行 start，直到该 round 的唯一退出/失效路径完成。
- `bindProxyEventLogs()`：core/server 只抛不记，落盘收拢于此。`forward`（按 kind 打行；debug 级 headers dump 经 `maskSensitiveHeaders` 把 `proxy-authorization`/`authorization`/`cookie`（大小写不敏感，含数组值）掩码为 `"***"`，其余头原样）/ `forwardError` / `serverError` / `clientError` / `auth`（allow→debug，deny→info 留审计；**两侧都带 `tag`**，见下）/ `pipe`（按 `type` 分发：`target-unresolved/loop-detected/upstream-refused/upstream-error/upstream-timeout/route（与 `[route]`info line 一一对应，字段为`target`、`route`、`reason`；core 在 server 模式短路不发）/ip-denied/target-denied/socks/bad-request/debug`；**转发层 502 必须带成因**：`upstream-error` 含 `target` + `err.message` 落 warn，否则 TLS 失败/ECONNREFUSED 在 info/error 级无痕）。
- **畸形握手失败的落盘等级定级在本层单点收口（`pipe` 的 `bad-request` case）**：`SocksForwarder.badRequest` 只发事实并带 `bytes`（`SocksHandshakeReader.bytesReceived`，core 自维护、可靠），本层按它选等级——**`bytes === 0` = 对端连上不发就断（裸 TCP 探活/端口扫描/健康检查）→ 传 `override = "debug"` 降级，且该降级优先于 warn**；**`bytes > 0` = 客户端真发了垃圾字节的畸形握手（非法/截断 greeting、缺 USERID NUL、握手缓冲超限等）→ 不传 override，维持事件默认 warn**；**缺 `bytes`（非握手来源）按 fail-closed 记 warn**。该事件此前落在 `default:` 分支恒 debug：真实握手失败在 `LOG_FILE_LEVEL=info` 下彻底不可见。`default:` 分支此后只兜未登记的 `type`（guard 的 `dial`/`established`/`client-error` 等）——**新增已知 `type` 必须显式开 case，禁止靠 `default` 吞掉等级**。0 字节的 `[client-timeout]` 由 `socks-base.ts:levelForBytes` 单独降级（不经 `pipe`），两条路径互不干扰；判据语义见 `src/core/AGENTS.md`，TLS 侧（按 `err.code`）见 `src/utils/AGENTS.md`。
- **失败退出必须先 flush（否则「为什么退 1」那一行根本落不了盘）**：`bindSignals()` 的 graceful 失败分支记完 `logger.error("[shutdown] signal/IPC graceful stop failed:", …)` 后走 `flushThenExitOwned(1)`——`process.exit` 会截断在途 `appendFile`，形态对齐 CLI 启动失败路径（`void logger.flush().finally(...)`），但窗口**有界**（复用 `STOP_HARD_EXIT_FLUSH_TIMEOUT_MS` 这个既有常量，不新造无限等待），且退出**仍经 `exitProcessIfOwned()` 单一闸门**：不得裸 `process.exit`，`allowProcessExit=false` 的抑制语义与「同一实例只退一次」闩锁都由该闸门单点保证，别的路径（stop/rollback hard-exit）先退时这里只是 no-op。公开 timeout 后已 arm 的 `stopHardExitRound` 仍优先，signal 失败不抢第二次 exit。
- 启动失败回滚：catch 入口**先判 `isProxyStartCancelledError`，再 `claimCleanup("start-failure", generation)`**（函数内复查 generation），三者之间没有任何 await，所以「本轮是不是清理 owner」在第一行代码就定死；`claim` 返回 `null`（已有 owner / 已被新 stop 接管）时只原样 reject。`cleanupAfterStartFailure(view)` 整段在 `runCleanupExclusive` 临界区内跑：先等待 `beginCoreStop()` 的真实 core stop settle，再做有界 `logger.flush()`，最后才 `disposeProcessResources()` 归还 signal/guard；每项 cleanup error 逐项记录并聚合，原始启动错误最后原样重抛（可扩展错误上附 `cleanupFailures`），不会让清理异常覆盖主因。
- **有界预算只结束等待视图，不释放 core ownership**：外层 `runBounded(() => fullCleanup, START_FAILURE_CLEANUP_TIMEOUT_MS)` 只是给调用方的有界视图；超时后 `markCoreStopLate(rollbackProxy)`、把 `rollback did not complete within <n>ms` 记成 cleanup failure，并挂 `void fullCleanup.then(...)` continuation 消费迟到的成功/失败（迟到失败只按 `[lifecycle] startup failure (late)` 记录，挂不回早已 reject 的启动错误）。回滚预算耗尽后，只有 `allowProcessExit=true` 的 process owner 才 arm 独立 rollback hard-exit 票据：独立 last-resort grace 为 **5000ms**，hard-exit 前再给 `logger.flush()` **1000ms** 有界兑现窗口；`invoked` 只在真正 exit 前置位，full rollback settle 会 identity 清理 timer，退出前绝不释放 `coreStopOwnership`/`cleanupOwner`/`this.proxy`，也不先移除 signal/guard 逃生口。`allowProcessExit=false` 时记录 error，说明宿主必须处理 pending rollback/必要时重建实例，不能静默 wedge。**超时分支禁止把 `this.proxy` 置 null**：core ownership 必须活到真实 stop settle，否则新 start 会绕过 `ERR_PROXY_STOP_IN_PROGRESS` 闸门去碰还没释放端口的旧 core。回滚有界视图必须保留（不能无限挂住调用方），ownership 则由 ownership token + hard-exit 票据 + continuation 兜住。
- `stop(graceMs)`：默认 server grace 为 **20000ms**；重入 `stop()` 复用同一轮公开等待视图，**不推进 generation**，新 grace 只按 `min(既有 deadline, now+newGrace)` 收紧：更长请求明确记 warning，**等值请求不刷无意义 warning**；收紧只重排尚未触发的 wait timer，公开 wait 一旦 timeout 就由 `hardExitArmed` 锁定唯一 hard-exit，不再重排。每轮建立私有 full `stopPromise`、公开有界 `stopWaitPromise` 与 `StopRound`（`token`/`startedAt`/`graceMs`/`deadline`/`coreStopRequired`/`coreStopTokenAtRequest`/`waitTimer`/`hardExitTimer`/`hardExitArmed`）；首次调用在同步路径捕获绝对 `deadline`，公开视图到点先 settle/reject，**之后才 arm hard-exit timer**，到期给 `logger.flush()` 1000ms 有界窗口后 `process.exit(1)`；公开超时绝不释放 full ownership、core 或 guard，也不得把 runtime deadline 传给 `graceMs`。full stop 迟到 settle 不得清掉已 arm 的 timeout hard-exit，保证公开 timeout 最终有且只有一次 exit；未 timeout 的成功/失败 stop 不会误退。`stopInternal(deadline, roundToken, graceMs, coreStopRequired, coreStopTokenAtRequest)` 的清理段（读 core → `beginCoreStop` → 有界 `logger.flush()` → `disposeProcessResources()`）整体在 `runCleanupExclusive` 临界区内：**core 快照必须在临界区内读取**（前一个 owner 可能刚释放/保留 core），且已有 `coreStopOwnership` 时是 **join 既有 stop 而不是再发一次**；请求时已存在的 core-stop token 在 full settle 后不会让排队 stop 重复触发。旧代 start 失败回滚仍在临界区时，本轮 stop 排队接管而不是并行清理，因此不会在旧 core 仍 `stopping` 时二次 `proxy.stop()`、也不会提前打出「代理已停止」。`disposeProcessResources()` 由 `finally` 保证执行；`finishStopRound` 按 Promise identity 收口（清未 timeout 的 timer/ownership/`shuttingDown`）并在此重试释放 core。真实 stop 失败保持主错误对象身份，flush/资源错误附加或聚合暴露；`allowProcessExit=false` 时 signal graceful 只记录并返回，公开 timeout 不 `exit(0)`，最终由已 arm 的 hard-exit 或宿主自行处理。
- `waitForStopSettled()`：公开 full-settle 逃生口；`stopWaitPromise` 超时后返回仍在持有的 `stopPromise`（或真实 `coreStopOwnership.settled`），让库调用方等待 core 真正收口，不通过重复 `stop()` 猜测 grace；无在途 stop 时立即 resolve。runtime 不 import server，也不把该方法塞进 `ProxyService` 结构端口。
- `EADDRINUSE`：提示查占用 + `pnpm start -- --port <next>`（逻辑在 `src/cli.ts`）。
- `runServer(options?)` 在 cluster 分支判断前显式 `initConfig()`，把 `allowProcessExit` 透传给 master 或 `ProxyServer`；单进程/worker 返回已启动的 `ProxyServer`，cluster master 没有本地 core、返回 `null`（没有可 stop 的句柄），只由 master 管理 worker。公共默认 false，库调用方需显式 `{ allowProcessExit: true }` 才由 server-owned 路径退出。CLI 则由 `ConfigService.load()` 完成同一初始化，并在 `src/cli.ts` 显式传 true。

## Cluster（`cluster.ts`）

- `clusterWorkers>1` 才 fork。master 在首次 fork 前安装具名 fork/exit/message/signal listener；**信号集合全平台是 `SIGINT`/`SIGTERM`，win32 上额外包含 `SIGBREAK`（Ctrl+Break）**——Windows 上 `SIGTERM` 永远投不出去（libuv `uv_kill` 直接 TerminateProcess），漏监听 `SIGBREAK` 会让 master 被控制台事件直接判死 `0xC000013A (STATUS_CONTROL_C_EXIT)`，连 `[cluster] master shutting down` 都打不出来，`sendShutdown` → 等 worker → `exitOnce(0)` 整段 IPC 优雅停机被跳过。判据 `process.platform === "win32"` 与注册方式刻意与 `ProxyServer.bindSignals()` 同一写法（两层不重复漏同一个信号），且**注册/移除严格对称**：`registerMasterListeners` 与 `removeMasterListeners` 共用同一个 `hasSigbreak` 条件与具名 `onSignal` 引用（匿名函数会导致摘不掉，监听器在已收口的 master 上复活）。`SIGBREAK` 复用同一条首次信号优雅停机路径（→ `shutdown()`）；第二次信号走 `SIGKILL` worker + 有界 flush + `exitOnce(1)` 的既有逻辑不受影响。生命周期/崩溃行走 `notice`（默认 error 级控制台可见）；worker 快速退出（`<5s`）1s backoff 重启，所有 rapid-restart timer 都由 master 持有，shutdown/failure 取消且 callback 再次检查状态。连续 5 次快速退出先封闭 `shuttingDown`/`failureStarted`、取消 timer、停止并有界收口所有 worker、移除 listeners，再按 `allowProcessExit` gate 决定是否 `exit(1)`；gate=false 时保留 rapid 原错并 reject/返回给宿主，不杀宿主但仍完成 worker 管理和 IPC 收口。master 的 shutdown/kill grace 走共享 `lifecycle-budget.ts`：`max(server stop 20s + hard-exit flush 1s + margin, upstreamTimeout + 5s)`，默认不会早于 worker 停机。shutdown 期间 worker 以 signal/nonzero 退出标记 unclean，最终码为 1；全部正常退出才是 0。早期 shutdown 即使尚无 worker 也能收敛，worker ready 时补发 shutdown；**第二个信号改 `exitOnce(1)`**（先尽力 SIGKILL worker 并给 flush 有界窗口；gate=false 只记录不退出）；signal/cluster listener 与 worker message 永远独立于退出 gate，不能因库模式关闭通信。
- `worker.send()` 始终传 callback，并给 `ChildProcess` 安装受控 `error` listener；异步 IPC 错误只记录，不转成未处理异常。首次 `cluster.fork()` 循环中途失败或 restart fork 失败时，先停止/强杀已创建 worker，取消 timer，移除全部 listener/timer，再把原始 fork 错误原样交给调用方；清理错误逐项记录/聚合。
