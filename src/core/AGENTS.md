# src/core — 代理内核

`types/`（唯一类型源）→ `server/`（建服骨架 + SOCKS 握手读取）→ `forward/`（`dial.ts` 执行层 + `base.ts` 胶水 + `inbound/` 四个入站适配器）+ `auth.ts` / `guard.ts` / `proxy-helpers.ts`（共享工具）。**传输策略不在本目录**（在 `src/plugins/forwarders.ts`）。各文件头 `@fileoverview` 是第一手说明，本文件只收敛跨文件的约定与禁区。

## 两个正交维度（`forward/` 的目录契约）

| 维度 | 载体 | 位置 |
| --- | --- | --- |
| **入站协议**（解析报文 / 答协议） | `ForwardInbound`：`http` / `connect` / `upgrade` / `socks` | `core/forward/inbound/{http,tunnel,websocket,socks}.ts` |
| **传输方式**（怎么搬字节） | `ForwardTransport`：`direct-stream` / `http-upstream` / `socks-upstream` | `src/plugins/forwarders.ts` |

唯一的接缝是 `core/forward/inbound/base.ts:dispatch` —— 按 `plan.transport` 从注册表取实现并 `forward(ctx)`。入站适配器**不持有 `Dialer`、不拼任何出站报文**；传输策略**不认 `ServerResponse`、不写 SOCKS 字节序、不读任何配置**。同一条 `direct-stream` 实现同时服务四条入站通道（已用一次性脚本黑盒验证：两条入站回灌后的字节完全一致）。

- `forward/base.ts:ForwarderBase` = 入站侧胶水（事件槽 / `emitWithUser` / `dialTarget` / `requireUpstream` / `refuse` / **`context()` 装配 `ForwarderContext`——`auth` 的唯一注入点**）。
- `forward/inbound/base.ts:InboundForwarderBase extends ForwarderBase` = 入站侧编排（`planRoute` / `preDial` / `denyUpstreamLoop` / `emitRoute` / `dispatch`）。
- `forward/dial.ts:Dialer` = 传输执行基础设施，**零配置读取**，不被入站侧直接调用。
- `ForwarderDeps` = `logger` / `auth` / `acl` / `routing` + **`forwarders` 注册表**；**已无 `config`**（出站 TLS 策略冻结进 `ForwardPlan.upstreamTls`）。`BaseProxy.forwarderDeps` 是它的投影，两处建入站适配器（http 三通道 / SOCKS 骨架）共用。
- 旧路径 `core/forward/{http,tunnel,websocket,socks,socks-reader}.ts` **已删、无兼容层**；`forwardHttp`/`forwardTunnel`/`forwardUpgrade` → `inbound/{handleHttp,handleConnect,handleUpgrade}`；`HttpForwarder`/`TunnelForwarder`/`WsForwarder`/`SocksForwarder` → `HttpInbound`/`TunnelInbound`/`WebSocketInbound`/`SocksInbound`。

## 类型（`types/`）

- `proxy.ts` 是 Single Source of Truth；`auth.ts` / `pipe.ts` 叶模块只做 `export type` 转发，禁止新增独立类型。
- 已删除、无需兼容：`types/connector.ts`、`types/server.ts` 整文件，`ProxyHttpServer`、`TokenExtractor`、`UpstreamTarget`、`DialHandle`、`ConnectorDial` 等，`AuthOptions.extractor` 假扩展点。
- **鉴权契约不再住在 `types/`**：`AuthProvider` / `AuthKind` 迁到 `plugins/contracts.ts`（注册表键即鉴权类型），需要它的文件一律从 `@/plugins/contracts.js` 导入。同理已删 `AuthOptions`（`type` switch 的配置形态已无意义）与 `ProxyOptions.auth`（鉴权改由 `ProtocolDeps.auth` 注入，不再是实例选项）。
- `plan.ts` **例外地** type-import `contracts.ts` 的 `AuthProvider`：`ForwarderContext.auth` 是出站凭证剥离的唯一判据，必须写进契约。`plan.ts ↔ contracts.ts` 因此是**双向 type-only 引用**——`import type` 在 JS 产物里被完全擦除、`.d.ts` 允许环状类型引用，运行时无环（`pnpm build:lib` 的库边界门禁只断言无 `runtime`/`cli.*`/`config/store`/`cordis`，不涉及此环）。**不得**为此改成 value import。

## 鉴权（`auth.ts`）

- **一类一实现，注册表键 = `AuthKind`**：`NoneAuthProvider` / `BasicAuthProvider` / `UidAuthProvider` / `JwtAuthProvider` 四个类，共同基类 `AuthProviderBase` **模块私有、不导出**（审计字段构造 + `enableLogging` 开关 + `authenticate` 模板 + 异常归约只此一份）。`Auth` 类与 `createAuthFromConfig()` 已删、**无兼容层**：「开不开鉴权」由组合根**选哪个实现**表达（`AUTH_ENABLED=false` → `NoneAuthProvider`，其 `isEnabled: false` 让基类模板直接放行且不发审计），不再是实例内的第二个开关。
- 账号住在 `AUTH_USERS_FILE`（`cfg/users.json`），**不在** env。账号表 / `JWT_SECRET` / `AUTH_LOGGING` 一律**经构造参数注入**（本模块不 import `config/store.js`）：provider 的重建时机归组合根（按 `ConfigScope` 生命周期），core 不再自己热加载。
- `basic` 命中任一账号的用户名+密码；`uid` 只比用户名；`jwt` 用户名取 token 的 `sub/username/user/uid/id`。凭证索引住在 `proxy-helpers.ts`（`buildCredentialIndexes` / `credentialIndexesFor` 单槽记忆 / `matchBasicCredential` / `matchUidCredential`），各 provider 只做薄委托，保证出站头剥离与鉴权用同一判据；结果带回 `username` 供逐连接日志。
- 失败闭环：账号形状非法 abort 启动（`validateAuthUsers`）；`authEnabled + basic|uid + 空表` abort（`assertAuthConfig`，见 `src/config/AGENTS.md`）；`authenticate()` **自身** try/catch 把任何异常归约为 deny（契约要求「永不抛错」），`BaseProxy.authorize()` 的捕获是第二道保险。
- Token：`Proxy-Authorization` 优先、`Authorization` 回退（RFC 7235，scheme 大小写不敏感）。
- 凭证防泄漏：`isProxyCredentialValue()` **已删**，判据收进 `AuthProvider.isOwnCredential(value)`；`isStrippableOutboundHeader(name, value, auth)` / `sanitizeHeaders(h, auth)` / `stripProxyHeaders(h, auth)` 显式收下本实例的 provider（`proxy-` 前缀分支不碰 auth）。basic/uid 的判据**必须比对整份账号表**（`credentialIndexesFor` 的产物），只比一个账号会让其余账号的凭证泄漏到目标站；**jwt 也参与出站剥离**——`isJwtShape(stripped) && verifyHs256Jwt(stripped, secret)`，不依赖账号表（jwt 允许空表），**任何「空表早退」都不许出现在该分支前面**。scheme 剥离形态与裸值形态各判一次（`credentialForms`）。已知边界：自定义注入的 `jwtVerify` 不被剥离判据感知（只认内置 HS256），方向仍是「宁可多剥不泄漏」。
- JWT：内置 HS256 校验 `defaultJwtVerify`（薄 async 包装 `proxy-helpers:verifyHs256Jwt`，`node:crypto` 零依赖：验签 + `exp`，永不抛，与出站剥离共用同一实现）由**组合根注入**（显式注入优先）；`JwtAuthProvider` 未注入校验器 = **一律 deny**（fail-closed，审计照打），刻意不在构造期抛错。
- `basic` 在 socks4/sockss4 额外接受 `USERID == username`（无密码字段）。
- 审计 `tag` 为 `"tunnel"` 仅当 `method === "CONNECT"` / `socks*` 协议 —— 不许用 `authority.includes(":")` 判定。auth 层零日志，审计经 `onAuthEvent` → proxy `auth` 事件 → server 层落盘。
- SOCKS 鉴权发生在握手后：socks5/sockss5 走 RFC1929 user/pass（auth 启用时），socks4/sockss4 用 USERID。

## 入站适配器（`forward/inbound/`）

- 四个入站适配器（`HttpInbound` / `TunnelInbound` / `WebSocketInbound` / `SocksInbound`）继承 `inbound/base.ts:InboundForwarderBase`（→ `forward/base.ts:ForwarderBase`），**构造器收 `ForwarderDeps`（logger/auth/acl/routing + `forwarders` 注册表）+ 可选 sink**。事件统一为 `PipeEvent`（泛型已删；`HelperEvent` 带索引签名可直接传入）。
- **入站侧零配置读取**：`forward/**` 不 import `config/**`，`ForwarderDeps` **已无 `config`**。目标、上游、传输方式、超时预算、监听地址、**出站 TLS 策略**全在 `ForwardPlan` 里冻结（`upstreamTls` 是本轮补进契约的——此前 `tlsPolicy()` 经 `deps.config.scope` 每次转发现读，是「转发器零配置读取」的唯一例外；热加载能力不丢：路由插件每次 `plan()` 现读 scope，改完对新请求即生效）。
- **`context()` 是 `auth` 的唯一注入点**：`ForwarderContext.auth`（必填）由 `ForwarderBase` 从 `deps.auth` 注入，传输策略拿它做 `sanitizeHeaders` / `isStrippableOutboundHeader` 的**出站凭证剥离**——判据必须与入站鉴权同源，漂移即把代理凭证泄漏给目标站。各入站不必各写一遍，也不可能「忘了传」。
- **`planRoute` 是路由决策与拒绝收尾的唯一入口**（`RoutingProvider.plan()` 的 `RoutingOutcome` 穷尽两分支）：拒绝时发 `type = rejection.reason` 的事实事件并把 `rejection.status` **原样**交给 `responder.fail()`。**状态码绝不合并**——名单拒绝恒 403、自环恒 502，**只有目标解析失败才回 400**（此前 `resolveForwardTargets()` 把拒绝与解析失败一起折叠成 null，调用方只能一刀切 400）。事件字段映射：`reason` → `type`（`loop-detected`/`target-denied` 稳定 grep 契约），`detail` → `detail`（target-denied 的名单原因 `blacklist`/`whitelist`）。
- `preDial` 保留为**纵深防御**（不依赖单个插件的实现质量）：`acl` 从 `deps` 注入、`listen` 从 `plan.listen` 传入，判定顺序仍是自环看 `dial`（经上游时即上游）→ 名单看 `dest`。**自环优先于名单**。
- `requireUpstream(plan, responder?)` 对「非 `direct-stream` 却缺 `plan.upstream`」**fail-closed**：发 `upstream-error` + 502。绝不静默回落直连——那会让本该走企业上游的流量绕过出口策略直连出去（泄漏比断链危险）。传输策略侧另有 `gateUpstream` 兜底（纵深防御）。
- `dispatch` 是两个维度的**唯一接缝**：`forwarders.require(plan.transport)` 对未注册键 fail-fast 抛错（装配错误），本方法就地收敛成「`upstream-error` + 502」，**不向数据面抛异常**。
- **协议应答经 `ProtocolResponder`（`core/types/plan.ts`）反转依赖**：各入站自建一个实现，转发链路不再直接写协议字节。**统一的是入口不是字节**——`fail` 的状态码语义码（400/403/502/504）由各协议自行映射（HTTP 写 `ServerResponse`；tunnel/upgrade 写预拼状态行 `httpReplyFor`；SOCKS 一律回 FAIL，**不区分**）。`establish` 的形态也各自不同：http 是**空实现**（上游响应即应答）、tunnel 写固定 200 行、upgrade **原样透传上游 101 响应头**（不自己拼）、SOCKS 回 replySuccess。
- **`relayUpstreamResponse`（可选钩子，传输策略遇非预期上游状态码时调）**：裸 socket 通道（connect/upgrade）原样把首包写回客户端（因此 CONNECT 客户端重新拿得到 `Proxy-Authenticate`，此前被窄化成 502）；http 通道写 `ServerResponse`（`incoming` 形态：`writeHead` + `pipe`，404/407/500 都是有效应答，**不得降级 502**）；**SOCKS 刻意不实现**（HTTP 字节写进 SOCKS 流即协议污染）→ 传输策略回退 `upstream-refused` 事实 + `responder.fail(502)` → FAIL。`head` 是「状态行 + 响应头 + 紧随其后的已读字节」整包。
- **SOCKS 入站的握手解析整体住在 `inbound/socks.ts`**（greeting / RFC1929 / SOCKS4 / 4a 哨兵 / SOCKS5 CONNECT + `badRequest` 的 `bytesReceived`），`SocksHandshakeReader` 在 `inbound/socks-reader.ts`（server 层 `socks-base.ts` 与入站适配器共用）。**建隧成功事实行**由 `establishedResponder` 在 `establish` 里发（文案按 `plan.transport` 三分支逐字复现 `tunnel established` / `tunnel via upstream` / `tunnel via socks upstream`）。
- **刻意不在入站侧的**：拨号、CONNECT/Upgrade 报文、`http.request` 语义转发、Host 回写、出站凭证剥离、拨号成因分流、余量回灌与桥接——全在 `src/plugins/forwarders.ts`（见该文件头与 `src/plugins/AGENTS.md`）。
- `dial.ts:Dialer`：**零配置读取**，全部事实经参数收下——`dialDirect`/`dialTls`/`choose` 收 `DialOptions`（`timeoutMs` = `plan.timeoutMs`、`tls: UpstreamTlsPolicy`（由 `plan.upstreamTls` 喂）、`target?`、`guard?`；`timeout` 由 `timeoutMs` 唯一决定，排在守卫展开**之后**，调用方误带 `timeout` 也改不写计划预算）、`dialViaHttpUpstream`（connect/socks 共用：拨 http(s) 上游 → 发 CONNECT → 等状态行；**绝不向客户端写字节**，成败应答归调用方；超时抛 `DialTimeoutError` 供调用方回 504）收 `opts.upstream: UpstreamEndpoint` + `timeoutMs` + `tls`、`dialSocks` 收 `SocksDialOptions`（版本与 TLS 承载**一律由端点的 `protocol`/`secure` 推导**，调用点不再重复推导）、`bridge`。`readReply(sock, n, timeoutMs)` 用 pause + `read(n)` 精确消费（跨 TCP 分段与余量回灌；**不许**在 data 回调里 `unshift`）。`handshakeSocks5` 的 CONNECT ATYP 按 `normalizeIp` 判族：family 6 用 `SOCKS5_ATYP_IPV6` + 16 字节地址（域名型是字符串、无 v6 语义），IPv4/域名沿用 `SOCKS5_ATYP_DOMAIN`（刻意简化）；SOCKS4a 无地址族字段，IPv6 亦按域名串交给上游（不加分支）。上游凭证（CONNECT 头行 / SOCKS4 USERID / RFC1929 子协商）一律取端点的 `username`/`password`，未配置即空串（旧语义）。
- `inbound/socks.ts:SocksInbound`：握手解析（`readGreeting` / `readUserPass` / `parseSocks4` / CONNECT）+ `serve()`（目标白名单 → `planRoute` → `preDial` → `emitRoute` → 上游端点 fail-closed + 上游自环 → `dispatch`；`badRequest(reader, message)` 收敛握手非法并把 `reader.bytesReceived` 作为 `bytes` 带进 `pipe` 事件，落盘等级由 server 层按字节数定（0 字节→debug、>0→warn，见下方「握手失败日志」条）；成功应答经 `establishedResponder` 在 `establish` 里写字节 + 发建隧成功事实，传输策略随后回灌余量并桥接）。
- **SOCKS 成功应答的 BND 字段（RFC1928 §6 / RFC1925 §3）**：走 `buildSocks5ReplySuccess` / `buildSocks4ReplySuccess`（`utils/protocol/socks.ts` 是字节布局的唯一来源，core 不手写偏移）逐连接构造；传输策略用 `utils/net/socket:getSocketLocalBinding` 鸭子类型嗅探出站 socket 的 `localAddress`/`localPort`（事实只存在于 socket 上），成对给出才经 `responder.establish({ local })` 交给应答器，否则传 `undefined`。硬规则：① **ATYP 恒 `0x01`（IPv4）**——改 IPv6 会把 10 字节应答变 22 字节，客户端按定长读取就会把隧道首字节当成答尾巴，因此**不引入 IPv6 应答形态**；② v4-mapped IPv6（`::ffff:a.b.c.d`，Windows/双栈常态）经 `utils/addr/address:normalizeIp` 归一为 4 字节；③ 真 IPv6 / 取不到绑定 → **回退 `0.0.0.0:0` 并发 `pipe` 的 `debug` 事件说明原因**（core 零日志），**绝不抛错、绝不让会话失败**；④ 失败应答（`SOCKS5_REPLY_FAILURE` / `SOCKS4_REPLY_FAILURE`）按 RFC 不要求 BND，恒为全零。
- **会话变体标签同源**：`SocksVariant`（`socks4`/`socks4a`/`socks5`）由 `socks4Variant(parsed)` 从 4a 哨兵判定，`CONNECT (...)` 分类行与 `tunnel established ... (...)` / `tunnel via socks upstream ... (...)` 成功行共用同一标签（4a 会话不得标成 `socks4` 误导排查）。标签反映**握手变体**、不反映传输（明文 socks4 与 TLS sockss4 同为 `socks4`）。
- `inbound/socks-reader.ts:SocksHandshakeReader`：握手缓冲读取器（`readExactly` / `readUntil` / `takeBuffered` + `dispose` + `bytesReceived`），server 与入站适配器共用，解决分段与 pipelining；**`timeout` 是必填选项**（本模块零配置读取，缺省会让多实例读到别的实例的预算），`maxBuffered` 仍是模块常量缺省 1024。
- `guard.ts`：`guardDialing`（上下游超时/错误/半关闭联动；`keepClientOnFailure` 置位 → 只毁上游、客户端留给调用方应答；**空 reply ≠ 调用方会写**，必须显式置位）/ `socksUpstreamGuard`（空回复 + 保客户端 + 成因上抛的选项工厂）/ `readResponseHead`（字节封顶 + CRLFCRLF + 严格状态码，**不毁 socket 不写应答**）/ `awaitStatusLine`（返回 `StatusLineResult` 判别联合，失败时毁上游，客户端收尾归调用方）。零日志，事件上抛。
- `proxy-helpers.ts`：**零配置读取**——本文件不再 import `config/store.js`、也不再查 ACL 名单，实例事实一律经参数注入（`AuthProvider` / `AccessControlProvider` / `RoutingProvider` 或字面量），否则同进程多实例时 A 实例的转发器会读 B 实例的配置。纯函数优先；`isStrippableOutboundHeader` / `sanitizeHeaders` / `stripProxyHeaders` 多收一个 `auth: AuthProvider`（凭证形态判据），`upstreamAuthValue`/`upstreamAuthHeaderLine` 收 `credentials: {username, password}`，`isSelfLoop(h, p, listen)` 收监听地址，`PreDialOptions` 多 `acl` 与 `listen` 两个字段。**裸判定入口是 `resolveRoute(dest, mode, acl)`**：`mode !== "client"` 短路 `{mode:"server", route:"direct"}`（不查 `upstream` 组）；client → `acl.checkUpstreamRoute`，名单命中回落 `{mode:"server", route:"direct", reason}`（dial/path/凭证/Host/secure 全按 server 语义自然回落），否则 `{mode:"client", route:"upstream"}`。**成对入口是 `resolveForwardTargets(url, hostHeader, routing[, inbound])`**：解析 dest 后**委托路由插件** `routing.plan()`（本函数内零配置读取），按 `plan.transport === "direct-stream"` 选 dial（否则取 `plan.upstream` 冻结的上游端点），把计划投影回 `{dial, dest, route}`；解析失败或**路由拒绝都返回 null**（拒绝的 status/detail 在此被合并）。**四个入站适配器一律不调这两个便捷入口**：它们直接消费 `routing.plan()` 的 `RoutingOutcome`（经基类 `planRoute`），分支判据是 `plan.transport`，**禁止在请求路径裸读模式/上游配置**。此前 websocket 的「socks 上游早分支」（目标尚未解析就按 `proxyMode`+`upstreamProtocol` 分流、进来后再自行 `resolveRoute`）已随本轮消失——目标是唯一入口，先解析再决策。`resolveRoute` 纯函数不打日志；路由事实经 `forward/inbound/base:emitRoute` 发 `route` 事件（**过 preDial 每请求恰一条、拒绝路径与 server 模式短路零条**，判定依据是 `plan.routeReason`），`[route]` info 行（字段 `target`/`route`/`reason`）由 `src/server` 落盘、与事件 1:1。目标主机必过 `isValidTargetHost`（字符白名单 + 255B，防 CONNECT/SOCKS 报文注入与长度域截断）。`guardPreDial` 语义：自环看 `dial`、名单看 `dest`（**名单永不判上游**，见 `src/config/AGENTS.md` 访问控制）。

## 服务端骨架（`server/`）

- `base.ts:BaseProxy`：状态机 `idle → starting → running → stopping → stopped`（可重入 `starting`），`start()`/`stop()` 幂等模板方法。**启停票据（deferred）必须先登记再 `setState`**：`startInFlight`/`stopInFlight` 在 `setState("starting"/"stopping")` **之前**同步登记（无 await），票据 promise 预挂 noop rejection 消费器，因此 `stateChange` 监听器同步重入 start/stop 只会复用同一在途 promise，绝不并发第二个 `runStart`/`runStop`；票据一律 identity 比对释放，迟到结果只能释放自己的。`stop()` 在 `starting` 态先 await 在途 start 票据（吞掉其异常），`stopping`/任何在途清理都复用同一份完整 stop Promise，**`state=stopping` 不得提前返回**。停机顺序固定为 `onBeforeStop → doStop → onStopped → markStopped → setState(stopped)`：`onStopped` 完成前不发布 `stopped`，钩子失败转 `error` 并原样透出。（`runStop` 的短路分支——无 server 且非 running/error——没有钩子要执行，直接落 `stopped`，不属完整停机路径。）
- **`setState` 是生命周期成败判定的边界**：`this._state = next` 先落地再 `emit("stateChange")`，且 emit 整体 try/catch 就地隔离（与 `authorize` 的 emit 保护同形）。`stateChange` 是订阅方契约，监听器抛错不得冒泡进控制流——否则 `runStart` catch 里的 `setState("error")` 会顶掉原始启动错误，`runStop` 末尾 `setState(stopped)` 抛错则会把已 `markStopped` 的正常停机误报成 `error`（重试还会再撞一次 error 态的 stop 路径）。core 零日志，此处**不打印**监听器异常（同 `socks-base` 的 emit 保护注释）；兜底代价仅为 EventEmitter 语义下抛错监听器之后的后续监听器被跳过。
- **core 层 start 准入闸门**：`stopInFlight` 存在或 `state === "stopping"` 时 `start()` 一律以 `ProxyStopInProgressError`（`code: "ERR_PROXY_STOP_IN_PROGRESS"`）拒绝——该判定必须排在 `isRunning()` 快捷路径之前，否则「正在关服但 server 仍 listening」会被判成启动成功，或并发跑第二个 `doStart`。**code 与 server 层停机 ownership 闸门完全一致**（`ProxyServer.start()` 有同 code 的模块私有错误类，调用方按 code 统一处理，`instanceof` 不可跨层复用）；调用方在 full stop settle 后显式重试；`stateChange(stopped)` 同步重入的 `start()` 同样被拒（stop 尚未 settle），`await stop()` 之后才可重启。`ProxyLifecycleErrorCode`（types/proxy.ts）是**四个**生命周期码（stop-in-progress / start-cancelled / service-operation-timeout / close-timeout）的**类型单一来源**：`base.ts` 的 `code` 字段以 `satisfies ProxyLifecycleErrorCode` 绑定字面量（漏登记即编译失败，联合将来新增码也不会把字段类型悄悄放宽）；runtime 只允许 type-only 绑定，不引入 server/core 运行时耦合。新增码必须先登记进联合再落地实现，禁止各处裸写字面量或另开 `string & {}` 假扩展点。
- **`closeServer()` 是关服成败的唯一判据，且 `this.server` 只在它 resolve 之后清空**：四条失败路径**一律 reject，绝不吞错**——① `close` 回调带 error（原样透出，含 `ERR_SERVER_NOT_RUNNING`）；② `close()` 同步抛错（此时**不排空**：close 未生效，动作建立在不确定状态上，交给重试）；③ `registry.drain` 同步抛错（排空没兑现即非成功）；④ `close` 回调在有界 deadline 内没来 → `ProxyCloseTimeoutError`（`code: "ERR_PROXY_CLOSE_TIMEOUT"`，见下）。四条失败都经同一个 `finish` 收口，顺手 clearTimeout——靠 Promise executor 自然抛出的话，已 reject 的 promise 还会留一个 ref 定时器把事件循环吊住 10s。`http.ts` / `socks-base.ts` 的 `doStop` 因此一律是「取局部引用 → `await closeServer(...)` → 成功后才 `this.server = null`（带 identity 比对，防误清并发建起的新引用）」，**禁止先置空再 await**：提前置空会让失败重试的 `doStop` 看到 null 引用直接返回，把仍 listening 的 server 洗成 `stopped`（端口仍被占、后续 start 还会 EADDRINUSE），并让 `isRunning()`/`getStats()` 谎报非运行。close→drain 顺序（close 先拒新连接、drain 再拆存量）保持不变。
- **关服 deadline（有界失败远好过永久 pending）**：`closeServer` 内置 `CLOSE_DEADLINE_MS`（10s）只作安全网，不是预算旋钮。取值必须**小于** runtime 的 15s service deadline 与 worker 的 20s stop grace（`src/server/lifecycle-budget.ts`），否则「close 永不兑现」会被外层超时/强退掩盖，core 连失败事实都报不出来。超时以 `ProxyCloseTimeoutError`（`code: "ERR_PROXY_CLOSE_TIMEOUT"`）reject 并保留 server 句柄——`runStop` 因此永远不会因关服而 pending，调用方拿到的是 `error` 态 + 可重试句柄。**定时器刻意保持 ref，不 unref**：deadline 的职责是把挂起转成**可观测**的失败，unref 后「loop 上再无其它 handle」时进程会静默退出、拒绝无人收，正好毁掉 deadline 的意义；正常路径 resolve 时立刻 `clearTimeout`，不拖慢退出。**新增码必须先登记进 `ProxyLifecycleErrorCode` 再落地实现**（本次已登记 `ERR_PROXY_CLOSE_TIMEOUT`），禁止裸写字面量。
- **关服失败 ⇒ `error` 态 + 可重试，不得吞错**：`doStop` reject 后 `runStop` 转 `error` 并原样透出，`this.server` 引用保留，于是 `stop()` 重试会真正重试到**同一个** server（重复 `close` 由此天然收敛在单一路径，`stopInFlight` 票据保证不并发二次 close；`error` 态不被 null server 洗白）。`ProxyServer` 侧本就按 `error` 处理（丢弃旧 join 票据、下次 stop 重新触发真实 `proxy.stop()`），两层契约一致，`start` 闸门/ownership 不因本次改动放宽。已知代价（刻意的诚实性权衡）：Node 只在 handle 已空（从未 listen / 已关闭 / 正在关闭）时给 `ERR_SERVER_NOT_RUNNING`，该错等价于「已不再 listening」，所以对这类 server 重试 `stop()` 会再次 reject 而非转 `stopped`——这条路径只在「上一次 stop 已失败」后才可能到达，调用方按 `error` 处理；**绝不要为让 `stop()` 变绿而把该错当成功 resolve**。
- **原始 socket 必须在 `connection` 事件登记（TLS SOCKS 的坑）**：`http.ts:bindServer` 与 `socks-base.ts:doStart` 都在 `connection` 上 `registry.track`，**不能只依赖握手/请求完成后的回调**——`tls.createServer(options, listener)` 的 listener 挂在 `secureConnection` 上，握手未完成/失败的连接只出现在 `connection` 事件里（tls.Server 内部监听器随后把 raw socket 包成 TLSSocket）。只登记 `onConn` 会让握手未完成的 socket 永远不在 registry 里：停机 `drain` 拆不掉它，`server.close` 回调永不兑现（`close` 只停 accept、不动存量连接），`stop()` 只能等 deadline 才有界失败。明文分支与 `onConn` 拿到同一对象，`ConnRegistry.track` 的 Set 按 identity 去重，不会重复计数。
- `ConnRegistry`（`track`/`drain`，http/socks 共用一份）+ `closeServer()` 关服模板 + `authorize()`（异常转 deny）。`drain` 的两条销毁路径**互补、都必须走**（不是二选一分流）：① 传入 server 且具备原生 `closeAllConnections()` 时**仍要调它**，兜底 registry 没登记到的连接；② **无条件**对 tracked 集合逐条 `destroy()`。**不变式：原生 `closeAllConnections()` 不覆盖 hijacked socket**——CONNECT 隧道与 upgrade 后的 WebSocket 劫持后已被移出 http.Server 的连接表，原生快路径一条都杀不掉，而 `server.close(cb)` 恰恰要等这些 socket 结束才兑现回调。把原生快路径当成「已排空全部连接」的保证，会让 close 回调永不兑现、只能等 `CLOSE_DEADLINE_MS` 超时 → `ProxyCloseTimeoutError` → 停机必然 exit 1（SOCKS 分支无 `closeAllConnections()`、逐条 destroy，同场景毫秒级干净停机）。因此 tracked 集合的显式销毁**不可省**，与 SOCKS 分支行为对齐。它必须在 `close()` **之后**同步触发（close 先拒绝新连接，drain 再拆存量），否则 `close` 回调要等 keep-alive/隧道连接自然结束。根 AGENTS.md 只保留状态机契约。
- `protocols.ts`（新，**取代已删的 `factory.ts`**）按 `ProxyProtocol` 注册 6 个 `ProtocolProvider`；**编译期 switch 建实例已彻底删除**（`factory.ts:createProxy()` 与其 `new XxxProxy(...)` 六路分支一并删掉，无兼容层），未注册协议由 `createProtocolRegistry().require()` 抛错（fail-fast），**任何 switch/默认实现兜底都不许加回来**。协议类本身仍是薄壳：`http.ts`（`HttpProxy`：request/connect/upgrade 三通道 + `handleForward` 名单→鉴权→委派 + `gateResponder` 闸门应答器）被 `https.ts` 继承复用（仅重写 `doStart` 建 TLS 服），四个 SOCKS 文件只透传 `(options, deps, runner)`。**依赖一律经构造注入**：`BaseProxy(protocol, options, deps)` 收 `ProtocolDeps`（config/logger/auth/acl/routing/forwarders），`authorize()` 走 `deps.auth`、客户端名单走 `deps.acl.checkClientIp(addr)`（**不再直读 `config/resources/acl/eval` 的模块级入口**，同进程多实例会读到别人的名单），协议层日志器取 `deps.logger.child(protocol)`（实例级，不落进程级 logger）。`BaseProxy` 另备一份 `forwarderDeps`（`ProtocolDeps` 去掉 `config` 的投影，**含 `forwarders` 注册表**）供 http 三通道与 SOCKS 骨架建入站适配器共用。
- **闸门阶段的 `ProtocolResponder` 由入站协议插件构造**（`HttpProxy.gateResponder`）：名单拒绝/鉴权未过都发生在转发之前，此刻只有协议层能写字节，故同一通道上「http 写 `ServerResponse`」与「tunnel/upgrade 写预拼裸报文」两形态由 `GATE_REJECT_REPLY` 一处收口（`establish` 是空实现——http 通道的成功应答即上游响应本身；`username` 恒空串，闸门失败时无会话身份；未登记状态码回 502 预拼报文，绝不猜成 407/403）。转发阶段的应答器由入站适配器自建（见上方「入站适配器」条），两侧共用同一份 `ProtocolResponder` 契约。
- **transport error 不得越权改生命周期**：`http.ts` / `socks-base.ts` 的底层 server `error` handler 只能 `emit("serverError", …)`（配套的 client/socket 错误只能发 `clientError`/销毁），**禁止 `setState("error")`**；生命周期 `state` 只能由 `BaseProxy` 的 `start/stop` 模板方法依据启停成败改写。这样 stopping 期间的传输错误仍保留为 `serverError` 事实，随后由 `runStop` 收口为 `stopped`，不会被错误改写成 `error`。
- `socks-base.ts`（`SocksProxyBase` + `PlainSocksProxy` / `TlsSocksProxy`：`createListener` 是明文/TLS 唯一差异点；`doStart` 在 `listen` 之前绑 `connection` → `registry.track` 登记原始 socket，这是 TLS 握手未完成连接的唯一登记点，见上）+ `socks-session.ts`（`runSocks4Session` / `runSocks5Session`，经 `SocksSessionHost` 最小接口注入，**不含日志器**）。四个 SOCKS server 文件是 21 行薄壳；监听器 `error` 与 http 同形只发 `serverError` 事件，不改生命周期 state。
- `socks-base.ts:onConn()` 首行过客户端名单（拒绝走 `pipe` 的 `ip-denied`，与 http 同形）；握手后 `authorized` 兜底是保险，主力是 `tlsClientError`（机制见 `src/utils/AGENTS.md`）。`doStart` 以 `.catch` 兜住 `onConn` 的意外抛错：销毁 socket 并发 `clientError` 上抛（core 零日志），避免 unhandledRejection。
- **握手失败等级由 server 层按「本次连接已收字节数」定级（裸 TCP 探活 ≠ 握手失败），core 只发事实**：`SocksHandshakeReader` 只增不减地统计 `bytesReceived`（**读取器自维护，不依赖任何 socket 属性**，可靠），并把它作为第二参传给 `onTimeout` / `onInvalid`；`socks-base.ts:onConn` 只把它作为 `bytes` 字段带进 `pipe` 事件（`client-timeout` / `bad-request`，另带 `client`），**core 不定级、不打印**（原 `levelForBytes()` 与 `logClientTimeout`/`logBadRequest` 调用已删），等级单点收在 `src/server/index.ts:bindProxyEventLogs`——**0 字节 = 端口扫描/健康检查的裸 TCP connect+close（或连上不发就断），是环境噪音 → debug**；读到过任何字节（超时/缓冲超限/格式非法）维持 warn。判据是**字节数**而不是错误码文本（`ECONNRESET`/`closed` 同样会出现在真实握手中断上）。**入站适配器侧的畸形握手走同形路径**：`SocksInbound.badRequest` 把 `reader.bytesReceived` 作为 `bytes` 字段带在 `pipe` 的 `bad-request` 事件上，server 层按同一条字节数规则定级。两条路径现在**同码同判据**（都是 `bad-request` + `bytes`），新增握手失败回调必须走 `pipe` 事实，不得再直接 `logBadRequest`/`logClientTimeout` 硬编码等级。TLS 侧**目标同形但判据不同**（那边只能按 `err.code`，`TLSSocket` 包装层的 `bytesRead` 恒为 0 不可用，见 `src/utils/AGENTS.md`）：`bindTlsClientError` 与 mTLS `authorized` 兜底仍经注入的实例日志器由 utils 打印（core 不直接打印，打印动作在 utils）。

## 本目录 Gotchas

- `http.Server` 的 `connect` socket 是 `Duplex` 不是 `net.Socket` —— 全链路用 `Duplex`。
- Status-line 等待（CONNECT 的 200、Upgrade 的 101）统一走 `awaitStatusLine`；超时预算来自 `plan.timeoutMs`（本层不读配置）只兜时间不兜内存（另有字节封顶）。
- SOCKS 域名是客户端原始字节（不过 HTTP 解析器）：解析/建握手前必过白名单。
- SOCKS4a 哨兵判 `DSTIP ∈ 0.0.0.0/24`：规范草稿写全 0、curl/PySocks 发 `0.0.0.1`，两者都得认；漏全 0 会误判纯4、域名残渣被当载荷打进隧道（客户端拿假 90 后收到 400）。修改握手时必须同时验证 `0.0.0.0` 与 `0.0.0.1` 两种哨兵。
- client 模式经 http/https 上游的 Upgrade 报文保留 absolute-form + 注入 `Proxy-Authorization`（`buildUpgradeReq(..., { toUpstreamProxy })`）；经 SOCKS/直连用 origin-form 且绝不带上游凭证。分流唯一依据是 **`plan.transport === "http-upstream"`**（`toUpstreamProxy` 的判据）：命中 `upstream` 路由名单时计划即 `direct-stream`（直拨真实目标），请求路径不许裸读 `proxyMode`（见上方 proxy-helpers 条）。
- 拨号失败成因区分：超时（`DialTimeoutError`）→ 504，其余 → 502；SOCKS 回 FAIL 不区分。catch 里一刀切 502 会吃掉超时成因。
- **转发报文 authority 一律经 `formatAuthority` 补 IPv6 方括号**：解析侧 `parseTargetParts`/`parseAuthority` 刻意剥方括号以便 `net.connect` 直用，拼装侧不补会产出 `CONNECT ::1:443` / `Host: ::1:443` 畸形报文。已收口：`buildConnectRequest`、`buildUpgradeReq` 的 Host 回写、`http.dialViaSocksAndForward` 的 Host 重写。
- `tunnel.handle` 解析 authority 失败回 **400**（客户端请求报文非法，与 http/websocket 解析失败语义一致）；502 只留给网关侧失败。
- Upgrade 非 101（`inbound/websocket.ts` 的 `relayUpstreamResponse`）：透传首包（状态行+响应头+已读字节）后按 `upstream.readableEnded` 分流——已 EOF 则 `client.end()`，否则 `upstream.pipe(client)` 续传剩余 body（`Content-Length` 大于首包时客户端不挂等）；**`readableEnded` 分支不可删**（`'end'` 可能早于续体挂 pipe 前发出）；上游错误/关闭收尾归 `guardDialing` 既有 handler，不额外 destroy。
- `cfg/users.json` / `cfg/acl.json` 热加载语义（1s 节流、坏文件保留旧值、缺失=空）见 `src/config/AGENTS.md`。
- **core 零日志禁区**：`src/core/**` 禁止直接打印日志（生命周期行也不行），事实一律经事件上抛（`pipe`/`serverError`/`auth`/`forward`…），落盘收在 `src/server/index.ts:bindProxyEventLogs`；向 utils 注入 logger（`loadCerts`/`bindTlsClientError`）不算打印——打印动作在 utils。
- 组合验证规则：新增入站 × 上游 × 证书组合时完成对应端到端黑盒验证；名单或路由变更须覆盖 target/upstream 真值表、允许请求的 `[route]` 事件恰一条，以及拒绝路径和 server 模式的零事件行为。
