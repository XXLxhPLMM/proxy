# src/core — 代理内核

`types/`（唯一类型源）→ `server/`（建服骨架）→ `forward/`（转发器）+ `identity.ts` / `identity/`（身份域） / `guard.ts` / `access-control.ts`（访问控制） / `traffic/`（流量配额）/ `helpers/`（共享工具目录）+ `log-events.ts`（core 事实 → `[event-code]` 文本词汇层）。各文件头 `@fileoverview` 是第一手说明，本文件只收敛跨文件的约定与禁区。

**依赖方向单向**：`core/server → core/log-events → utils/logger`，core **不依赖 `src/server`**。core 只允许 import `@/utils/*` 与 `@/config/*`；**禁止** import 任何 `@/server/*`。跨目录优先走层 barrel（`@/utils/{logger,constants,tls,json-file}/index.js`、`@/config/files/rules/index.js`、`@/core/helpers/index.js`）；`utils/ip.ts` 与 `utils/host-text.ts` 是单文件叶子、无 barrel，只能直接引。

## 三个可插值端口

core 与四条入站通道**只认端口，永不自己造实现**。三个端口都是「外部调用方真的会注入替身」的那种——判据不是「core 内部用到了」，而是**库调用方能不能换掉它**：

| 端口 | 声明处 | 唯一内置实现 | 回答的问题 |
|---|---|---|---|
| `IdentityProvider` | `types/proxy.ts`（经 `types/identity.ts` 转发） | `identity/factory.ts:createIdentityFromConfig` + `identity/modes.ts` 四插件 | **你是谁**（认证） |
| `AccessControl` | `types/proxy.ts` | `access-control.ts:createFileAccessControl` | **你能访问哪里**（授权） |
| `ConnectorSource` | `forward/upstream/connector/types.ts` | `forward/upstream/connector/registry.ts:createConnectorSource` | **怎么到达 dest** |

`CoreServices`（`types/proxy.ts`）= core **内部归一后**的 `{ identity; access; traffic }` 三项全必填包。`trafficLedger` **刻意不在里面**：落盘账本是 runtime 独有的副本，core 从不打开账本文件、也从不给它起定时器，塞进 core 的包等于向 core 承诺一件它不做的事。

### 三条不可协商的裁决

- **`isOwnCredential(name, value)` 必填、无缺省、不可返回 `undefined`；库层对「每一个出站头名 × 每一个头值」都问一遍。** 判据**必须由插件给出，绝不能从 `config` 猜**——`authEnabled`/`authType`/`jwtSecret` + `users.json` 只能覆盖「配置即身份真相源」那一种世界；**身份一旦可插值，凭证形态由插件决定**（自定义头名、HMAC 摘要、云厂商网关签名……），config 就不再是真相源，**从 config 猜必然失配**。而失配的代价不是「剥多了」（目标的 `Authorization: Bearer <token>` 被误剥，最多少送一个头），而是反过来——**代理自己的凭证被原样转发给目标站**。所以三条推论必须同时成立：判据由插件给出（只有它知道自己的凭证长什么样）；判据必填（漏实现要在**编译期**红，而不是运行期默默泄密）；判据**对每个出站头名都可能被问到**。护栏：`tests/integration/custom-services-wiring.test.ts` 用一个只认 `ApiKey <secret>` 自定义 scheme 的替身，断言**它认的那个被剥掉、客户端给目标站的 Bearer 不被误剥**。
  - **两条判据为什么必须分开、且顺序不可换**：`proxy-` 前缀是**协议规则**（RFC 7230 §7.6 的命名空间，与身份无关，`isProxyHeaderName` 是**零依赖纯函数**，`core/error-boundary.ts` 在**拿不到任何插件**的上下文里也要用它，**签名一字不许动**）；凭证形态是**身份规则**（只有插件知道），故**每个出站头名都问一遍**、库层不做任何头名限制。把头名门禁加回去，等于把插件的凭证形态重新关进 `authorization` 这一个名字里——库调用方用 `X-Api-Key` 鉴权时，那个 key 会**原样转发给目标站**。协议规则在前，是因为它无条件、且那个头**根本不该问插件**（否则「插件漏实现」有机会把 `Proxy-Authorization` 放出去）。
  - **⚠️ 代价如实写**：委派次数 = **每个出站头 × 每个值**。空判据插件每头 ≈44 ns（一次 `toLowerCase()` + 一次 `!==`）；内置四插件的廉价早退在 `core/identity/token.ts:ownCredentialForms` **首行**（`name.toLowerCase() !== "authorization"` 即返回，`FileAccountIdentity` 前面还有一层 `!isEnabled`），17 头典型请求 `1.315 → 1.612 µs`（+0.3 µs，噪声里）——**那是它们自己的优化，不是端口的限制，自定义插件不必照抄那个早退**。**配置驱动动态门面** `core/identity/factory.ts:createIdentityFromConfig`（CLI 与 `createProxyRuntime` 走的正是这一条）是唯一的大头，每次委派 ≈ **1.8 µs**、17 头 ≈ **31 µs/请求**。⚠️ **归因不是「每请求现造一份快照」**——逐项实测（esbuild bundle + Node 22 + Windows，17 头，每次 `live()` 调用）：**`loadAuthUsers(config, obs)` 1793 ns / 87.7%**、`new FileAccountIdentity({...})` **12 ns / 0.6%**、`4 × config.get` 31 ns / 1.5%。涨上去的是 **`readJsonCached` 的编排被调了 N 次**，不是快照被构造了 N 次。**`live()` 已记忆化**（`liveSnapshots`：`WeakMap<ConfigAccessor, LiveSnapshot>`，六个输入每次现读、逐项比身份后复用快照）——但**别把它写成性能优化**：实测只省 0.2–1.6 µs/次（噪声底量级），它消除的是**重复构造**。**`fs.stat` 次数不变**（1s 节流按文件计）。**⚠️ 剩余成本缺口（如实记账）**：`readJsonCached` 编排（`path.resolve` 占 `loadAuthUsers` 的 **44%**）**× 每请求出站头数**；三条修法（提出 `path.resolve` / 每次 `sanitizeHeaders` 只读一次账号表 / 用 `Date.now()` 记忆）**都必须先裁决**，最后一种被本仓**明确禁止**（会把正确性耦合到 1s 节流上）。不许为省任何一条加回头名门禁。
- **`AccessControl` 的三个方法必须同步。** `checkRoute` 被**四条入站通道**在**拨号之前**调用，返回值要立刻喂给「选哪个连接器 / 拒绝应答 / 发 `route` 事件」这一整串**同步**控制流。改成 `async` 会级联炸掉整条转发链（每条通道各多一个 `await` 边界、`resolveForwardTargets` 连带变 async、转发器入口签名与两阶段准入的时序全部要重排）——为「将来也许要查个远程策略」付这个代价不划算。**需要远程查策略的诉求归 `identity`**（`identify` 本来就是 async）：身份判定的结果允许等，准入判定不允许。
- **`proxyMode` 模式门留在 `resolveRoute`，不许进 `AccessControl.checkRoute`。** `proxyMode` 是**路由模式**决定，与「谁被允许访问哪里」**正交**。塞进判定层（无论是让 `checkRoute` 去读 `proxyMode`，还是给 `AccessRouteInput` 补一个模式维度）都意味着**每个自定义策略实现都得重写一遍模式门**——策略端口漏进路由关切比「工具层读配置」更坏。故 `RoutePolicy` 把 `mode` 与 `access` **并列**交给 `helpers/route.ts`，端口只回答「这个目标该直连吗」。**短路健在且就住在那里**：`resolveRoute` 的第一行就是 `if (policy.mode === "server") return { mode: "server", route: "direct" }`（不查名单、**不带 `reason`**）。`access-control.ts:checkRoute` 的注释现在只**陈述这条已定结论 + 理由**，并点明「不要因为读了它就去 `checkRoute` 里加模式门」——**那段注释必须永远是「已定结论 + 理由」**：把它写成「未决的跨文件契约」正是「下一个人照着注释去判定层加模式门」的触发点。

### 放宽 `reason` / `source` 的代价（写清楚免得下一个人又收回去）

`AccessDecision.reason` / `source` 与 `PipeTargetDeniedEvent.source` **从闭合字面量集放宽为自由 `string`**：名单判定只会说 `whitelist`/`blacklist` / `global`/`user`，但端口一旦对外暴露，替换实现可能是限速引擎、地理封锁、订阅制网关——闭合集会让它们**没法用类型描述自己的结论**，只能回去 `as never` 强转。

代价是**消费方不能再假设取值**，于是两条负向纪律变成硬要求：
- **`runtime/bridge.ts` 原样透传、不认闭合集**：若表外值被静默吞掉（不发布 `access.target-denied`），那等于**安全事实消失**（一次拒绝在事件流里彻底不见），比「载荷里带一个没人认识的 reason」坏得多。自定义策略引擎判出的 `"rate-limited"` / `"geo-blocked"` 照常发布。
- **「缺失即跳过，绝不臆造」那半条纪律保留**：`reason` 缺失/空串**仍不发布**（载荷里没有 reason 就没有「为什么被拒」这条事实）；`target-denied` 的 `host` 缺失同样跳过（公共契约必填）；`source` 缺失**不倒填成 `global`**（那会把「个人名单拒的」伪装成「全局拒的」，运维去改错文件）。
- **内置引擎的自律仍在源码级**：`access-control.ts` 的 `hostDenied` 只返回 `whitelist|blacklist`、`checkClient`/`checkTarget` 只给 `source: "global"|"user"`，`AclReason` 是**模块私有类型、不导出**。这是「守卫从编译期降级为自律」的现状——护栏 `tests/unit/access-control-port.test.ts` 断言 `createFileAccessControl` 的真值表，`tests/integration/custom-services-wiring.test.ts` 断言**闭合集之外**的 reason 也能穿过桥接层。

### 缺省档与「显式的没有」——**只有两个**，因为 `access` 缺席是「取消防护」而不是「关闭功能」

`ProxyOptions` 上**四个**注入位里，**三个可选、各自带一个显式缺省档**（`BaseProxy` 构造期归一**一次**，全仓唯一做这件事的地方），**`access` 不在其中——它是必填的**：

| 选项 | 缺省档 | 语义 |
|---|---|---|
| `identity` | `NONE_IDENTITY` = `noneIdentity()`（冻结单例） | **不判身份**（恒放行、恒不剥凭证） |
| `traffic` | `INERT_TRAFFIC_ACCOUNT` = `inertTrafficAccount()` | **不计量** |
| `connectors` | `createConnectorSource(options.ctx)` | 装配期只解析一次 |
| **`access`** | **无**（`ProxyOptions.access: AccessControl`，**无 `?`**，core 侧零缺省解析） | — |

**⚠️ 为什么只有两个 inert 档（`identity` / `traffic`），`access` 走编译期必填**：

前两者的缺席读作**关闭一项功能**——不鉴权、不计费。它们各有一个语义明确的 inert 档，于是「忘注入」在运行期有一个**说得清**的答案，而不是怪问题；且那个答案落在**安全的一侧**（少一道功能，不是多一道风险）。

`access` 的缺席读作的是**取消防护**：缺省即全放行，而**全放行是所有失败形态里最危险的一种**——黑名单命中仍返回 200、SOCKS 应答 `05 00` 而非 `05 01`、该回落直连的请求走上游，**且零信号**。它与前两者**方向相反**，所以**不能**套用「缺省 = 显式 inert 档」那套：那套的前提是「缺席落到安全的一侧」，这里的前提恰恰相反。判据仍是仓库的通用纪律「**缺席会走到哪条路**」——缺席走到「放行」，于是必须**编译期**拦住。

**代价如实记**：低层直构 core 的调用方（测试、嵌入方）从此必须显式写一份判定。**想要「不判名单」就写一份显式放行实现**（测试侧那份在 `tests/helpers/access.ts:openAccessControl()`），那比省略多一行代码，换来的是「这一行是**你写的决定**」而不是「core 替你猜的」。

- **别给 `access` 加缺省档**：`OPEN_ACCESS_CONTROL`（那个「显式放行档单例」符号）在全仓**不存在**，`BaseProxy` 里 `access: options.access` 不带 `??`。加了会让「忘注入」变成「配了名单却全放行、且零信号」；改成「缺省一律拒绝」（fail-closed）也不行——「只想跑直连、不部署 acl.json 的最小部署」会被自己拒绝。两侧各有具体危害，所以**两侧都不做**，把决定交回编译期。
- **护栏**：`tests/unit/access-control-port.test.ts` 的「源码级：`access` 的必填性与缺省档删除（防复活）」三条 —— ① `types/proxy.ts` 的 `access:` 声明行**不带 `?`**（`codeOnly` 后逐行匹配，防「有人加回 `?` 又顺手把 20+ 处构造点补成显式放行」这种**能过全部检查**的改动）② `base.ts` **零 `OPEN_ACCESS_CONTROL`**（**锚点今天仍有牙齿**：那个符号只在 `base.ts` 里出现过，锚在别处会恒真；「access 缺省解析」在运行期已无任何形态可测，源码级是唯一有牙齿的判据）③ 正向证据：`runtime/services.ts` 仍解析默认实现（防前两条变成「把功能删了也算过」）。
- **⚠️ 别把这两条写成「锚在已删除的符号上」的恒真空断言**（本仓踩过两次的假绿形态，见 `tests/AGENTS.md`）：`OPEN_ACCESS_CONTROL` 之所以合格，是因为本条断言的作用域是「**从现在起不许它回来**」；而「`access` 缺省 = 放行」这类**行为**断言已随那个常量一并删除——它锁的正是我们要消灭的东西。

**「配了 `acl.json` 却没生效」这条缺口已闭合，判据是编译期 + 启动期告警两层**：

1. **编译期**：`ProxyOptions.access` 必填 → 「忘了注入 `access`」在直构 core 时根本编译不过。
2. **启动期告警**：库调用方**显式注入了** `services.access`（这**是**正当用法，端口的意义就是换实现）时，配置驱动的那份名单判定**根本没被解析** → `acl.json` 写的名单全部不生效。运维视角是「我配了名单怎么没生效」，故启动期一条 **`acl-inert`**（文案常量 `core/log-events.ts:ACL_INERT_DETAIL`，判据 = `hasConfiguredAcl`（读**文件事实**）∧ `isAccessOverridden`，产出点 `runtime.ts:reportAclGate`，与 `quota-inert` 同一轮报告、**只报一次**）。**判据与取舍见 `src/runtime/AGENTS.md`**，落盘行见 `src/server/AGENTS.md`。

**真正的默认实现只在唯一组装根解析**：`createProxyRuntime` → `runtime/services.ts:buildDefaultServices`（`identity` / `access` / `traffic` / `trafficLedger` 四项）与 `createConnectorSource`（连接器）。runtime 解析一次并**显式注入**，故 core 侧那两个缺省档**永不生效**——它们只服务**直构 core** 的低层调用方。护栏：`tests/integration/custom-services-wiring.test.ts`（真 runtime + 真请求 + 真事件，断言替身**真的被调用**而不是「原样透传就当生效了」）、`tests/integration/acl-inert-warning.test.ts`（`acl-inert` 三档真 runtime 断言 + CLI 落盘行）、`tests/integration/traffic-quota.test.ts`、`tests/unit/proxy-runtime.test.ts`。

### `ConnectorSource`：装配期一次，记忆化正确性挂在 startup 相位上

`ConnectorSource` = `{ direct(); upstream() }`（`direct` 是**同一张表的一行、不是特例分支**）。**每请求查表在本仓不存在**：两个入口都只读装配期定死的登记表，登记表本身是 startup 相位的解析结果。给「每请求查表」再配一份 `WeakMap` 缓存只会制造第二真相源（协议键本来就不随 store 热改变变）。

- **`UPSTREAM_PROTOCOL` 是 startup 相位 → 连接器在装配期解析**：每请求重读它有两个问题——① 白读（startup 键构造后不再变）；② 与「startup 键不随 store 热改变变」正面冲突，那会让读代码的人误以为它可热改。
- ⚠️ **记忆化的正确性挂在「`UPSTREAM_PROTOCOL` 是 startup 相位」这条不变式上**。一个 source 只问一次表、只认第一次看到的协议。**哪天它被重分类成 runtime 相位（热改即时生效），这份记忆立刻变成第二真相源**——改完配置不重启，source 仍握着旧协议的连接器，且没有任何报错。那时必须**删掉记忆**（每次问表），**不是加失效钩子**：一个能被热改的键就该每次现读。改 `FIELDS` 里 `UPSTREAM_PROTOCOL` 的 phase 前**必须**先读 `forward/upstream/connector/registry.ts` 模块头那一段。
- **fail-closed 的抛点保留在请求期**（`upstream()` 第一次被调），**不在装配期**。理由三条各自成立：① 护栏 `tests/integration/upstream-protocol-fail-closed.test.ts` 从**库路径**注入 `"ftp"`（`ConfigStore` 零校验，故该分支可达），断言的是**请求期**表现为 `forward.error` + **源站零字节**；抛点前移会让那条 `forward.error` 事实消失、改成启动期异常——**那是换掉一个安全属性，不是加固它**（一条都没发出去的代理比一条 `forward.error` 更难定位是哪个请求撞上了）。② `proxyMode: "server"` 下有效路由恒 direct、`upstream()` 一次都不会被调，装配期就为它抛等于让「上游字段填错」打挂一个压根不上游的服务。③ 想要「启动就报错」，正确位置是**配置校验层**（CLI 路径的 `FIELDS.parseEnum` 已 fail-fast），而 `createConnectorSource` 拿不到 `configDir`、也不该知道「这是一个 runtime 的装配根」。
- `??=` 右侧抛错时**不赋值**：非法协议每次都重新查、每次都抛，绝不会出现「第一次抛、第二次悄悄给一个直连」那样的旁路。

**端口形状是裁决，不是实现细节**：
- `consume(user, dir, bytes)` **必须同步**。无锁的全部论证就是「一次 `consume` 从读到写没有 `await` 点，Node 单线程事件循环不可能在中间插入另一个 `consume`」。**若哪天把它改成 `async`（例如为了顺便把账本落盘），这条论证当场失效**，必须先补互斥。护栏：`tests/unit/traffic-account.test.ts` 的「consume 的同步性」**五条**（`consume` 返回的不是 Promise + 源码级 `零 async/零 await` + 连续调用的累计值单调精确 + **「零定时器/零微任务」** + **「挂了落盘账本之后仍是同步的、返回值仍不是 Promise、且落盘接线就写在 consume 路径上」**）。后两条是给这条论证**加的约束**：窗口滚动的正确实现是「每次访问槽位时比对窗口键」，而「起个 `setInterval` 到点清账」这个直觉做法同时破坏两件事——① 引入让出点 → 无锁论证失效；② 让进程多一个要 `unref`/要摘的后台任务；落盘则只许在 `consume` 的**同步区间内**做一次数组 push（`sink?.record(...)`），IO 全在账本侧。护栏把「零定时器」钉成源码级事实，且额外钉住「**全切片唯一的定时器站点是 `flush-loop.ts` 那一处 `setTimeout`**」（`ledger.ts`/`memory.ts` 零定时器）——定时器散进账本 IO 时那条断言就写不出来了。
- **超限必须在本次就返回 `allow:false`**，绝不允许「先放行、下次再说」。端口刻意**不**提供「先查后加」的两段式 API：两段式在并发下必然留窗口。
- 判定顺序 `bytesUp` → `bytesDown` → `bytesTotal`，**任一突破即拒**。推论是「配额耗尽 = **账号级封禁**」：撞了 `bytesUp` 之后该用户的 `down` 方向同样被拒（否则可以上传撞顶后改走下载继续白嫖）。代价是硬切后该账号在**当前窗口内**彻底不可用（跨过窗口边界自动恢复，见「窗口化」）。
- **恰好等于上限放行**（`<=` 语义，判据是「累计 **>** 上限才拒」）。`bytesTotal: 100` 允许用满 100 字节：配额是**上限**而不是「额度 + 1 的坑」，写成 1GiB 的运维最难受的就是「差一个字节传不完」。
- `usage` 与 `limit` **恒取同一 scope 的两个数**（`total` 被突破时 `usage` 是总量），消费方才算得出「超了多少」。
- `dir` 与 `scope` **可以不同**（本次流动 `down`、被突破的是 `up`）：方向由挂点如实上报，**绝不从 `scope` 反推**（撞 `total` 时两个方向都可能，反推有一半是假的，而 `dir` 是事件载荷必填项——假的比没有更糟）。故 `QuotaExceededHandler` 收 `(dir, verdict)` 两个参数。
- **未配 / 全 0 / 用户不存在 → 恒 allow**（**显式分支**，不是「默认上限 0 恰好放行」）。但**未配也照常累加 usage**：「没有上限」≠「不计量」，这样 `usage` 恒为真用量，将来加上限即刻按真账判定。唯一「不计量」的情形是**没有身份**。
- 已知限制（写在文件头免得被当成没想过）：账本是**纯内存无淘汰**的 `Map`。`users.json` 固定规模时天然有界，但 `authType=jwt` 的 `sub` 理论上可无限增长。**落盘压缩解决了这条限制的「持久」那一半，进程内那一半仍未解决**：
  - **已解决**：落盘账本在**压缩**时按 `(用户, 窗口键)` 求和并**丢弃已过期窗口的条目**（`ledger.ts:compactEntries`），所以「28 个 `sub` 跨 28 天」在压缩后文件行数降到 0，重启恢复时这些过期槽位**根本不会回到内存**。也就是**磁盘上那一份（唯一会无界增长的那一份）现在是有界的**（阈值 8MiB）。
  - **未解决**：**同一个长跑进程内**的内存 `Map` 仍不淘汰（本文件零 `.delete(` 仍是护栏）。彻底解决需要重启一次进程 —— 这是自觉的取舍：进程内淘汰必须先定义「被淘汰的用户拿到一份清零的账 = 凭空多出一份额度」的语义，而那属于配额窗口的设计。
  **「处理窗口由落盘压缩承担」这条已落地**（护栏断言原文见 `tests/unit/traffic-window.test.ts`：文件头必须含 `jwt` 与 `5b-2` 两个词——文档也是契约的一部分）。
- **刻意不加** LRU 之类猜测性淘汰：淘汰策略必须与配额窗口一起设计，否则会出现「配额还没过期、账本先被淘汰」这种更糟的行为（被淘汰的用户拿到一份清零的账 = 凭空多出一份额度）。护栏把这条决策钉成源码级事实：`tests/unit/traffic-window.test.ts` 断言 `memory.ts` **零 `.delete(`、零 LRU/容量上限字样**；`tests/unit/traffic-ledger.test.ts` 把同一条负向断言**扩展到 `ledger.ts`/`flush-loop.ts`**（账本里也不许有 LRU）——谁想加淘汰，必须先改那条护栏并说明淘汰语义。

**窗口化：每用户槽位带 `windowKey`，滚动即清账**

槽位是 `{windowKey, up, down}`，并在**每次访问槽位时**（`consume` 与 `usage` 共用私有 `slotFor`）比对当前窗口键——**不同即用量清零并换键**。三条不变量：
- **惰性滚动，零定时器**：不引入任何 `setTimeout`/`setInterval`/`setImmediate`/`nextTick`/`queueMicrotask`。理由有两条，各自独立成立：① 定时器必然引入让出点 → **当场作废上面那条无锁论证**；② 账本是纯内存的，而 `consume` 是同步函数，「到点就清」在同步函数里只能靠后台任务，于是凭空多出一个要 `unref`、要摘、要处理停机的对象。真实需求只是「**跨过边界后别拿旧账当新账**」，而这在每次访问槽位时判一次就完备——没人访问的槽位清不清账**语义上不可观测**（`usage` 一读就现算）。护栏：上面「consume 的同步性」第四/第五条（源码级零定时器，且**全切片的唯一定时器站点是 `flush-loop.ts` 那一处**——落盘定时器在账本侧，不在滚动侧）。
- **已用量绝不跨窗口继承**（裁决）：继承等于白送「等窗口翻页」的重叠额度——卡在边界前用满的用户，等窗口一翻又能用满一份，配额立刻失去意义。故跨窗一律清零，**上一窗口的耗尽状态也随新窗口解除**（新窗口给完整额度）。**已用变异测试验证**：把清零改成「继承旧值」→ `traffic-window.test.ts` 8 条红。
- **清账 ≠ 除名**：跨窗只**替换**槽位，**从不删除**。删了就等于「清账」变成「除名」，而且「反复读一个未知用户」会变成无限增长。对称的一条：`usage` 对**从未计量过**的用户直接返回零值、**不建槽**（读一次不该凭空长出槽位）。

**落盘账本：`ledger.ts` + `flush-loop.ts`，两条铁律各自独立成立**

**铁律一：`consume` 仍同步，落盘完全异步。** 内存账本通过 `bindSink(sink)` 挂上 `JsonlTrafficLedger` 后，`consume` 只多一行 `this.sink?.record(user, dir, bytes, now)` —— **纯数组 push**（`TrafficSink.record` 是同步端口，无 Promise/无 IO）。真正的写盘在账本自己的后台 flush 里。三条性质因此全部保持：① `consume` 仍是**同步函数**（上面那条无锁论证分毫未动）；② `consume` 的**耗时与磁盘无关**（磁盘满/目录不可写都不影响判定与放行）；③ `consume` **绝不因账本失败而抛错**。`consume` 里**时刻只取一次**（`const now = this.clock()`）并同时喂给 `slotFor` 与 `record` —— 窗口键与落盘 `ts` 必须同源，否则同一批字节会被判定分到窗口 A、却按窗口 B 落盘（重启恢复后用量就错了）。

**铁律二：`src/core/**` 与 `src/runtime/**` 一律不许读 `process.env`，槽位是显式参数。** 传递链是 `cli.ts` 的 env 快照 → `runServer(context, { trafficWorkerSlot })` → `ProxyServer.trafficWorkerSlot` → `createProxyRuntime({ trafficWorkerSlot })` → `runtime/services.ts:buildDefaultServices` → `JsonlTrafficLedger`。理由与其它配置端口同源，但在这里**更硬**：槽位**会被拼进账本文件名**，一次「猜来源」就是一次「写错文件 / 读别人的账」。env 名 `PROXY_WORKER_SLOT` 的**唯一写入方**是 `server/cluster.ts` 的 fork（`core → server` 是被禁方向，所以这一环天然在 core 之外），且它**刻意不进 `FIELDS`**（它不是配置项，见 `src/config/AGENTS.md`）。护栏：`tests/unit/traffic-ledger.test.ts` 的「core/** 与 runtime/** 零 process.env」**逐文件扫全文**。

**槽位必须是稳定序号，不能用 PID**：每次重启换文件名的话，旧文件再无人问津，「持久化」等于「每次都从零开始」——那比不落盘更坏，因为运维会以为配了持久化。cluster 派发 `1..N`，进程退出时释放（重启复用同一个号，账本接得上）；单进程/库模式恒为 `"0"`。`normalizeSlot` 只认 `1..9999` 纯数字，其余（含 `../../evil`）一律按**路径穿越面**拒绝、回落 `"0"`。

**已否决的四个方向（文档里出现即为错，除非同时改掉对应的负向护栏）**：
- **禁限速 / 速率整形**：只能到 chunk 粒度（TLS record ~16KB），低限速值要靠延迟换平滑；且整形必然要 `pause()`/`resume()`，会与 `guardDialing` 的半关闭联动形成第三层流控。护栏：`tests/unit/user-quota.test.ts` 显式断言 `rateBps`/`rate` 被判非法、`tests/unit/traffic-ledger.test.ts` 断言源码零速率字段。
- **禁每用户最大并发连接数**：那是「连接数配额」不是「流量配额」，与窗口/字节两条轴都正交；真要做必须先定义「并发数按哪个窗口重置」。护栏同上（`maxConnections`/`concurrency` 被判非法）。
- **禁滚动时间窗**：理由（解释成本 / 聚合成本 / 不预留占位值）写在「窗口化」小节与 `window.ts` 文件头。护栏：`tests/unit/user-quota.test.ts` 断言 `week`/`hour`/`rolling` 整组非法。
- **禁跨 worker 共享账本**：每个 worker 写自己那份 `worker-<slot>.jsonl`，**没有**中心聚合、没有文件锁、没有 IPC 汇总。代价是「同一用户被分到两个 worker 时额度各算各的」——`cluster.fork()` 的负载分配不保证粘性，理论上可被绕开一点额度；接受它换来的是「账本 IO 完全不跨进程协调」这个简单得多的模型。真要共享必须先引入跨进程互斥，那与「`consume` 同步无锁」那条论证直接冲突。护栏：`tests/unit/traffic-ledger.test.ts` 的 slot 隔离档（两个 slot 写两个文件、互不污染）。

**格式：`<quotaLedgerDir>/worker-<slot>.jsonl`，一行一条 delta `{ ts, u, d, b }`，只写增量绝不写绝对值。** 绝对值一律在**读取时按 `(用户, 窗口键)` 求和**——写绝对值等于让「谁最后写」成为唯一真相（两次 flush 交错就互相覆盖，且崩溃后残留的绝对值无法与已追加的增量对账）。坏行**跳过而不是抛错**：一行脏数据让整本账打不开 = 配额整体失效，跳过只丢那一行的额度。

**两个压缩安全点**（Windows 上 `EPERM` 的经典来源：不允许 rename 覆盖一个仍打开的文件）。压缩流程被钉死为 `flush → close 句柄 → 读全量求和 → 写 .tmp → fs.rename → 重开句柄`，触发点是 ① **启动时**（`open()` 里读完立刻压，此时**还没有句柄**）② **运行期按文件大小阈值**（默认 8MiB，在同一轮 flush 内做完）。全程无并发压缩：Node 单线程 + `flush()` 走一条 **Promise 链**串行化。**「关句柄」这条不是洁癖**：Windows 上 `rename` 覆盖一个**仍打开**的文件必然 `EPERM`，所以压缩流程里那句「close 句柄」是承重的。压缩后若再开一个 append 句柄又忘了关，后续任何 `rename` 覆盖本文件都会失败，表现是「压缩静默不生效、文件一字不变」——`compact(reopen: boolean)` 的参数就是为「压缩后要不要重开句柄」留的。

**压缩是幂等的**，做法是**保留幸存条目里的最大 `ts`**（不是压缩时刻）：`ts` 必须落在该窗口内，重压才算出同一个键 → 两次压缩逐字节相同。若写成「压缩时刻」，两次压缩间隔只要跨过窗口边界就产出不同内容，幂等那条护栏也就测不出东西了。**`compactedAt` 门槛**保证「已经压不动的账本」不被反复全量重写（判据用 `rename` 次数而不是文件内容——幂等压缩产出同样的字节，看内容区分不出）。

**崩溃安全 = `.tmp` + `rename`**：崩溃点只有两种（`.tmp` 写了一半 → rename 未发生 → 原文件完好；rename 已完成 → `.tmp` 已消失），中间不存在「原文件被截断成半个」的态。本模块**从不读** `.tmp`（所以残留的临时文件**不可能污染原文件**），启动时顺手 best-effort 删掉它。

**压缩丢弃已过期窗口的条目**（`compactEntries`）与**恢复只认当前窗口**（`summarizeCurrent`）**必须用同一条判据**（同一个 `windowKey` 比较），否则会出现「恢复算进来的量比压缩保留的量多」。两条刻意不合并成一份带副作用的函数：一条产出恢复结果、一条产出可写回文件的条目，但对「什么算过期」必须有同一个定义。

**写盘失败韧性**（`EACCES`/`ENOSPC`/…）的正确形态只有一种：**内存计数继续 + 未落盘 delta 累积留待下次重试 + 一条可见事实**。整批 delta 放回队首（`concat` 而非 `unshift(...batch)`，大批次上展开调用会打爆调用栈），事件是公共的 **`traffic.ledger-error`**（`{ path, error }`，与 `config.file-error` 同形：同一类事实），CLI 落一条 `[quota-ledger-error]` **error** 级日志。**「直接失败」与「静默重试」都更坏**：前者等于「磁盘满 → 代理全挂」（配额是增强功能，不该有能力打垮数据面），后者让运维以为配额持久化了、几天后重启才发现用量全丢（比不落盘更坏，因为那是**被误导**的降级）。日志文案里必须写明「**不要为此重启**」——重启会把队列里未落盘的增量一起丢掉。**重试可能重复计一次账**，这是刻意选的**安全方向**：多算 = 少用一点额度（等下个窗口即可），少算 = 白拿额度。压缩会把重复行求和收敛回正确值。

**零成本档**：`enabled()`（= 注入的 `hasConfiguredQuota`：**没有任何用户配了非全 0 的 `quota`**）为 false 时 `open()` 在 **`mkdir` 之前**立刻返回 —— **不建目录、不开句柄、不起定时器、不注册任何 fs 事件**，`record()` 也全程 no-op（否则「没配配额」反而吃内存）。判据是**文件事实**而不是配置猜测，且与 `runtime.start()` 里 `quota-inert` 告警**共用同一个函数**（两处各写一份，迟早出现「告警说没配、账本说配了」）。护栏断言的是**「目录不存在」**（不是「建了但空」）——那才是可观测的硬证据。

**端口为什么拆成 `TrafficSink` 与 `TrafficLedgerController` 两个**：两个调用方、两种失败代价。`record` 由 `consume` 在**同步区间内**调用（每 chunk 一次），抛错就等于把「写盘失败」变成「转发失败」，所以必须是最小同步面；`open`/`close` 只在 `runtime.start/stop` 各调一次，**允许 Promise**。合在一个接口上最容易顺手让 `record` 也返回 Promise——那正是**明确禁止**的方向。同理 `seed(restored)` / `bindSink(sink)` 刻意**不进 `TrafficAccount` 端口**（同 `size` 的理由：端口是「用量与判定」的契约，落盘位置与规模诊断是装配决策）。

**窗口键夹取**：`clampShiftHours` 把 `shiftHours` 夹到 `[0,23]`，非有限值夹 0。`quotaResetHour` 在配置层已被 FIELDS 校验，但**库调用方可以绕过 `loadConfig`**（`createProxyRuntime({ config })` 走 `ConfigStore`，而 `ConfigStore` **零校验**），所以「配置层保证 0..23」对库路径**不成立**。不夹取的代价是具体的：畸形键会进恢复结果的 `windowKey` 并参与判定。夹到定义域的后果只是「按最近的一个合法边界算窗口」——位置错了但形状仍是合法键，账本里看到的是 `2026-03-15` 而不是一眼就知道坏掉的 `NaN-NaN-NaN`。`flush-loop.ts` 的间隔下限夹 1 同理（0/负数会变成 `setTimeout(fn, 0)` 的忙循环 = 纯 CPU 挂死）。

**事件**：新增公共契约 **`traffic.ledger-error`**（`AppEventMap`），载荷 `{ path, error }`（`path` 是账本文件，`error` 是原始异常，消费方据此区分 `EACCES` 与 `ENOSPC`）。生产点是 `JsonlTrafficLedger.report`（经 `runtime/services.ts` 注入的 `onLedgerError` 闭包）→ `runtime.ts` 只 `publish`，**不落日志**。⚠️ **两件必须分开的事**：① **`onLedgerError` 这个桥接闭包不落日志**——落盘那一跳是 `src/runtime/event-log.ts:bindProxyEventLogs` 的职责（由 `createProxyRuntime` 在 `start()` 的 `activateSubscriptions` 里装配、缺省开启、`eventLogs: false` 可关）；② **库调用方同样拿得到这一行 error**——走 `createProxyRuntime()` 就已订阅到那份绑定。判据是本仓自己的分界线「谁声明拥有这个进程」：落盘**不拥有进程**（零 `process` 触点，纯 `hub.subscribe` + `logger.*` 注入），所以它归 runtime 层的 `event-log.ts`（正文见 `src/runtime/AGENTS.md`「事件 → 落盘绑定」一节）。

**窗口键语义**（`traffic/window.ts` 是第一手说明）：
- `QuotaWindow` 只有 `day` / `month` 两个**日历窗**字面量，缺省 `month`（`DEFAULT_QUOTA_WINDOW`，由 `quotaWindow()` 归一——**归一在消费侧不在配置侧**，理由见 `src/config/AGENTS.md`）。磁盘上写其它值（`"week"`/`"hour"`/`"rolling"`/大小写变体/非字符串）由 `config/files/users.ts` 判**整组非法 → 启动期 abort**；**为什么不做滚动窗**（解释成本、聚合成本、不预留占位值）写在 `window.ts` 文件头。
- `windowKey(nowMs, window, shiftHours)`：先**减 `shiftHours` 小时再取本地日历字段**。故 `resetHour=3` 时当天 `01:00` 仍属**前一天**窗口、`03:00` 才是新窗口第一刻。`day` → `YYYY-MM-DD`，`month` → `YYYY-MM`（本地时区字段，**不是 `toISOString()`** —— 配额是运维所在时区的日历概念）。
- **「减毫秒再读字段」而不是手工日历进位**：闰年/月末/跨年的进位是这类代码的事故源，交给 `Date` 的本地字段就没有特例可漏。
- **DST 边界是近似（刻意接受并记录）**：夏令时让某一小时在本地重复或消失，窗口切换点因此最多偏移 1 小时。为「每天早上大致清零」引入一整条时区规则链不值得。护栏按这个取舍断言而非按「精确午夜」断言：逐小时走 48 小时（必覆盖任何一次切换），切换点必落在本地午夜 ±1h 内。
- `now` **必须可注入**（`TrafficWindowSource.now?`，缺省墙钟）：窗口边界是最容易写错的地方，靠真实时钟只能写出「今天大概对」这种测不出回归的用例。生产路径**不需要**注入它（账本只用它算键，滚动是惰性的），故做成可选。`shiftHours` 的 `0..23` **在本层夹取**（`clampShiftHours`）——理由见上面「窗口键夹取」一节：库路径的 `ConfigStore` 零校验，配置层那条前置条件对库调用方**不成立**，而畸形键会一路进落盘账本并参与恢复判定。

**计量落点是唯一正确的那个**（`meter.ts` 文件头是完整的第一手说明，这里只列结论）：
- **被动计数**：在**源流**上挂一个 `data` 监听器，只读 `chunk.length`。**不插 Transform、不改 pipe 结构、不用 pause/resume 整形**。理由：插 Transform 就得配背压，背压必然要 `pause()`/`resume()`，会立刻改变 `guardDialing` 半关闭联动的时序，把一条已验证的收尾语义变成要重新验证的东西。护栏：源码级断言 `meter.ts` 零 `Transform`/`pause(`/`resume(`/`push(`/`pipe(`，且 `on("data")` **恰好一处**。
- 三个挂点（`base.ts:ForwarderBase`）：`openTunnelMeter`（隧道/SOCKS/WebSocket 复用，`up` 挂客户端流、`down` 挂上游流）+ `openHttpQuotaGate` + 两处 `meterStream`（HTTP：`up` 挂 **`req`**、`down` 挂 **`upRes``）。**HTTP 的 `up` 绝不能挂 `req.socket`**：入站 socket 被 keep-alive 的多个请求共享，在它上面计数就是账本串号（变异测试验证：改挂 `req.socket` → 3 条红）。
- **建链协议字节天然不计入**：`CONNECT` 请求行/请求头被 Node 的 HTTP 解析器摘走（我们是在解析器摘完之后才挂监听器）、`200`/`101` 应答由**我们** `write()` 出去（出站不产生本流 `data` 事件）、SOCKS 握手由 `SocksHandshakeReader` 逐段读走并在 `detach()` 里 pause。
- **首批载荷要计入**（`head` / `rest` / SOCKS 流水线余量）：它们不经 `data` 事件，由 `bridgeWithBuffered` / `upgradeOver` 经 `meter.charge(dir, n)` 显式补记；判定不通过就**不写**（写进已销毁的 socket 会抛 `ERR_STREAM_DESTROYED`）。护栏：CONNECT 请求头与载荷**同一次写**（载荷进 `head`）那条用例——变异测试验证：临时去掉 `head` 补记 → 该条立刻变红。

**已知不对称（诚实记录，不假装两侧对称）**：
- **隧道 / SOCKS / WebSocket 走裸 socket**：客户端首包与响应余量都经过 socket，加上 `data` 计数与首批补记，**两个方向都精确**（实测 4096B 载荷 → `usage = {up:4096, down:4096}` 逐字节相等）。
- **HTTP 普通转发**：`IncomingMessage` 流**只覆盖消息体**——请求行+请求头、状态行+响应头都是 Node 直接写进 socket 的，不经过请求/响应对象。故 HTTP 路径**两个方向各少算一个 HTTP 头**：`up` 少算请求行+请求头（实测典型 GET/POST 约 90–200B），`down` 少算状态行+响应头（实测典型 200 约 60–150B）。**不要为了「补齐」去在 core 里合成 Node 已经写出去的字节**——那就不是被动计量了。护栏按「显式说明的误差」断言：HTTP 路径断言的是**消息体字节数逐字节相等**，头字节的差额写在本文件与 `meter.ts` 里。

**耗尽语义（裁决，不许软化）**：**硬切**。不给「用尽后只拒新请求、已有连接放着」——一条长连接隧道能永远不触发耗尽判定，配额就成了摆设。
- **HTTP 转发**：`res.headersSent` 为假 → 回 **507 Insufficient Storage**（`@/utils/constants` 的 `STATUS_INSUFFICIENT_STORAGE`/`REASON_INSUFFICIENT_STORAGE`；**不是 403**——配额耗尽不是权限问题，403 会诱导客户端换凭证/换身份重试，而重试对「用完了」毫无意义）；已发出 → `destroy()`。**`down` 方向实际总是走 destroy 分支**（响应体只在 `writeHead` 之后流动，那时 `headersSent` 必为 true），**507 分支由 `up` 方向承载**（请求体撞顶时响应还没开始）——两条分支都要有。
- **隧道 / SOCKS / WebSocket**：应答早已发出（`200` / SOCKS reply / `101`），**改不了** → 双端 `destroy()`。
- **「恰好一次」由闭锁保证**（`openTunnelMeter` / `openHttpQuotaGate` 各自的 `fired` 标志）。HTTP 两个方向**共用同一个闭锁**：否则 `up` 撞顶恰好与 `down` 首个 chunk 落在同一轮事件循环时会发两条。socket 被 destroy 后本不会再有事件，但闭锁让这件事**不依赖时序**。
- **状态行不保证到达客户端**：`res.destroy()` 直接销毁 socket，尚在写缓冲里的应答头会一起丢掉，客户端可能看到 200、也可能只看到 ECONNRESET。两者都是「硬切」的正确表现。**不要**为了「让状态行一定送到」改成 `setImmediate` 延迟 destroy——那会在延迟窗口里漏掉本该被拒的字节，硬切就不硬了。

**无鉴权 → 配额整体不生效**（产品决策）：没有身份就没有归属，故 `meterStream` 在 `user === undefined` 时**一个监听器都不挂**（关鉴权的部署零开销），启动时若账号表里真有非全 0 的配额则打一条 `[quota-inert]` warn（文案 `core/log-events.ts:QUOTA_INERT_DETAIL`，**判据是文件事实而非配置猜测**——关鉴权本身是常态，没配配额时告警纯属噪音）。护栏那条断言「`consume` 一次都不许被调」而不是「usage 恒零」：后者区分不出「没调」与「调了但查不到配额」。

**服务装配**：`ProxyOptions.traffic?: TrafficAccount` **可注入**、缺省 = **显式禁用档**（`inertTrafficAccount()`，与本文件既有的 `identity ?? NONE_IDENTITY`（即 `noneIdentity()`）先例**完全同构**，归一只发生在 `BaseProxy` 构造期**一处**）。**真正的默认实现（读 users.json 的内存账本）只在唯一组装根 `createProxyRuntime` 解析**（`runtime/services.ts:buildDefaultServices`），并经 `services.traffic` 落到 `ProxyOptions.traffic`——所以库调用方注入的替身一定原样生效。**窗口口径也只在那里注入**：`TrafficWindowSource.resetHour` 是经同一 accessor 的**闭包**（每次访问现读 `quotaResetHour`，故热改立即生效）、`now` 不注入（账本只用它算窗口键且滚动是惰性的，缺省墙钟）。**落盘副本也只在那里注入，且与默认内存账本同生共死**：调用方**显式注入** `services.traffic` 时 `services.trafficLedger` 恒为 `undefined`（那一本账归调用方管，我们不写它的文件、不给它起定时器）。**账本本身零配置依赖**：它不读 `ConfigAccessor`、不读 `process.env`，目录/间隔/窗口/「有没有配额」全部由装配点以闭包注入（`slot` 是显式的**字符串**）——与「core 零配置依赖」同一条纪律。**四个转发器必须共享同一个账本实例**（各建各的等于没配配额），故它们构造时都收 `ctx` + `services`（`CoreServices`，`traffic` 是其中一项）+ `connectors` 三个**必填**参数，由 `HttpProxy` 构造函数 / `SocksProxyBase` 字段初始化器从 `this.services` 传入（`forwarder-request-path-allocation.test.ts` 的「恰好 4 个构造点」静态计数不受影响）。

**身份铁律同样适用**：`traffic` 是**进程级**服务、可以存字段；`user` **绝不**——它逐请求产生，只在 `openTunnelMeter` / `openHttpQuotaGate` 的闭包里活一次。

**事件**：新增公共契约 **`traffic.quota-exceeded`**（`AppEventMap`），载荷 `{ user, dir, scope, usage, limit }`（`user` **必填**：无身份即不计量，这条事件不可能出现在无鉴权部署上；写成可选就等于允许消费方回答「配额是谁的」这个答不出来的问题）。生产点唯一：`base.ts:ForwarderBase.publishQuotaExceeded`，**直接发公共事件而不走 `pipe`**——刻意**不**给 `PipeEvent` 判别联合加第 15 个变体（那会让 14 变体的穷尽清单与两处既有测试同时要改，而这条事实本来就不需要「管道上下文」）。`EventContext` 恒带 `user`，其余关联维度取自 `scope.terminal.snapshotContext()`（协议入口已算好的同一份事实，重算会出现「同一请求两个 id 口径」）。落盘 `[quota-exceeded]` warn 行在 `src/runtime/event-log.ts:bindProxyEventLogs`（与 `[target-denied]` 同一面），文案「`<user> 配额耗尽 dir=<up|down> scope=<up|down|total> usage=<n> limit=<n>`」。**第二个公共事件 `traffic.ledger-error`**（`{ path, error }`）与它的落盘面见上面「落盘账本」一节。

## 依赖承载体（`context.ts`）

- `CoreContext` = 三件套的只读接口（`config: ConfigAccessor` / `logger: Logger` / `events: EventHub`），三项**全必填、无可选标记**；全部 type-only 引 `@/config/index.js`、`@/utils/logger/index.js`、`@/core/events/index.js`，编译期擦除、零运行期依赖边。**本文件刻意零兜底**：不出现 `createNoopLogger()` / `new EventHub()` / 任何 `??`，依赖缺失的兜底只允许发生在唯一组装根 `createProxyRuntime()`——在承载体里兜底会把「忘注入」变成静默的运行期怪问题。
- `ContextualBase`（`constructor(protected readonly ctx: CoreContext)`）只把 `ctx` 投影成 `config` / `log` / `events` 三个 **protected getter**，零副作用：不订阅事件、不读配置、不打日志、不碰 `process`/文件。getter 名字是契约：子类要换名字就得写转发，那这套 getter 就白存在了。
- **依赖载体只有一个 `ctx`**：`ProxyOptions` 上是**单个必填 `ctx: CoreContext`**（配置 / 日志 / 事件总线一次性整体注入，core 内零缺省解析）。`ForwarderBase` / `Dialer` / **`BaseProxy`** 都 `extends ContextualBase`，零自有 `config` 字段与投影 getter（`this.config` / `this.log` / `this.events` 统一走继承 getter，13 处 `Dialer` 读取、全部 `ForwarderBase` 读取与 `BaseProxy` 内的调用点一字未改）；四个转发器（http/tunnel/upgrade/socks）的构造参数是 **`(ctx: CoreContext, services: CoreServices, connectors: ConnectorSource)` 三个必填**、**不收 `PipeEventSink`**（事件槽由 `RequestScope` 携带，见下方「构造签名」条），**入口只有实例方法**——`forwardHttp` / `forwardTunnel` / `forwardUpgrade` 三个函数式入口不存在（低层调用方直接构造转发器实例并调 `handleRequest` / `handleConnect` / `handleUpgrade` / `serveSocks4` / `serveSocks5Connect`，见「三个入口方法名互不相同」那张表）。`ProxyOptions.ctx` 与 `ContextualBase` 的 `this.ctx` 是**同一个对象**（`super(options.ctx)` 原样透传），语义零变化，且不存在「子类实例字段遮蔽继承 accessor」的隐患。构造顺序：TS 要求 `super()` 先执行，故 ctx 先落基类、再归一 `this.options`；`ContextualBase` 构造只做一次字段赋值（零副作用），构造期内没有任何代码读 `this.config`/`this.log`/`this.events`，不存在「读早于赋值」。
- **`BaseProxy` 另持有一个 `protected readonly identity` 别名**：与 `services.identity` **恒为同一对象**。之所以留这个别名（`sessionHost` 的产物是给 `socks-session.ts` 的最小接口，字段名 `identity` 比 `services.identity` 更贴近那份接口的语义），而转发器一律写 `this.services.identity`——两处并存是刻意的，不要「顺手统一」成一个。
- **`core/index.ts` 刻意不导出本文件**：core 现有惯例是按扁平路径直接引用（`@/core/identity.js`、`@/core/access-control.js`、`@/core/events/index.js`），`core/index.ts` 本就是选择性出口（连 `access-control`/`error-boundary`/`request-terminal` 都不在其中），库入口 `src/index.ts` 也不经它。不要为了导出而导出。

配置类需求**不要**放进 core：`config/files/acl.ts` 只管读名单，请求期判定归 `core/access-control.ts`，配置契约/来源/归一化归 `src/config/`。

## 类型（`types/`）

- `proxy.ts` 是 Single Source of Truth；`identity.ts` / `pipe.ts` 叶模块只做 `export type` 转发，禁止新增独立类型。
- **事件契约只有一份**：`AppEventMap`（`core/events/types.ts`），`types/` 下**零 EventEmitter 事件表**。`src/runtime/event-log.ts:FORWARD_ERROR_LABEL` 用 `ProxyForwardKind` 索引，`ProxyForwardKind` 本身**保留**（三条公共事件与该日志前缀表都在用）。`ProxyAuthEvent` 与 `PipeEventSink` **保留**（前者是 `IdentityContext.onAuthEvent` 的内部审计回调契约，后者是 `(e: PipeEvent) => void` 函数类型别名）。
- **`types/identity.ts` 是身份域叶模块**：只 `export type` 转发 `IdentityRequestLike` / `IdentityContext` / `IdentityResult` / `IdentityProvider` / `IdentityOptions` / `AuthAccount` / `ProxyAuthEvent`。`IdentityRequestLike` **超出端口六件套**也从这里出去——它是 `IdentityContext.req` 的形状，调用方要手搓一个 `IdentityContext` 做测试替身时必须能引到它，逼它去引总表 `@/core/types/proxy.js` 反而破坏本叶模块存在的意义。
- **三个端口的声明都在 `types/proxy.ts` 一处**：`IdentityProvider` / `AccessControl` / `CoreServices` 与 `AccessClientInput`/`AccessTargetInput`/`AccessRouteInput`/`AccessDecision`/`AccessRouteDecision`。**判定输入刻意收成只读入参对象而不是位置参数**：`checkTarget` 有三个事实（host + user + 将来的更多维度），位置参数在下一次加维度时必须改所有调用点，而入参对象加字段是纯增量。字段全 `readonly`。
- `proxy.ts` 对外**三条**出边：`import type { LogEvent } from "../log-events.js"`（9 个 pipe 判别键的权威，见下「管道事件判别联合」）、`import type { CoreContext } from "@/core/context.js"`（`ProxyOptions.ctx` 的类型落点）、`import type { ConnectorSource } from "@/core/forward/upstream/connector/index.js"`（`ProxyOptions.connectors` 的类型落点）。三条都是 `import type`，编译期擦除、零运行期依赖边。**无环性已核实**：`connector/types.ts` 只 import `node:stream` 与 `@/core/guard.js`，`guard.ts` 只 import `node:stream` / `@/utils/*`，全链不回头引本文件。⚠️ 但类型层存在一条**纯 type-only 的环**：`connector/registry.ts` 自身 type-only 引了本文件的 `ProxyProtocol`——两侧都被擦除，既不产生运行时边（esbuild bundle 内无环），TS 也能正常处理；**若将来要断言「本文件零入边」，必须记得 `registry.ts` 是那条边**。
- **`types/` 下只有三个文件**：`proxy.ts`（端口类型与判别联合的 SSOT）、`identity.ts`（身份域类型的转发出口）、`pipe.ts`（`PipeEvent` / `PipeEventSink` 的转发出口）。公共事件表 `AppEventMap` **不在这里**，住在 `core/events/types.ts`。**禁止新增第四个类型文件**——`IdentityOptions.extractor` 那类假扩展点同理：端口形状是裁决，不是给你加维度的口袋。

## 身份（`identity.ts` + `identity/`）

**目录形态**：`identity.ts`（层出口，**刻意不引 barrel**——本目录**没有** `index.ts`，出面只用相对路径逐个 re-export，避免自我引用 barrel 造成循环）+ `identity/token.ts`（`TokenIdentityBase` 抽象骨架）+ `identity/modes.ts`（四个模式插件工厂）+ `identity/file-account.ts`（`FileAccountIdentity`）+ `identity/factory.ts`（`createIdentity` / `createIdentityFromConfig` / `defaultJwtVerify`）。

- **为什么值得拆四个文件**：四种模式的差异**只在「拿到 token 之后怎么比对」这一步**（账号表精确比对 / 仅比用户名 / 异步验签 / 恒放行），而「取凭证 + 脱敏 + 审计发事件 + 结果判定」是完全同形的一份。拆开后：① 库调用方能**单独构造其中一种语义**（`noneIdentity()` / `basicIdentity()` / `uidIdentity()` / `jwtIdentity()`）——这是可插值身份的真实价值；② 那份同形的骨架收进 `TokenIdentityBase`，**不许**把它也拆成四份拷贝（scheme 大小写不敏感、隧道 tag 判据、失败必发审计这三条不变量经不起任何一处漂移）。**`TokenIdentityBase` 刻意一并导出**——它是自研身份插件的**唯一复用入口**，不导出会逼调用方把「取凭证 + 脱敏 + 审计发事件」重新抄一遍，而那正是上面那条「不许拆成四份拷贝」的理由。
- 账号住在 `AUTH_USERS_FILE`（`cfg/users.json`），**不在** env。`createIdentityFromConfig(ctx, onFileEvent?)` 收**整个 `CoreContext`**（配置 / 日志 / 事件总线三件套），不是 `ConfigAccessor`——`isOwnCredential` 跑在**出站头剥离热路径**上，逐方法传参等于把 DI 成本摊到最热的路径。文件观察面（发公共事件那一半）**仍由唯一组装点注入**。它每次 `identify()` **与每次 `isOwnCredential()`** 都现读 `ctx.config` 的 `authEnabled`/`authType`/`jwtSecret`/`authLogging` 与账号文件（热加载），改 runtime 配置下次请求即生效；两条路径**共用同一个 live 构造闭包**，不存在「鉴权读到新值、剥离读到旧值」的口径分裂。⚠️ **「现读」指的是现读那六个输入，不是「每次判定都 new 一个实例」**：`factory.ts` 的 `liveSnapshots` 记忆表（按 `ConfigAccessor` 隔离、判据是**输入的身份**而非时间、零定时器 / 零 TTL / 零轮询）让输入逐项未变时复用上一份快照，而**判定本身每次都照跑**。热路径成本的大头是 `loadAuthUsers`（`readJsonCached` 编排），**不是**快照构造——数字与归因见「三个可插值端口」第一条的「代价如实写」。
- `createIdentity(opts: IdentityOptions, config: ConfigAccessor)` 是**低层直构**入口（不收 ctx，供自研实现复用骨架）。
- `basic` 命中任一账号的用户名+密码；`uid` 只比用户名；`jwt` 用户名取 token 的 `sub/username/user/uid/id`。凭证索引住在 `helpers/credentials.ts`（`buildCredentialIndexes` / `credentialIndexesFor` 单槽记忆 / `matchBasicCredential` / `matchUidCredential`），身份层只做薄委托，保证出站头剥离与鉴权用同一判据，结果带回 `username` 供逐连接日志。
- 失败闭环：账号形状非法 abort 启动（`validateAuthUsers`）；`authEnabled + basic|uid + 空表` abort（`assertAuthConfig`，见 `src/config/AGENTS.md`）；`identify()` 内异常一律 deny（`BaseProxy.authorize()` 捕获）。
- Token：`Proxy-Authorization` 优先、`Authorization` 回退（RFC 7235，scheme 大小写不敏感）。
- **凭证防泄漏的判据由 `IdentityProvider.isOwnCredential` 独占**（见上方「三个可插值端口」）：`sanitizeHeaders` / Upgrade 报文的出站凭证剥离**转交插件**（`proxy-` 前缀仍走 `isProxyHeaderName` 那条协议规则，其余**每个**出站头名 × 每个值都问插件，见上方裁决第一条），`helpers/headers.ts` 零 `@/config/index.js` 导入、零 users.json 读取。basic/uid 走**整份账号表**比对；**jwt 也参与出站剥离**——剥 scheme 前缀后按 `isJwtShape` + `verifyHs256Jwt`（内置 HS256 + `JWT_SECRET`）验签判定，不依赖账号表（jwt 允许空表，该分支必须先于空表早退）。已知边界：自定义注入的 `jwtVerify` 不被剥离判据感知（只认内置 HS256；生产默认注入内置校验器），方向仍是「宁可多剥不泄漏」。
- JWT：默认注入内置 HS256 校验 `defaultJwtVerify`（薄 async 包装 `proxy-helpers:verifyHs256Jwt`，`node:crypto` 零依赖：验签 + `exp`，永不抛，与出站剥离共用同一实现）；显式注入优先；`jwtIdentity()` 要求显式注入（未注入一律拒绝），`FileAccountIdentity` 直构时 type=jwt 同样必填（未注入一律拒绝，审计照打），`createIdentityFromConfig()` 默认注入内置校验器。
- **`kind` 是稳定字符串、不是闭合集**：消费方读它的**唯一**用途是「要不要走鉴权握手分支」（SOCKS5 选 user/pass 还是无认证方法），core 遇到不认识的值的默认行为恒是「当作已启用」。**消费方只读 `isEnabled`**（口径 = 「本实例会不会拒绝任何人」，`none` 已并入）——不要再自己判一次 `kind !== "none"`，那是把同一个事实抄成第二份真相。
- `basic` 在 socks4/sockss4 额外接受 `USERID == username`（无密码字段）。
- 审计 `tag` 为 `"tunnel"` 仅当 `method === "CONNECT"` / `socks*` 协议 —— 不许用 `authority.includes(":")` 判定。身份层零日志，审计经 `IdentityContext.onAuthEvent` → `BaseProxy.authorize` 直发 `auth.decided`（`tag` 在 data、身份维度在 context）→ runtime 层落盘（`runtime/event-log.ts:bindProxyEventLogs`）。
- SOCKS 鉴权发生在握手后：socks5/sockss5 走 RFC1929 user/pass（`isEnabled` 为真时），socks4/sockss4 用 USERID。

## 转发器（`forward/`：**按两条正交的轴分目录**）

**目录形态**（`unit/forward-directory-layout.test.ts` 逐字锁住文件清单 + 依赖方向）：

```
forward/
  base.ts              ← 横跨两轴的公共基类，**刻意留在根上**（搬进 channel/ 会让基类依赖自己的子类目录）
  channel/             ← 入站协议轴：http / tunnel / upgrade / socks + 握手读取器 socks-reader
  upstream/
    dial.ts            ← 纯传输层（建链 + 桥接）
    connector/         ← 上游对接轴：四个连接器 + registry + barrel
```

- **为什么值得拆**：真实收益不是「好看」，是**依赖方向变得可断言**——`channel/**` 只能朝 `upstream/**` 单向，反向即目录级环；`dial.ts` 与四个转发器平铺同级时「谁引谁」只能靠人记，拆开后直接扫 import 钉死。`channel/**` 内部**同目录相对**、引 `upstream/**` 与 `base.ts` 一律 `@/` 别名。
- 四个转发器（`HttpForwarder` / `TunnelForwarder` / `WsForwarder` / `SocksForwarder`）继承 `base.ts:ForwarderBase`（本身已 `extends ContextualBase`）：共享 `services`（`CoreServices`）/ `connectors`（`ConnectorSource`）/ `dialer`（**2c 起只服务 `bridge`**） / `config`（继承 getter） / `preDial` / `connectorForRoute` / `preDialPeerTarget` / `denyUpstreamLoop` / `denyUpstreamLoopOf` / `settleDenied` / `settleDialFailure` / `emitRoute`（路由事件，core 零日志）/ `refuse` / `refuseByCause`。**发事件只有 `scope.emit(e)` 一个入口**（零 `emit` 实例字段、零 `emitWithUser` 方法），身份维度由 `RequestScope` 携带。四个类的构造函数都显式写 `constructor(ctx: CoreContext, services: CoreServices, connectors: ConnectorSource)` 后 `super(ctx, services, connectors)`（不靠隐式继承构造），**不收 `PipeEventSink`**。事件统一为 `PipeEvent`（无泛型；`HelperEvent` 是 `PipeEvent` 的真子集、可直接传入；判别联合不带索引签名）。

### 三个入口方法名互不相同，且与 `InboundKind` 逐字对齐

| 入站事件（`InboundKind`） | 转发器 | 入口方法 | 文件 |
|---|---|---|---|
| `"request"` | `HttpForwarder` | `handleRequest(req, res, scope)` | `channel/http.ts` |
| `"connect"` | `TunnelForwarder` | `handleConnect(req, socket, head, scope)` | `channel/tunnel.ts` |
| `"upgrade"` | `WsForwarder` | `handleUpgrade(req, socket, head, scope)` | `channel/upgrade.ts` |

- **三个入口方法名刻意各不相同**（`handleRequest` / `handleConnect` / `handleUpgrade`）——同名的护栏等于没断言（按方法名无法区分三项），所以「派发表的三项各自指向不同实现」只能靠**按名字逐项断言**（`unit/inbound-dispatch.test.ts`）。**名字自带身份**也让「派发到哪」从表里一眼可读，不必去翻转发器类名。
- **`upgrade.ts` 不实现 WebSocket 协议**——不做帧解析、不做分片重组、不做掩码、不做 ping/pong、不做 close 握手（`buildUpgradeReq` 只改写 HTTP 握手报文，`relay` 等 101 之后就是一条透传管道）。叫 `websocket` 会让人以为「帧的处理归这里」。**类名 `WsForwarder` 与 `logPrefix: "upgrade"` 刻意与文件名不同**：类名是导出符号，改它会波及调用面与既有护栏的字面量；`logPrefix` 是**落盘日志文本契约**（`forwarder-connector-wiring` 逐字断言 `[upgrade] error …`）。**文件名的 `upgrade` 与 `InboundKind` 的 `"upgrade"` 同字**，这一致性是想要的。

### 前置接线已收进基类（窄抽的五个方法）

四条通道**逐条同形**的那部分收在 `ForwarderBase`，`channel/*.ts` 里已不再出现「选连接器」与「补判 preDial」这两件事：

| 基类方法 | 收的是什么 | 调用点 |
|---|---|---|
| `connectorForRoute(route)` | 按有效路由选连接器（三元式 `route.route === "direct" ? this.connectors.direct() : this.connectors.upstream()`，**两行、三元式没有变**） | 四条通道各一处 |
| `preDialPeerTarget(req, connector, targets, deny, scope)` | 传输对端 ≠ 有效拨号地址时补判一次 `preDial`，返回 `{ peer, denied }` | `http` / `upgrade` |
| `settleDenied(status, scope)` | 守卫拒绝的终态映射（403 → `target-denied`/access，其余 → 自环 `fail`） | 四条通道的 `deny` 闭包 |
| `settleDialFailure(respond, err, scope)` | 拨号失败的「协议应答 + `fail(stage:"dial")`」 | 四条通道的 catch |
| `denyUpstreamLoopOf(connector, respond, scope)` | 上游自环预检的接线半边（地址取自 `selfLoopTarget()`、直连即跳过、终态文案 `upstream proxy loop detected`） | `tunnel` / `socks` |

- **收益是「改一处好过改四处」，不是减行数**。`codeOnly` 实测（逐文件非空代码行）：四条通道合计 **936 → 857（瘦 79）**，`base.ts` **183 → 230（涨 47）**，**净 -32 行 = 原 936 行的 3.4%**。**这个数字远小于直觉，原因见下条**。配额绕过之所以要逐处修补，正是因为「同一逻辑四份拷贝」；那才是判据。
- **刻意留在各通道的**（`core/AGENTS.md` 已记为刻意差异，见下方「刻意不收的」）：四种应答形态（`ServerResponse` 早失败 / 裸 socket 状态行 / SOCKS 二进制 + 延时销毁 / 原样透传不断链）、`upstream-error` 的文案与**是否带 `err`**（tunnel 靠守卫已发过、socks 那条不带）、`isSocksTunnel(connector)`（**现只服务 upgrade 的 `"via socks "` 失败日志尾巴**，报文形态已归 `connector.targetForm`）。**不要**把它们参数化成万能函数——那正是本文件下方「不建协议应答层」那条记录的同一种假抽象。
- **`settleDenied` 只有两个分支不是遗漏**：`helpers/predial:guardPreDial` 只有 `deny(STATUS_BAD_GATEWAY)` 与 `deny(STATUS_FORBIDDEN)` 两个调用点，**400 那条拒绝走各协议自己的解析失败路径**（`request.rejected(reason, "parse", 400)`），不经 `deny` 闭包。三条通道里任何「顺手也判 400」的分支都是**不可达**的（400 只走各协议自己的解析失败路径），`unit/forward-directory-layout.test.ts` 钉住不得复活。
- **⚠️ 为什么净收益只有 3.4%（下一个人若想「补完剩下的重复」请先读这段）**：本仓的「重复」与教科书里的不一样——**大部分重复是注释，不是代码**。每份接线都带着一大段解释「为什么这样做」的注释，窄抽时那些注释**跟着各自的语义留在了通道**（`upgrade.ts` 仍在解释「为什么等 101」、`socks.ts` 仍在解释「为什么版本号取自 `connector.kind`」），只有**逐字相同的那几句**归到了基类（`upgrade.ts` 仍在解释「为什么等 101」、`socks.ts` 仍在解释「为什么版本号取自 `connector.kind`」）。行数口径 `codeOnly` 虽然去掉了注释，但它同时**去掉了大部分收益**。**净收益的构成，逐文件点名**：`http.ts` 少 16（deny 闭包的 8 行三分支 + `failEarlyWithTerminal` 整个方法 16 行 → 1 行 + catch 收尾）、`tunnel.ts` 少 31（三元式/if-else 的选连接器 5 行 → 1 + 上游自环接线 14 行 → 1 + deny 闭包 10 行 → 2 + catch 2 → 1）、`upgrade.ts` 少 16（同 http 的 deny 闭包与 catch）、`socks.ts` 少 16（选连接器 4 → 1 + 上游自环接线 14 → 1）。**剩下的「重复」已经不值得抽**：应答形态 4 种、`upstream-error` 载荷 3 种、`isSocksTunnel` / `viaSocksTunnel` 各一个调用点——那正是下方第 3 条「不建协议应答层」记的假抽象。**结论：前置接线已收干净，这层没有下一次同型收益了。**

- **⚠️ 铁律：`user` / `requestId` / `connectionId` 只能经 `RequestScope` 参数逐次传入，绝不存成转发器字段。** 四个转发器实例由服务在**构造期**一次组装、跨请求/跨会话复用（`HttpProxy` 三个 + `SocksProxyBase` 一个），而这三条身份是逐请求才产生的——存字段就是「A 的请求被记到 B 头上」的串号雷。跨会话共享单例这件事全靠「调用点从不把身份写回实例」这条**口头约定**撑着；那条约定由 `RequestScope` 的类型签名接管。`ForwarderBase` 的类注释里写明了这条不变式，护栏见 `tests/integration/forwarder-instance-reuse.test.ts` + `tests/unit/forwarder-request-path-allocation.test.ts`。
- **构造签名是 `(ctx: CoreContext, services: CoreServices, connectors: ConnectorSource)`（三个都必填）**：四个子类都显式写 `constructor(ctx, services, connectors)` 后 `super(ctx, services, connectors)`（不靠隐式继承构造），**不收 `PipeEventSink`**。`services.traffic` 是**进程级**账本服务（与 `user` 那条铁律正交：它不是逐请求数据，四个转发器共享同一实例正是「配额能按用户累计」的前提），低层直构转发器时传一个 `{ identity: noneIdentity(), access: <放行档>, traffic: inertTrafficAccount() }` 的包显式表达「这条链路不判身份、不判名单、不计量」。**`services` 刻意是一个包而不是三个字段**（理由三条见 `forward/base.ts` 文件头「为什么 `services` 是一个包」，并与下方第 5 条那条**已撤回**的否决记录对照）。
- **请求路径零实例化**：三个 `server.on(...)` 回调、`handleForward`、`SocksProxyBase.onConn` 与两个会话处理器里**不得出现 `new XxxForwarder`**。组装只发生在 `HttpProxy` 构造函数（三个）与 `SocksProxyBase` 的字段初始化器（一个），**服务层合计恰好 4 个构造点**（静态计数由 `unit/forwarder-request-path-allocation.test.ts` 锁住）。**入口只有实例方法，没有 `forwardHttp` / `forwardTunnel` / `forwardUpgrade` 三个函数式入口**（它们内部就是 `new XxxForwarder(sink, ctx).handle(...)`，正是「每请求 new」的来源）；低层调用方（几处护栏测试）**直接构造转发器实例并调入口方法**（`handleRequest` / `handleConnect` / `handleUpgrade` / `serveSocks4` / `serveSocks5Connect`，见上方那张表）——那与服务构造期组装是同一种形态。`src/runtime/event-log.ts:FORWARD_ERROR_LABEL` 里的三个**字符串**（日志前缀 `[forwardTunnel error]` 等）是日志文本契约，与那三个函数式入口同名纯属巧合，**不许跟着改**。
- **上游连接器层 `forward/upstream/connector/`**：「怎么到达 dest」的唯一抽象。四个具体类（`DirectConnector` / `HttpConnectConnector` / `Socks4Connector` / `Socks5Connector`，后两者共用抽象基类 `SocksUpstreamConnector`）+ `types.ts` 的 `ConnectorSource` 端口 + `registry.ts:createConnectorSource(ctx)`。**出口只有 `createConnectorSource` 一个**（未登记协议 fail-closed **抛错**，不静默回落 direct）。**选连接器全仓只有一处**：`ForwarderBase.connectorForRoute(route)`，判据是 `route.route === "direct" ? this.connectors.direct() : this.connectors.upstream()`——`direct` ⟺ 该拨真实目标是 `resolveRoute` 已判定的事实，不是独立标志位。四条通道只调那一个方法，**不许在 channel 里再写第二份三元式**（护栏：`unit/forward-directory-layout.test.ts` 的「选连接器收口**那五条**」——① 四个通道文件零「自己拿连接器」的入口（`this.connectors.` / `createConnectorSource(` / 协议查表三种形状）② 零 `new *Connector` ③ 对连接器层**只有 type-only 引用、零值导入** ④ `this.connectors.direct(` 与 `this.connectors.upstream(` 在 `forward/**` 全文**各恰好出现一次**且都在 `connectorForRoute` 体内 ⑤ `connectorForRoute` 体内**零** `upstreamProtocol` / 零 `config.get(`；逐条清单与锚点写法见 `tests/AGENTS.md` 那一节。**注意这五条的锚点全部是「今天仍存在的形状」**：任何一条锚在已不存在的符号上都会**恒真而不锁任何东西**（本仓最危险的一类假绿）。端口的形状、装配期解析与「记忆化挂在 startup 相位上」那条不变式见上方「三个可插值端口」。
  - **协议实现住哪儿（硬不变量，零例外）**：`connector/socks4.ts`（SOCKS4/4a 握手）、`connector/socks5.ts`（SOCKS5 握手 + CONNECT 应答解析）、`connector/http-connect.ts`（CONNECT 上游对接）、`connector/direct.ts`（**无协议实现**——直连不与任何代理对话，`open()` 由传输层建链原语直接组成）。抽象最容易出的错是「实现没跟上抽象」：连接器只剩薄委托、真实现还躺在 `forward/upstream/dial.ts`，于是想读「我们怎么做 SOCKS5 上游」的人去 `connector/socks5.ts` 找不到东西——**可发现性极差**。所以 `open()` / `transport()` **就是**实现本体，不许再写回委托。`socks-upstream.ts` 的抽象基类只装两版共用的东西（拨号外壳 + **握手应答读取器 `readReply`（文案带 SOCKS 字样故只能住这儿）** + 4 个逐字相同的声明式成员），**协议体一律由子类以 `handshake` 提供**。
  - **`OpenContext` 只有 `client` / `dest` / `onEvent` / `logPrefix` / `clientLifetime`**：没有 `viaUpstream` 标志位（`kind` 就是连接器的身份声明），**也没有 `user` 身份字段**（`HelperEvent` 载荷只有 `type`/`message`/`err`；身份一律由 channel 侧的 `scope.emit` 带上，`RequestScope` 每请求一条闭包、身份在其中注一次）。四个 channel 传的都是 `onEvent: scope.emit`（同一个函数引用，与本通道其它 pipe 事件共用一个出口，runtime 层按 `type` 统一分派）。`clientLifetime`（`"linked"` 缺省 / `"independent"`）是**必须由 channel 如实申报**的那一个：只有 channel 知道这次要的是隧道（`open()`，两端同一资源）还是每请求新建的传输层（`transport()` → `http.request`），connector 无从推断，故只透传、不自己设默认。**`logPrefix` 必填**（四个 channel 恒传 `"http"`/`"tunnel"`/`"socks"`/`"upgrade"`）：`logPrefix?` + 三处 `??     - **`"independent"` 的唯一使用方是 http 请求路径**（`forward/channel/http.ts:clientLifetime: "independent"`）。它解的是一条真实的回归：守卫 `upstream.on("close") → client.destroy()` 是**隧道语义**，套到请求路径上会让「源站关掉自己的连接」打死**入站 keep-alive**（实测客户端 `reusedSocket` 恒 false、入站 TCP 连接数 = 请求数，第 2 个请求还会吃到 ECONNRESET）。入站连接的存活是**客户端侧属性**，与上游连不连得上无关。
    - **不要**把它挪到隧道路径（CONNECT / upgrade / SOCKS）：那里 `ctx.client` 与管道确实是同一资源的两端（`bridge()` 双向 pipe），解耦会让「上游已死、客户端还在等字节」变成挂死。护栏：`integration/http-inbound-keepalive-decoupled.test.ts`（正向 + 反向两向）+ `unit/guard-client-lifetime.test.ts`（机制逐条）。
    - 附带事实：`"independent"` 形态下守卫的**客户端侧**监听随上游 socket 的 `close` 摘除。不摘的话入站是长连接、每请求挂一对 → 11 个请求就触发 `MaxListenersExceededWarning` 且闭包线性累积（实测 20 请求 → 22 个 `close` 监听）。挂 `upstream.close` 可靠：出站恒带 `Connection: close`，实测 Node 在响应收尾时必定销毁 `createConnection` 提供的 socket（源站遵守或不遵守都一样）。
  - **`open()` 与 `transport()` 是两种「要什么」**：`open()` 给「到 dest 的字节管道」（CONNECT / socks 入站拿它自己桥接）；`transport()` 给「到**本连接器对端**的传输层连接、**不做协议级协商**」——http 普通请求要的是「连到我、但你自己写报文」（`http.ts` 经 `http.request({ createConnection })` 用），**Upgrade 通道也用它**（对端要的是完整请求而不是裸流，先发 CONNECT 会把上游代理的状态机带偏 → 死锁）。四类实现：direct 与 socks4/5 的 `transport()` 就是 `open().sock`；`HttpConnectConnector` **只拨号到上游**（`secure` 决定 net/tls），**不发 CONNECT、不等状态行**（发了会把上游代理的协议状态机带偏：它先回 200 再等 CONNECT，而 `http.request` 已在等 HTTP 响应 → 死锁）。
  - **因此 TLS 承载归连接器**：`transport()` 返回的 socket 已是握手完成的 `net.Socket`/`TLSSocket`，`http.ts` 侧零 TLS 选项构造、零 `https` 模块 import。**不要**在 http 通道「顺手」把 TLS 选项加回来——那会出现两处协商。
  - **`peerTarget(dest)` 刻意带 `dest` 参数**而 `selfLoopTarget()` 无参：后者答「**我自己的**上游地址」（纯配置事实、连接器独占）；前者答「本次请求的传输对端」——对直连/SOCKS 就是 `dest`，是**请求作用域事实**，连接器并不拥有，无参无从回答。传 `dest` 而非整个 `OpenContext`，是为了让这个纯查询不必拖上 `client`/`onEvent`（声明式方法不该有机会碰事件汇）。两个成员是**两种形状的刻意并存**，不是签名不一致。用途：`http.request` 的 `host`/`port` + 上游失败日志路由 + 「传输对端 ≠ 有效拨号地址时补判自环」（SOCKS 隧道直达 dest，而 client 模式下 `targets.dial` 是上游）。
  - **通道侧只剩一处「两种判据并存」的例外**（`http.ts` 的 Host 回写，直连与 SOCKS 规则不同）：见 Gotchas。**其余差异全部由连接器的声明式数据（`kind`/`targetForm`/`upstreamAuthHeader()`/`peerTarget()`）承担**，`http.ts` 不再自己推协议。
  - **`selfLoopTarget()` 是上游自环预检的唯一数据源**：返回 `undefined`（直连）就跳过预检，返回 `{host, port}` 才喂给 `denyUpstreamLoop`。上游地址**只由连接器给**——channel 一律不许读 `UPSTREAM_HOST`/`UPSTREAM_PORT` 去猜（那正是「自己读配置猜上游地址」的第二真相源，`denyUpstreamLoopAuto` 就是那种东西，别重建它）。
  - **`OpenedUpstream.refusal`（仅 http-connect 的非 200）由 channel 处置，语义刻意不同**：`tunnel.openUpstream` 是「原样透传 `head`+`rest` 给客户端再销毁上游」（不断链语义，`Proxy-Authenticate` 必须送达客户端），`socks.connect` 是「发 `upstream-refused` 事件 + 回 SOCKS 失败应答再销毁上游」（回 HTTP 报文会污染协议）。**连接器绝不销毁、绝不向 `ctx.client` 写任何字节**，成败应答一律归 channel。
  - **接线护栏在 `tests/integration/forwarder-connector-wiring.test.ts`**：锁三条通道的守卫 route 文本（逐字，`[prefix] error <clientAddr> -> <dest> [via …]`，**upgrade 三档齐全：经 SOCKS 上游 / 有效 client 经 http(s) 上游 / 主路径回落直连**）、tunnel 的 refusal 透传（逐字节）、以及「有效路由 direct 时必须选 `connectors.direct()`」（双桩互斥判别；观测的是装配期定死的 `ConnectorSource`）。**route 文本自此是契约**，改它必须先改该文件并说明理由。
  - **upgrade 通道是单一路径**：`WsForwarder.handleUpgrade` 与 `handleRequest` / `handleConnect` / `socks.connect` **同形状**：`resolveForwardTargets` → `preDial` → `emitRoute` → `connectorForRoute` → `preDialPeerTarget` → `transportVia` → `upgradeOver` 等 101。**入口零协议分支**：四个 channel 一律零 `isSocksProto` / `socksVersionOf` / `isTlsUpstreamProto`（护栏在 `tests/unit/dialer-protocol-boundary.test.ts`）。

    - **守卫前缀恒为 `"upgrade"`**（`transportVia` 里的 `logPrefix`）：三条路径的 route 文本是**锁死的契约**（`forwarder-connector-wiring` 逐字断言 `[upgrade] error …`），**不得**按连接器身份改成 `[socks]`。「是否经 SOCKS 隧道」**现在只影响失败日志文案**：`upgradeOver` 内的 `viaSocksTunnel`（由 `connector.kind` 推出的模块内 `isSocksTunnel(connector)` 判定，**不从 `upstreamProtocol` 推导**）决定 `"via socks "` 尾巴。**报文形态（request-target 形态与是否注入上游凭证）只由 `connector.targetForm` / `connector.upstreamAuthHeader()` 决定**，与 `http.ts` 逐字同源——`viaSocksTunnel` **不参与**报文形态（读「有效模式 + `viaSocksTunnel`」就是绕过端口造出第二判据；完整危害与「巧合 vs 契约」的教训见 Gotchas「上游凭证的注入条件不在 `http.ts`」那一条）。`targetForm` 判不出「是否经 SOCKS 隧道」（直连与 SOCKS 同为 `"origin"`），故日志那半边仍用 `kind`。
  - **upgrade 通道的 client 模式也经连接器层**：`WsForwarder.handleUpgrade` 的「有效 client」分支是 `this.transportVia(this.connectorForRoute(route), socket, targets.dest)`——与另外三条通道同一条路。**两点必须保持**：① TLS 承载由 registry 构造期定死，`channel/upgrade.ts` 零 `isTlsUpstreamProto` 导入；② 守卫 route 文本是 `"<dest> via <upstream>"` **全量形式**，与 http/tunnel 同源——**全量形式才是契约**，逐字断言在 `forwarder-connector-wiring`（详见 `tests/AGENTS.md` 与该用例注释）。**不要**把它改回 `open()`：那会让上游先收一条 CONNECT、随即等一条 Upgrade（实测死锁：上游回 200 后本通道在等 101，响应超时）。
- **刻意不收的**：各协议应答形态（HTTP `ServerResponse` 早失败、SOCKS 二进制应答、tunnel 回 200、upgrade 等 101）——强行模板化是假抽象；余量回灌 + 桥接已由 `bridgeWithBuffered` 收口（`establishTunnel`/`establish` 只剩应答 + 委托）。
- `dial.ts:Dialer`（`extends ContextualBase`，`constructor(ctx: CoreContext)`、无自有字段，`this.config` 全走继承 getter）**是纯传输层，建链 + 桥接两块职责**：
  - **建链**：`dialDirect` / `dialTls` / `choose`（按是否加密自动选 net/tls）+ private `dialWith`（open 回调 / error / timeout 三源竞态的统一收敛）。只负责「连上」，连上之后的对端协议协商不归这里。**四个方法的守卫形参一律必填**（`guard: DialGuardOptions`）：`opts?` / `guard?` 那类可选形状零存在理由。**判据是「缺席会走到哪条路」而不是「谁在用」**——`guardDialing` 的缺省档会**向客户端写 502/504 原始 HTTP 报文**且让上下游同生命周期，恰好违反「连接器绝不向 `ctx.client` 写任何字节」这条硬契约。那不是一条自洽的备用路径，是**会静默破坏契约的兜底**（客户端要等到那个时刻才知道自己被写坏了）。护栏：`tests/unit/dead-optionality-cleared.test.ts`（负向源码断言 + 变异测试）。

  - **硬不变量：上游协议的实现只住在 `connector/<协议>.ts`；`Dialer` 不得知道任何上游协议。** 本文件不得出现 `SOCKS4*` / `SOCKS5*` / `buildConnectRequest` / `awaitStatusLine` / `normalizeIp` 等协议常量或协议级状态机，也不得提供「按协议拨号」的入口。`dialViaHttpUpstream` / `dialSocks` / `handshakeSocks` / `handshakeSocks4` / `handshakeSocks5` / `withUpstreamDial` / `readConnectReply` / `readReply` **全部不住在本文件**（它们都在 `connector/<协议>.ts` 或 `SocksUpstreamConnector` 基类里）——**这条不变量零例外**。**防职责回流的负向断言在 `tests/unit/dialer-protocol-boundary.test.ts`**（锁 `Dialer.prototype` 的方法闭集 + **去注释后的源码文本零协议词汇** + 三个连接器各自的实现归属 + 「SOCKS 拨号外壳 / `readReply` 各只在基类一份」）。

     - **判据是「外部真的会注入替身」，不是「core 内部用到了」**：`tests/integration/custom-services-wiring.test.ts` 起真 runtime、走真请求、断言替身**真的被调用**（只查字段是 unit 档的活）。
     - **生命周期确实不同、且这个差异正是打包的理由**：`identity` 与 `access` 是**纯判定**（无状态、随配置现读），`traffic` 是**进程级可变状态**（内存账本 + 落盘队列）。三种不同的东西第一次凑齐到同一个「core 需要什么」的清单里。

     **当初的度量衡错在哪**：拿「给 2 个字段套一层间接」当判据，而正确的判据与上方第 ④ 条同源——**「改一处好过改四处」**。现在每加一个可插值服务都要同时改 `ProxyOptions` 字段、`BaseProxy` 的归一表达式、`ForwarderBase` 的构造参数与四个子类的 `super(...)`、以及每处使用点的 `this.identity`/`this.services.identity` 选择；打包之后新增一项的改动面从「N 处字段 + N 处构造」降到「一处包成员 + 一处归一」。
     **但不要把它拆开**：`services.traffic` 仍可存字段（它是进程级服务、四个转发器共享同一实例），`services.identity` 与 `services.access` 仍每次现读（它们是纯判定、每请求同一个引用，**都不缓存**）。**判据是「生命周期」，不是「存取方式」**。
     ⚠️ **`RuntimeServices`（`runtime/types.ts`）与 `CoreServices`（`types/proxy.ts`）是两个不同的东西，别混**：前者是**库调用方可覆盖的四项**（`identity`/`access`/`traffic`/`trafficLedger`，全部必填或可选由声明说话，`trafficLedger` 是 runtime 独有的落盘副本）；后者是**core 内部归一后的三项**（全必填，`trafficLedger` 刻意不在内——core 从不打开账本文件、也从不给它起定时器，塞进去等于向 core 承诺一件它不做的事）。

## 服务端骨架（`server/`）

- `base.ts:BaseProxy`：**`extends ContextualBase`**（零 Node EventEmitter），状态机 `idle → starting → running → stopping → stopped`（可重入 `starting`），`start()`/`stop()` 幂等模板方法；`stop()` 在 `starting` 态先等在途 start。`ProxyOptions.ctx` 必填并**原样**（不冻结、不兜底）归一进 `Required<ProxyOptions>`，并**同时**经 `super(options.ctx)` 落到基类（同一个对象）；core 内不存在任何依赖缺省解析；**未给 `identity` 时归一成 `NONE_IDENTITY`（`noneIdentity()` 的冻结单例）**、**`access` 必填、core 侧零缺省解析（见上方「缺省档」一节）**、**未给 `traffic` 时归一成 `INERT_TRAFFIC_ACCOUNT`（`inertTrafficAccount()` 的单例）**、**未给 `connectors` 时归一成 `createConnectorSource(options.ctx)`**——那**两个**缺省档**全是显式的「这一项没配」**（不是判否、不是兜底成全局），且**归一只在构造期发生一次**，是**全仓唯一**做这件事的地方（护栏：`tests/unit/access-control-port.test.ts` 的「源码级：`access` 的必填性与缺省档删除（防复活）」三条、`tests/integration/traffic-quota.test.ts` 的「直构 core 不注入 traffic → 归一成显式禁用档」）。⚠️ **`connectors` 必须在任何转发器字段初始化之前就位**，故归一顺序是它先落、转发器字段后落。**缺省解析只允许发生在唯一组装根 `createProxyRuntime()`**（本文件零 `createNoopLogger()` 之类兜底）。`this.config` / `this.log` / `this.events` 是 `ContextualBase` 的**继承 protected getter**（本文件不再自带任何投影）；**必须每次现读、绝不允许把 `events` 缓存成字段**——`RuntimeContext.setEvents()` 能在运行期换总线，缓存会把「换完立刻生效」变成半个进程级暗改（`setState` 就是每次现读后 publish）。⚠️ **那条论证的前提在本仓内永不成立，如实记下来**：`setEvents` 的调用方全在**库调用方**（`ProxyRuntime` 公开面——它把 `RuntimeContext` 经 `services` / `ProxyOptions.ctx` 交出去），`src/` 内**零调用**是**预期形态、不是死代码**。但也正因为本仓内没人用它，**「绝不允许缓存 events」这条纪律在本仓是靠注释与源码级断言维持的，不是靠运行时压力**——谁把 `this.events` 缓存成字段，**全仓测试都不会红**。改 `base.ts` 的 `events` 读取形态时必须自己复核这条，别把「护栏不存在」当成「没人发现问题」。`setState` 发 `lifecycle.changed`（**唯一来源**，见下「事件单通道」）。`ConnRegistry`（`track`/`drain`，http/socks 共用一份）+ `closeServer()` 关服模板 + `authorize()`（异常转 deny，并**直接发布 `auth.decided`**）。**`listen` 的对称面只住 base.ts**：`listenAsync(server, port, host)` 与 `ListenableServer`（net/tls/http.Server 均结构满足的最小形状：`listen`/`once`/`off`）——`http.ts`/`https.ts`/`socks-base.ts` 一律从 `base.js` 取，禁止再各自包 `listen` Promise（也别为它新开一个 `utils/net.ts`）。根 AGENTS.md 只保留状态机契约。
- `factory.ts` 按 `ProxyProtocol` 建实例；`http.ts`（`HttpProxy`：三个 `server.on` 回调 + **派发表 `buildInboundChannels`** + `handleForward` 走两阶段准入 + `writeRejected`）被 `https.ts` 继承复用（仅重写 `doStart` 建 TLS 服：证书材料经 `@/utils/tls/index.js:loadCerts` 读、选项经 `tlsServerOptions` 拼、握手告警经 `./tls-alarm.js:bindTlsClientError` 挂）。**`HttpProxy` 持有三个 `protected readonly` 转发器字段（`httpForwarder` / `tunnelForwarder` / `wsForwarder`），在构造函数里一次组装**；`bindServer` 的三个回调只调它们的方法，**方法体内零 `new`**。`protected` 是刻意的：子类（含测试探针）能拿到实例断言复用行为。
- **入站派发表（「哪种事件走哪个转发器的哪个方法」的唯一一处）**：`http.ts` 导出 `InboundKind = "request"|"connect"|"upgrade"`、`InboundEvent`（判别联合，每支字段由该事件的 Node 回调参数决定）、`InboundChannel<K>`（`forwardKind` + `rejectTarget(event)` + `dispatch(event, scope)`）、`InboundChannels`（映射类型）、`buildInboundChannels(forwarders)` 与 `channelFor(channels, kind)`。`HttpProxy` 在**构造期**建一次表（`private readonly channels`），`handleForward` 只做一次表查。
  - **三个 `server.on` 回调只做「Node 参数 → 统一形状」的适配**：回调体内**零 `if (kind …)`、零三元选转发器、零 `Forwarder` 字样**。加第 4 种入站事件的动作是「往表里加一项 + 加一个回调」，**不是复制一遍前置接线**。护栏：`tests/unit/inbound-dispatch.test.ts`（恰好三项 / 三种 `forwardKind` 互不相同 / 三个不同 `dispatch` 闭包 / 派发参数逐字 / 回调源码级负向）。
  - **`channelFor` 不是运行期逻辑，是「把种类已确定这件事告诉类型系统」**：`channels[kind]` 在 `kind` 放宽成 `InboundKind` 时会退化成三个通道类型的**并集**，其 `dispatch` 收不了 `InboundEvent`（三个形参类型求交等于无解）。`channelFor` 按映射类型的索引访问（`InboundChannels[K]`）把泛型带回来，事件的判别键与通道签名因此逐字对齐——`connect` 那支写 `event.head` 能编译，误写成 `event.res` 立刻编译期红。**别把它「简化」成 `channels[kind]`**，也别给它加查表失败的兜底。
  - **`InboundChannel.forwardKind`（`ProxyForwardKind`）只服务一件事**：公共事件面 `request.started` / `forward.request-headers` / `forward.error` 的 `data.kind`（逐字契约，`request-scope-ids` 与 `core-event-bridge` 锁着）。**它不参与任何控制流**，改它不改行为。它也**不承担**「本种类归哪个转发器」这个职责——那件事由三个互不相同且与 `InboundKind` 逐字对齐的方法名承载，护栏直接按名字断言（见上方「三个入口方法名互不相同」一节与 `unit/inbound-dispatch.test.ts`）。**别再为了那条标签把方法名改回同名**。
  - **SOCKS 不进这张表**（它不是 `server.on` 事件，而是连接内的握手状态机），但它与本表共用 `admission.ts` 的两阶段准入与 scope 组装。
- **`admission.ts`（入站两阶段准入）**：`createInboundAdmission({ ctx, protocol, socket, requestId, scopeContext, services, authorize })` 造一个 `InboundAdmission`，持有**客户端 TCP 对端 / connectionId / requestId / 终态守卫**四样事实，并提供两个阶段方法：

  | | 阶段 A（握手前） | 阶段 B（握手后） |
  |---|---|---|
  | HTTP（`handleForward`） | `admitClientIp(403, respond)` | `authenticate(credentials, 407, respond)` → `scopeFor(user)` → 派发 |
  | SOCKS（`onConn` → `socks-session`） | `admitClientIp(undefined, respond)` | **握手**（greeting / RFC1929 / SOCKS4 目标）→ `authenticate(credentials, undefined, respond)` → `scopeFor(user)` → 派发 |

  - **`services` 收整个 `CoreServices` 包、却只用到 `access`**——刻意。判据是「这条缝上 core 需要什么服务」有且只有一份形状：阶段 B 的身份端口**已经**由 `authorize` 闭包从同一个包里桥接进来了；若这里只收 `access`，同一个包就被拆成「一半走形参、一半走闭包」，读代码的人要停下来问「为什么 identity 在一个地方、access 在另一个地方」——而那个问题**没有语义答案**，正因如此更要收成一个包。
  - **两个方法名保留 `admitClientIp` / `authenticate` 不改成端口方法名**：它们是**准入流程的两个阶段**（"这个 IP 准不准进" / "这份凭证过不过"），不是端口方法的转写。`admitClientIp` 内部调 `services.access.checkClient({ client })`，`authenticate` 内部调 `identity.identify(...)` 并把异常转 deny。阶段 A 的判定**必须同步**（`checkClient` 是同步端口，它的返回值立刻喂给「发 `ip-denied` / 写协议应答 / 结算 `access` 终态」这一串同步收尾）——收包不影响这一点，但收裸函数就一定会有人把它写成 `await`。

  - **两阶段而非「一函数走完三关」是硬裁决**：SOCKS 的握手**夹在**阶段 A 与鉴权之间，塞进通用流程就是把「连接内的字节状态机」硬合并。握手仍住 `socks-session.ts`。
  - **判定与应答分离**：`admitClientIp` 只判定准不准 + 发 `pipe: ip-denied` + 结算 `access` 终态；**协议应答由调用方的 `respond` 回调给出，且它在这两步之间执行**（顺序是契约：`pipe: ip-denied` → 协议应答 → 终态）。`rejectedStatus` 显式传 `403` / `undefined`——SOCKS 无状态码协议传 `undefined` **不是「忘了传」**。
  - **`authenticate` 只覆盖「凭证判定不通过」**（reason 恒 `"proxy-auth-required"`、stage 恒 `"auth"`）；握手解析失败那类**不是凭证判定**的拒绝（非法 SOCKS4 报文 `invalid-socks4-request`/parse、非法 RFC1929 帧 `invalid-auth-message`/auth、非法 greeting `invalid-socks5-greeting`/parse）仍归 `socks-session.ts` 的状态机。凭证侧事实由 SOCKS 侧合成（RFC1929 → `proxy-authorization: Basic …`、`req` 只有 `{headers, socket}`），`requestId`/`connectionId` 由准入层注入。
  - **`scopeContext` 同时决定哪些关联 id 进入 scope 的身份维度**（`createRequestScope` 把 `identity` 合并进发布的 context，「在 context 里却不算身份」是自相矛盾的形状）。HTTP 传 `{protocol, client: getClientAddress(req), target?, requestId, connectionId}`；**SOCKS 刻意只传 `{protocol}`**——SOCKS 的 pipe 事件不带 id，**补 id 就是改事件载荷**。这是**内容**差异、不是**形状**差异。
  - 终态的 `client` **恒为 TCP 对端**（两条路径一致）；`eventContext.client` 恒为 `getClientAddress(req)`（展示/审计口径）。**两者是不同的事实，刻意不合并**。终态不含 `scopeContext.client`。
  - 护栏：`tests/integration/inbound-admission-order.test.ts`（HTTP 与 SOCKS 各自三关的顺序与事件逐条锁死，含「SOCKS 握手应答字节先于 `auth.decided` 出现」这条把**结构差异**钉成可观测顺序的断言）。
- `tls-alarm.ts:bindTlsClientError(server, log: EventLog, protocol)`：TLS 握手/客户端证书告警接线，`https.ts:doStart` 与 `socks-base.ts:onListenerReady` 共用一份实现。**它住在 core 而非 utils**（原 `utils/cert.ts`）：`utils` 是依赖树最底层，握手告警需要「core 事实 → 日志文本」翻译层，放 utils 会逼出 `utils → core` 的反向依赖。事件码/文本格式在 `../log-events.js`。
- `socks-base.ts`（`SocksProxyBase` + `PlainSocksProxy` / `TlsSocksProxy`：`createListener` 是明文/TLS 唯一差异点）+ `socks-session.ts`（`runSocks4Session` / `runSocks5Session`，经 `SocksSessionHost` 最小接口注入，**不含日志器**）。四个 SOCKS server 文件是 21 行薄壳；监听器 `error` 与 http 同形发 `server.error` 事件。
- **`SocksProxyBase` 的转发器字段**构造器只收 `this.options.ctx`（事件槽由 `RequestScope` 携带），仍是**跨会话共享单例**。**`sessionHost` 收 `InboundAdmission`（不是 `terminal`）**：`authenticate` 与 `scopeFor` 都是准入层方法的透传（`authenticate: (creds, respond) => admission.authenticate(creds, undefined, respond)` / `scopeFor: (user) => admission.scopeFor(user)`），**本地不再实现任何准入逻辑**。握手解析阶段调 `scopeFor()`（不带 user，此时还没鉴权），鉴权命中用户名后调 `scopeFor(ok.username)` —— 逐次传入，绝不落 forwarder 字段。SOCKS 的 pipe 事件**不带 `requestId`/`connectionId`，且刻意不补**（补上就是改事件载荷）；需要按 id 串联时读 `terminal.snapshotContext()`。
- `socks-base.ts:onConn()` 的**第一件事是造 `InboundAdmission` 并过阶段 A**（拒绝走 `pipe` 的 `ip-denied`，与 http 同形；`respond` 是 `socket.destroy()`，SOCKS 侧 `rejectedStatus` 恒 `undefined`）；握手后 `authorized` 兜底是保险，主力是 `tlsClientError`（接线与边界见 Gotchas 的「core 零日志禁区」与 `core/log-events.ts`）。`doStart` 以 `.catch` 兜住 `onConn` 的意外抛错：销毁 socket 并发 `clientError` 上抛（core 零日志），避免 unhandledRejection。

## 本目录 Gotchas

- `http.Server` 的 `connect` socket 是 `Duplex` 不是 `net.Socket` —— 全链路用 `Duplex`。
- **请求路径不再 `new` 任何转发器**：`HttpProxy` 的三个 `server.on(...)` 回调、`handleForward`、`SocksProxyBase.onConn`、两个会话处理器体内都**不许**有 `new XxxForwarder`（它们拿到的都是构造期建好的实例 + 每请求一条 `RequestScope`）。想「顺手改成懒加载」之前先看 `ForwarderBase` 的铁律注释——懒加载会诱使人把逐请求数据挂到实例上。
- Status-line 等待（CONNECT 的 200、Upgrade 的 101）统一走 `awaitStatusLine`；`upstreamTimeout` 只兜时间不兜内存（另有字节封顶）。
- **`tunnel.establishTunnel` 的 `opts` 必填且两个字段都必填**（`{ head?: Buffer; rest?: Buffer } = {}` 那份「可选 + 缺省」形状零存在理由）：唯一调用点在 `openUpstream` 的成功分支上，`head` 来自 Node 的 `connect` 事件（**恒为 Buffer**，可为空）、`rest` 来自 `OpenedUpstream.rest`（**端口契约上恒为 Buffer**，直连/SOCKS 传共享空缓冲）。两者的「可能为空」表达在**值的层面**（零长 Buffer），不表达在**类型的层面**——给一个恒有值的字段留可选项，等于让「忘了传」和「传了空」在类型上无法区分。
- SOCKS 域名是客户端原始字节（不过 HTTP 解析器）：解析/建握手前必过白名单。
- SOCKS4a 哨兵判 `DSTIP ∈ 0.0.0.0/24`：规范草稿写全 0、curl/PySocks 发 `0.0.0.1`，两者都得认；漏全 0 会误判纯4、域名残渣被当载荷打进隧道（客户端拿假 90 后收到 400）。护栏在 `tests/integration/socks-handshake.test.ts`，脚手架 `socks4aRequest(..., dstip)` 可改哨兵。
- 对端是 http/https 上游代理（`connector.targetForm === "absolute"`）时，Upgrade 报文保留 absolute-form + 按 `connector.upstreamAuthHeader()` 注入 `Proxy-Authorization`（`buildUpgradeReq(..., toUpstreamProxy, identity, upstreamAuth)`）；对端是源站（直连 / SOCKS 隧道 / 隧道中继型）用 origin-form 且绝不带上游凭证。**分流唯一依据是 `connector.targetForm`（对端身份），不是 `route.mode`、也不是 `connector.kind`**——判据归连接器这一条，危害与「巧合 vs 契约」的教训见 Gotchas「上游凭证的注入条件不在 `http.ts`」那一条。
- **⚠️ Upgrade 通道走 `transport()`，绝不走 `open()`（2c 实测踩到）**：`WsForwarder.transportVia` 调的是 `connector.transport()`。对 `HttpConnectConnector` 而言 `open()` 会**先发一条 `CONNECT` 再等 200**，而本通道紧接着要发 absolute-form 的 Upgrade 并**等 101**——上游代理回完 200 就进入「等 CONNECT」的状态机，本通道却在等 101，实测结果是客户端只拿到 `[upgrade] upstream response timeout`（`integration/forward-tunnel-guard.test.ts` 的两条非 101 用例会直接红）。`DirectConnector` 与 `SocksUpstreamConnector` 的 `transport()` 恒等于 `open().sock`，故只有 http(s) 上游这一档会踩。判据一句话：**Upgrade 通道的「先发字节」是本通道自己写的报文，不是裸流**——要传输层，不要隧道。
- **`http.ts` 只有一条路径**：`handleRequest()` 只做「解析目标 → 选连接器 → 单一路径 `forwardViaTransport`」，`forwardViaRequest` / `forwardViaSocks` / `dialViaSocksAndForward` / `dialer.dialSocks` / `upstreamTlsOptions` / `node:https` 这些形状**都不存在**。差异只剩连接器的声明式数据：`targetForm` 决定 request-target 形态、`kind` 决定 Host 回写规则、`upstreamAuthHeader()` 决定凭证面、`peerTarget()` 决定 `http.request` 的 host/port 与失败日志路由。
  - **Host 回写是「两种判据并存」，不是同一个东西抄了两遍——不要统一**：`targetForm === "absolute"`（对端是代理）**原样保留**客户端 Host（absolute-form 请求行的权威值已经是「客户端要访问谁」，改写会与请求行自相矛盾）；直连（`kind === "direct"`）在客户端发 absolute-form 时按 RFC 7230 §5.4 **条件回写**（触发条件＝客户端 Host 与 request-target 冲突）；经 SOCKS 隧道**无条件回写**为 `formatAuthority(dest.host, dest.port)`（前提＝request-target 已被本代理改写成 origin-form、客户端的 Host 不可信）。实测两种判据在**可达**请求上产出的字节逐字相同，差异只在「URL 省略缺省端口」那种 `absoluteFormAuthority` 会丢端口的形态上——**所以更不能因为「看起来等价」就顺手统一**。
  - **上游凭证的注入条件不在 `http.ts`**：只由 `connector.upstreamAuthHeader()` 决定（直连与 SOCKS 恒返回 `undefined`，凭证在 SOCKS 握手里）。在 http 通道再按 `toProxy` 判一次就是冗余的第二判据，不许有。
    - **⚠️ 两条通道必须逐字同源**：都只认 `connector.targetForm` / `connector.upstreamAuthHeader()`。**别再从 `config` 或 `kind` 推**——`buildUpgradeReq` 收一个 `ConfigAccessor` 自己调 `upstreamAuthValue(config)` 算凭证、`toUpstreamProxy` 判 `mode === "client" && !viaSocksTunnel`（`viaSocksTunnel` 由 `connector.kind` 推），这类写法会让两条通道各执一份判据、造出绕过端口的第二真相源。
    - **危害（第三方注入自定义 `ConnectorSource` 时真实可达）**：一个「**隧道中继型**」连接器（`kind:"https"` + `targetForm:"origin"` + `upstreamAuthHeader(): undefined`——中间有一跳中继网关，终点仍是源站）会同时骗过两份判据的两半：`isSocksTunnel` 恒 false → 旧判据判成「对端是代理」→ 用 **absolute-form** request-target 打给一个**不是 HTTP 代理**的对端，并把 `UPSTREAM_USERNAME`/`UPSTREAM_PASSWORD` 的 **Basic 凭证注入给真实目标站**。现行写法是 `toUpstreamProxy = connector.targetForm === "absolute"`、凭证只经 `connector.upstreamAuthHeader()`，**同一个字段说了算**。护栏：`tests/integration/forwarder-connector-wiring.test.ts` 的「隧道中继型」那条（**已变异测试验证**：把 `toUpstreamProxy` 改回「有效模式 + `viaSocksTunnel`」→ 恰好那一条红）。
    - **⚠️ 教训：「巧合撑着的契约」是本仓反复出现的陷阱**。今天这个漏洞**不可达**只因内置连接器恰好满足「`kind === "direct"` ⟹ 该请求恰是 server 模式」且「SOCKS 两版的 `targetForm` 恒 `origin`」，于是两份判据在**内置集合上恒等价**。但 `kind` 与 `targetForm` 是**两个独立声明式字段，端口对二者零约束**（`kind:"https"` + `targetForm:"origin"` 编译期完全合法）——**那是巧合，不是契约**。凡「两条判据在今天的内置实现上等价」的写法，都要当成待办而不是已修：等价只说明**缺陷路径还没被走通**，不说明它走不通。**下一个人发现某处读 `kind` 推对端身份时，正确的改法是读 `targetForm`、而不是给 `kind` 加约束。**
  - **`upstreamTimeout` 必须自行装订在 socket 上**（合并引入的新事实）：Node **不会**把 `http.request({ timeout })` 应用到 `createConnection` 提供的 socket（实测传了 `timeout` 后 `socket.timeout` 恒为 `undefined`、`req.on("timeout")` 永不触发）。用 `proxy.setTimeout()` 也不行——那是「从请求起算的一次性」定时器，会把耗时超过 `upstreamTimeout` 的**慢速大响应误杀**；要保持的是**空闲**超时，故装在 socket 上。`<= 0` 即禁用（同 `socket.setTimeout(0)`）。
  - **`Connection: close` 只有 `sanitizeHeaders` 一处**：渠道分支自己再写一遍 `connection = close` 是重复，且不改变任何字节（三条支路都经过 `sanitizeHeaders`）。
  - **⚠️ 面向运维的已知特性：本代理不复用上游连接，每个转发请求新建一条上游连接。** 实测同一源站连发 20 个请求 → 源站侧 20 条 TCP 连接，且源站看到的 `Connection` 恒为 `close`（即使源站本身完全支持 keep-alive）。**成因与取舍**：`Connection: close` 由 `sanitizeHeaders` 无条件强制（`helpers/headers.ts`），而出站传输层由连接器/守卫掌管（每请求新建 socket + 拨号守卫 + 每 socket 空闲超时），**池化与这套传输层管理不兼容**（池里的 socket 无法逐个绑定请求作用域的守卫与超时，且后续流量计量还要在这些 socket 上包一层）。**这是自觉的性能取舍，不是缺陷**：入站 keep-alive 不受影响（客户端侧连接由 Node 的 http 服掌管，正常复用，见 `http-inbound-keepalive-decoupled.test.ts`）。**不要**以「复用连接省资源」为名在 http 通道把 `Connection: close` 去掉或引入 agent 池——那会让每请求新建的守卫与上游 socket 的归属重新变得含糊。
  - **出站失败日志统一为 `[http] upstream error <peer.host>:<peer.port>`**（SOCKS 支路不写 `via socks` 字样）；「经哪种上游」的信息改由守卫 route 文本承担（`[<prefix>] error <clientAddr> -> <dest> via socks<N> <upstream>`，见 `forwarder-connector-wiring` 护栏），信息量只增不减。
- 拨号失败成因区分：超时（`DialTimeoutError`）→ 504，其余 → 502；SOCKS 回 FAIL 不区分。catch 里一刀切 502 会吃掉超时成因。
- **转发报文 authority 一律经 `formatAuthority` 补 IPv6 方括号**：解析侧 `parseTargetParts`/`parseAuthority` 刻意剥方括号以便 `net.connect` 直用，拼装侧不补会产出 `CONNECT ::1:443` / `Host: ::1:443` 畸形报文。**三处都经它**：`buildConnectRequest`、`buildUpgradeReq` 的 Host 回写、`http.forwardViaTransport` 的 SOCKS 分支 Host 重写。
- `tunnel.handleConnect` 解析 authority 失败回 **400**（客户端请求报文非法，与 http/upgrade 解析失败语义一致）；502 只留给网关侧失败。
- **上游协议 fail-closed（安全属性，抛点固定在请求期）**：未知 `upstreamProtocol` 的兜底形态只有**抛错**一种，绝不是「降级 direct 保连通」；非法协议由 **`ConnectorSource.upstream()`（即 `registry.ts:resolveUpstream`）抛错**，server 层 `handleForward` 的 catch 转 `forward.error`。
  - **正确理由是「静默降级直连 = 流量旁路」**：对一个代理服务，「上游协议配错 → 全部静默直连」意味着流量**绕过上游直出**，外部表现是「服务还在跑、请求还成功、但根本没走你配的链路」——这比直接报错糟糕得多（报错至少让运维知道配置错了）。所以必须 **fail-closed**。
  - **别拿「那条分支不可达」当理由**：CLI 路径的 `upstreamProtocol` 确实经 `FIELDS.parseEnum` fail-fast，但**库路径不经**——`createProxyRuntime({ config })` 走 `new ConfigStore(...)`，而 `ConfigStore` **零校验**（不跑 FIELDS 的解析/范围/交叉校验），`upstreamProtocol: "ftp"` 能被直接注进去。该分支**可达**。
  - **不要以「增强健壮性 / 保持连通」为名把静默兜底加回来。** 想要健壮，正确的位置是**配置校验层**（`loadConfig` 与纯内存 runtime 的构造期校验），让它**启动就报错**，而不是让请求期偷偷换一个上游形态。
  - **⚠️ 不要把抛点前移到装配期**（裁决固定为「保留在请求期」）。前移会让上面那条护栏断言的 `forward.error` 事实**消失**、变成启动期异常——**那是换掉一个安全属性，不是加固它**：一条都没发出去的代理比一条 `forward.error` 更难定位是哪个请求撞上了完整配置。完整三条理由见上方「三个可插值端口」`ConnectorSource` 小节。
  - 回归护栏 `tests/integration/upstream-protocol-fail-closed.test.ts`（库路径注入非法协议 → `forward.error` + **源站零字节** + 客户端拿不到 200；带一条合法协议的对照组证明不是「怎么都不通」）、`tests/unit/connector-registry.test.ts`（未登记协议 `upstream()` 抛错、且**每次都抛**——`??=` 右侧抛错不赋值，绝不出现「第一次抛、第二次悄悄给一个直连」）。
- **三条通道的「上游自环预检」入口已统一**：`connector.selfLoopTarget()` 为 `undefined`（直连）就跳过，否则喂 `denyUpstreamLoop(host, port, …)`。channel 里**不许**出现「读 `UPSTREAM_HOST`/`UPSTREAM_PORT` 调 `denyUpstreamLoopAuto`」的写法（那个方法不存在，别重建）。**`denyUpstreamLoop` 只有 4 个形参、不收 `req`**：它的两个调用点（tunnel / socks）都在 `connector.open()` **之前**，那里没有 `IncomingMessage`；`loop-detected` 事件上的 `req` 维度由 `preDial` → `guardPreDial` 那条路径带（那里才真的手上有 req）。`extra?: { req?: unknown }` 那个形参**零调用方**，**别加回来**。
- `WsForwarder.relay` 非 101：透传 `head`+`rest` 后按 `upstream.readableEnded` 分流——已 EOF 则 `client.end()`，否则 `upstream.pipe(client)` 续传剩余 body（`Content-Length` 大于首包时客户端不挂等）；**`readableEnded` 分支不可删**（`'end'` 可能早于续体挂 pipe 前发出）；上游错误/关闭收尾归 `guardDialing` 既有 handler，不额外 destroy。
- `cfg/users.json` / `cfg/acl.json` 热加载语义（1s 节流、坏文件保留旧值、缺失=空；仅 `ENOENT`/`ENOTDIR`/非普通文件算缺失，其它 stat 错误如 `EACCES` 保留旧值并发 error，ACL 不静默全放行；相对路径先绝对化）见 `src/config/AGENTS.md`。
- **core 零日志禁区（保留一条既有例外）**：`src/core/**` 禁止直接打印日志（生命周期行也不行），**请求期**事实一律经 `this.events.publish(...)` 上抛（`pipe`/`server.error`/`auth.decided`/`request.started`/`forward.error`/`server.client-error`/`server.listening`/`server.closed`），落盘收在 `src/runtime/event-log.ts:bindProxyEventLogs`（**CLI 与库共用同一份绑定**，判据见 `src/runtime/AGENTS.md`）。**唯一保留的例外**：`core/server` 在**握手/接入期**（请求尚未成立、无 pipe 事件可挂）把 SOCKS 非法握手、首包超时、TLS 握手失败经 `@/core/log-events.js` 的 `logBadRequest` / `logClientTimeout` / `logTlsClientError` **直接写进当前实例注入的 `this.log`**。这是「进程内告警端口」而非转发管道落盘，DI 契约被 `tests/integration/tls-client-auth.test.ts` 锁定（直构 core 并 spy 注入实例的 `warn`），改这里必须同步改那个测试。`this.log` 的其余唯一用途是把 logger 显式传给 `@/utils/tls/index.js:loadCerts` 等告警端口；**不得**调用 `getLogger()` 或任何全局 logger 回退。事件码词汇表 `LogEvent` 与各事件文本格式住在 `core/log-events.ts`（**不在** `server/log/`），`runtime/event-log.ts:bindProxyEventLogs` 也从那里取事件函数。**事件码是类型级唯一真相源**：`LogEventCode = (typeof LogEvent)[keyof typeof LogEvent]`，`makeEvent` / `makeExtraEvent` 的 `code` 形参一律收口到它（表外或拼错的码在编译期即失败，新增码只加 `LogEvent` 一行）。

- **`ConnRegistry.drain(server)`：原生优化 + 兜底销毁，两样都做，不是二选一**。**Node 的 `closeAllConnections()` 只覆盖它自己的连接表**——`connect`/`upgrade` 事件发出后该 socket 已脱离这张表，故**只走原生调用就拆不掉活着的 CONNECT/WebSocket 隧道**，`BaseProxy.closeServer` 的 `server.close(cb)` 永不回调、`HttpProxy.stop()` 挂死。现语义：先按需 `closeAllConnections()`（http/https 有；SOCKS 的 `net.Server`/`tls.Server` 没有，走不到），**之后一律**遍历 `this.conns` 逐条 `destroy()`（`destroyed` 判断保证重复销毁无害）再 `clear()`。分工：原生调用一次性覆盖 idle keep-alive 那一大类，兜底循环负责它结构上覆盖不到的升级连接与任何非 http 承载（SOCKS 分支无原生方法可走，走的就是那条循环）。回归护栏 `tests/integration/stop-drain-live-tunnel.test.ts`（活隧道 / idle keep-alive / 零连接三档，`stop()` 各自带明确超时预算 + 停服后同端口可重绑断言）。写涉及活隧道的测试不再需要绕开 `BaseProxy` 生命周期（真 `HttpProxy` + 真 CONNECT 可直接放进 `withProxy`）。

### ⚠️ 已知缺口（不要假装已修）

- **`ProxyServer.shuttingDown` 一旦置 true 永不复位**：`stop()` 里 `this.shuttingDown = true` 之后没有任何地方把它设回 false。于是「程序化 `stop()` → `start()` → 用户 Ctrl+C」会走**「二次信号强退」分支**（`cliProcessPolicy.onSignal` 判 `isShuttingDown() && !isWorker()` → `forceStopNow()`），即第一次 Ctrl+C 就强退、不再优雅排空。**要修必须先裁决「迟到的上一代信号该二次强退还是二次排空」**——两者对用户都「能用」，但语义不同（强退 = 丢在途连接与未落盘账本；排空 = Ctrl+C 按了没反应直到排空完）。**这不是能顺手改的 bug**。影响面仅限 `ProxyServer`（库调用方走 `runtime.stop()`，不碰这个字段）。
- **`process.on("uncaughtExceptionMonitor", …)` 只能经 `ProcessPolicy` 的 `installExceptionMonitor` 装**（`src/server/process.ts`），**不许裸调**：裸调不在端口内、不受任何幂等旗标保护，于是 `start → stop → start` 每轮在进程上多挂一个闭包，每个闭包持有 `this.logger`（泄漏）。`ProxyServer` 侧由 `bindExceptionMonitor()` + `exceptionMonitorDisposer` 旗标保证幂等，与 `bindSignals()`/`signalDisposer` 同形。**三条裁决**：① **调用位置固定**（在 ready 面之后的最后一步）——所以**没有**并进 `installGuards`（那在 `start()` 第一步，挪位置会改「`runtime.start()` 抛错时监听器装没装」这件事）；② **`cliProcessPolicy` 装**（CLI 行为逐字保留）；③ **`managedProcessPolicy` 不装**——「不拥有进程」的前提正意味着那份诊断归宿主，它只决定未捕获异常的 stack 由谁打进 stderr。⚠️ **`stop()` 刻意不摘它**：现状那个监听器活过 `stop()`，改掉是另一个决策（会让停机后出的未捕获异常不再有本代理那一行日志），本条只保证不叠加。护栏：**本仓没有**（`src/server/AGENTS.md` 那份的同名段落仍写着旧结论，**待同步**）。
- **纯内存 `config` 模式不跑 FIELDS 校验，非法枚举值能进 store**（`ConfigStore` 零校验）：CLI 路径的 `FIELDS.parseEnum` fail-fast 对库路径**不适用**。这一条有两个出口，且**两个都留着**：① 入站协议由 `runtime.ts:protocolFor(config)` 在**构造期**抛（`未知代理协议: <值>`），覆盖只改变**用哪个值**、不改变**是否校验**；② 上游协议由 `ConnectorSource.upstream()` 在**请求期**抛（见 fail-closed 条）。别把「① 已经启动就报」误读成「② 也可以前移」——前移会让 `forward.error` 那条安全事实消失。

## 事件单通道

**core 的全部事实（含生命周期跃迁）都直接发布到注入的 `EventHub`**（`this.events.publish`），`src/core/**` **零 `EventEmitter`**、零 EventEmitter 事件表；`grep -rn "node:events" src` **零命中**。`forward/**/*.ts` 里的 `this.emit(...)` 也**零命中**——发事件一律 `scope.emit(e)`；`this.emitRoute(...)` 是**路由事件**的独立方法名，与 EventEmitter 无关，grep 时别把它误当成 `emit`。

- **`lifecycle.changed` 一个事实一个来源**：`BaseProxy.setState` 直接发布；`runtime.ts` **订阅**它并只派生 `runtime.*`，**绝不再自己发一遍**（core 与 runtime 同时发布会重复）。因此事件顺序是「`lifecycle.changed` 先、它派生出的 `runtime.*` 后」——core 是发布方、runtime 是观察方，`tests/unit/proxy-runtime.test.ts` 按新顺序断言。**发布次数**：每个状态跃迁恰好一条（`setState` 的「相同状态直接 return」仍在）。
- **`EventContext` 新增 `method?: string`**：日志面要还原 `[forward]` 行的 `method`，而事件载荷刻意不携带原始 `IncomingMessage`（带 socket 与全部请求头），故方法单独走 context。`request.started` 的 `data` 恒为 `{ kind }`（`tests/integration/request-scope-ids.test.ts` 以 `toEqual({kind:"http"})` 锁死）。
- **两个 `client` 是不同事实，刻意不合并**：`request.started`/pipe 的 context 用 `getClientAddress(req)`（XFF → X-Real-IP → Forwarded → socket，展示/审计口径，与 `[auth]`/`[forward]` 日志行同源）；名单判定与 `ip-denied` 的 `client` 恒为 `getSocketAddress(socket)`（只认 TCP 对端）。
- **`auth.decided` 的 `tag` 在 data 不在 context**：`tag`（CONNECT/socks 隧道场景标签）是「本次判定独有的事实」，不是跨事件复用的关联维度，放 context 会让每个事件的 context 都背上它。
- **头掩码住在 `core/server/http.ts`，不进 `helpers/`**：落盘那行 `[{kind}] headers` 需要一份「入站头 → 可展示形态」的翻译，归属判据是「core 事实 → 可展示形态」而非「日志文本拼装」。`@/core/log-events.ts` 是 `[event-code]` **文本**词汇层（函数直接 `log[level](msg, fields)`，且编一个假的 `LogEvent` 码会改掉 `[http] headers` 的 msg 文本）；`@/utils/logger/sanitize.ts` 是**渲染**层（值→文本 / `k=v`），且 `utils/AGENTS.md` 明写「logger/ 只负责写文本，不拥有事件词汇」；`@/core/helpers/headers.ts` 的全部导出都是**出站**判定，其不变量是「`proxy-` 前缀（协议规则）无条件剥，其余**每一个**出站头名 × 每一个头值都问 `identity.isOwnCredential`（身份规则），插件说是我签发的就剥」——目标的 `Authorization: Bearer <token>` 出站**保留**、日志里却必须**掩码**，两种判据方向相反，混在一处迟早被「顺手统一」掉而放大泄漏面。`maskSensitiveHeaders` 只被 `handleForward` 一处调用（它已覆盖 http/tunnel/upgrade 三种 kind），故就近放 `server/http.ts`，不进 `helpers/` 的公共导出面。**掩码必须在 publish 之前完成**（事件总线对库调用方可见）；`req` / `IncomingMessage` 绝不进入任何事件载荷。
- **`PipeEventSink` 保留**（与 EventEmitter 无关）：它仍是 `(e: PipeEvent) => void` 函数类型别名，但**零生产端**——`PipeEventSink` 在 `src/core/forward/**` 与 `src/core/server/**` 里零出现（护栏见 `unit/forwarder-request-path-allocation.test.ts`），唯一出口是逐请求的 `RequestScope.emit`。作用域携带的逐请求闭包内部把 `identity` 同时贴进 `PipeEvent` 载荷与 `EventContext`，投递方式仍是 `this.events.publish("pipe", …)`，`PipeEvent` 载荷形状与日志面零改动。
- **`ProxyAuthEvent` 保留**（长得像载荷但不是）：它是 `IdentityContext.onAuthEvent` 的**内部审计回调契约**（`core/identity.ts` → `BaseProxy.authorize`），`authorize` 读到后转成 `auth.decided` 并把原对象交给前一个 `onAuthEvent` 继续走旁路。**别因为它像事件载荷就删掉**。同理 `AuthAccount`（一条账号表条目）也保留原名：它描述的是**数据**而不是「用哪种方式识别身份」，改名只会给调用方凭空加一次翻译。

## 事件内核（`events/`）

- `src/core/events/types.ts` 是新事件契约的类型单一来源：`AppEventMap` 以元组声明参数，`EventData` 取元组首项作为实际 payload；`EventEnvelope` 携带只读事件名、关联上下文、payload 和时间戳，`EventContext.runtimeId` 必填，connection/request 作用域可选。`EventContext` 另带 `method?`（写入方与理由见上方「事件内核」一节）。`"pipe"` 的 data 类型是 `import type { PipeEvent } from "@/core/types/proxy.js"`（编译期擦除；`core/types/proxy.ts` 不 import `events/types.ts`，故无环）。
- `EventHub` 只公开 `publish` / `subscribe` / `once` / `listenerCount` / `removeAll` / `EventHub.merge`，内部订阅表和分发实现不得暴露 Node `EventEmitter`；runtimeId 缺省由 `crypto.randomUUID()` 生成。发布时 context 浅拷贝并补齐 runtimeId，订阅返回的 `EventSubscription.dispose()` 幂等。
- 分发使用 listener 快照：emit 期间新增或 dispose 不改变当前这次迭代；单个 listener 抛错会被隔离并交给 `onListenerError`。缺省完全静默，既不打印也不读取 `process.env.NODE_ENV`；只有显式 `reportListenerErrors: true` 才走 `process.emitWarning`，或由调用方直接传 `onListenerError`。listener 异常不得影响其它 listener 或 `publish` 返回；`removeAll()` 释放全部订阅，后续 publish 是安全空操作。
- 作用域层级固定为 `runtime → connection → request`：`EventScope.child()` 继承父级 id，可覆写/补 protocol/client/user/target；`toContext()` 只返回不含 runtimeId 的 publish 上下文，`withIdentity()` 返回身份补全后的独立快照。作用域只承载关联事实，不保存日志或控制状态。
- 事件只发布已经发生的事实，不驱动控制流：鉴权、访问控制、路由、请求完成/拒绝/失败等结果由生产方发布，订阅方只观察；事件内核不直接打印日志，日志落盘仍收在 runtime 层的 `src/runtime/event-log.ts`。
- 当前 `AppEventMap` 事件清单：`runtime.starting`、`runtime.started`、`runtime.stopping`、`runtime.stopped`、`runtime.error`、`runtime.dependencies-changed`、`lifecycle.changed`、`config.loaded`、`config.changed`、`config.restart-required`、`config.file-error`、`config.file-recovered`、`config.file-reloaded`、`auth.decided`、`access.client-denied`、`access.target-denied`、`route.selected`、`request.started`、`request.completed`、`request.rejected`、`request.failed`，以及 7 个 core 直发事实 `forward.error`、`forward.request-headers`、`server.error`、`server.client-error`、`server.listening`、`server.closed`、`pipe`，以及 `traffic.quota-exceeded` 与 `traffic.ledger-error`（**都是 core 直发公共事件，刻意不进 `pipe` 判别联合**，见「每用户流量配额」一节）。

## 配置访问器（`ConfigAccessor`）

- `src/config/context.ts` 是 core 读配置的**唯一端口**（一律经 `@/config/index.js` barrel 引用）：`ConfigAccessor` **只有泛型 `get`**，没有 `getAll`、`set` 或任何隐式全局状态；`configAccessorFromStore(store)` 从调用方实例派生 live reader。core 不创建配置状态、不导入模块级 Map，也不存在 `globalConfigAccessor`。
- **数据层与策略层分离**：`config/files/acl.ts` 只负责读文件、校验结构、返回 `AclConfig`；`config/files/users.ts` 同理只提供账号表与 `loadUserPolicy`；**请求期判定全在 `core/access-control.ts`**（`createFileAccessControl(config)` 返回 `AccessControl` 对象 + 按 accessor 隔离的编译缓存 `WeakMap` + `bindAclFileEvents`）。core 侧只 import 判定层，config 侧不认识请求语义；改名单语义只动 core，改文件格式只动 config。
- **判定面只有一个出口，签名统一为「只读入参对象 + 无 `config` 形参」**：`createFileAccessControl(config)` 把 `config` **闭包捕获**并逐次透给三个私有判定，于是「这份判定读的是哪份配置」不可能有第二个真相源（让每个导出函数各收一个 `config` 形参，同一件事就有四种传法——三处调用 + 一处装配——错一处就是「拿 B 实例的名单、判 A 实例的请求」，那类错在运行期表现为**「名单时灵时不灵」**）。三个方法与编译辅助**都是模块级私有函数、一律不导出**，`createFileAccessControl` 只返回一个**对象字面量**（不是 class 实例）：判定层的护栏是**源码级**的（「个人名单不越界」逐函数体断言、`hostDenied` 只有一份），藏进 class 或深层闭包会让那些断言失去锚点，而失去锚点的护栏不是「红」，是**抛错**。
- **观察面也只有一个入口 `bindAclFileEvents(config, handler)`，工厂刻意不收 `onFileEvent`**：若工厂也能传 `onFileEvent`，就会出现**两个写同一个 `WeakMap` 的入口**——两个 handler 都装上了，而判定层只认后装的那个，先装的静默收不到事件，外部表现是「日志说名单没变、判定却换了」。**少一个入口永远优于多一个便利形参。** 故判定路径读观察面的方式只能是 `fileEventHandlers.get(config)`。
- **每用户名单与全局名单的合流**：`checkTarget({ host, user? })` 是**两层**判定，`放行 ⇔ 全局 target 组放行 ∧ 该用户 target 组放行`：
  - **先全局、后个人、全局短路**：全局拒绝是**绝对**的（个人名单只能更严、不能更松），故全局拒时**连 `users.json` 都不读**；两关都拒时报**全局那一条**（`source:"global"`）——全局是权威层，运维先看到自己的全局配置问题，而不是「某用户碰巧也被全局禁了」。
  - 两层判定走**同一个私有 `hostDenied(host, whitelist, blacklist)`**：个人组与全局 target 组「同形」是硬要求，抄两份迟早漂移（源码级断言锁在 `tests/unit/user-acl-merge.test.ts`）。
  - `user === undefined` / 用户不存在 / 未配 `acl` / 两组皆空 → 个人层**中性放行**（等价于只有全局生效）。
  - **个人名单绝不参与 `checkClient`（鉴权之前没有身份）与 `checkRoute`（client 模式的路由决策与「你是谁」正交）**——那两个函数体里连 `user` 三个字母都不许出现（同上护栏的源码级断言；这两个名字是**端口方法名**，`access-control.ts` 内的同名私有函数即其实现体）。
  - 编译缓存：全局一份 `WeakMap<ConfigAccessor, CompiledAcl>`，个人一份 `WeakMap<ConfigAccessor, Map<username, CompiledUserTarget>>`；失效判据都是**源对象身份**（`cached.source === 当前快照`），与 `credentials.ts:indexMemo` 同一手法。个人层在账号被删/撤掉 `acl` 时顺带清槽，缓存规模恒 ≤ 账号表规模。
  - **`AccessDecision.source` 是只在拒绝时写的可选字段**（放行恒为 `{allowed:true}`，不写键）——「哪一层放的」对放行没有意义，写了还让「两关都过」与「上层不存在」无法区分。⚠️ **`AclReason` / `AclSource` 两个别名不存在**（`AclReason` 是 `access-control.ts` 的**模块私有**类型、不导出）：留着导出等于把「名单语义」重新摆成公共承诺，而事件契约那一份已改成 `string`，两处各挂一个公共闭合集正是「两份真相」的起点。**收窄是消费方自己的事**（桥接器按自己能认的取值决定发不发），判定层不该替它们收。**不要把分层信息塞进 `reason`**（不许写成 `"user:blacklist"` 之类）——那是两个维度挤进一个字段，运维分不出该改 `acl.json` 还是 `users.json`。
  - **身份只经 `preDial` 流动**：`ForwarderBase.preDial` 是全仓唯一读 `scope.user` 的地方（`predial.ts` 自己不读任何全局/实例状态）。`channel/http.ts` 与 `channel/upgrade.ts` 各有两次守卫（①有效拨号地址 ③传输对端，且**仅当两者地址不同**才补判——③那条现由基类 `preDialPeerTarget` 承担，窄抽后两条通道共用同一份），判的是同一个 `dest`，且第一次拒了就 return，**故 `target-denied` 不会重复发**（护栏：`tests/integration/user-acl-enforcement.test.ts` 的 client 模式 + SOCKS5 上游那条；`websocket-single-path.test.ts` 另有一条「补判那次不得重复发」的同类断言）。**名单条目原语**（`normalizeIp`/`ipToString`/`parseIpRule`/`compileIpRules`/`ipMatches` 与 `normalizeHost`/`parseHostRule`/`compileHostRules`/`hostMatches`）住在 `config/files/rules/{ip,host}.ts`（acl.json 的规则/数据层），core 侧（`access-control.ts`、`forward/upstream/dial.ts`、`forward/channel/socks.ts`、`helpers/self-loop.ts`）一律经 `@/config/files/rules/index.js` 取，config 目录内部则用相对路径。
- **core 全链路只经必填访问器读配置**：`helpers/predial`（自环）、`forward/base.ts`、`forward/upstream/{dial,connector/**}`、`forward/channel/{http,tunnel,upgrade,socks,socks-reader}`、`identity/`、`server/{base,http,socks-base}` 一律读构造期注入的 `this.config`（`BaseProxy` 侧是 `ctx.config` 的 getter 投影）；HTTP/SOCKS server 把 `this.options.ctx` 整体透传给转发器，转发器/拨号器再经继承 getter 透传到 `Dialer(ctx)`，保证同一实例全链路读同一 accessor。⚠️ **`helpers/route.ts` 与 `helpers/headers.ts` 不在这份名单里**：前者只读 `policy.mode` 一个键、后者零配置导入。
- **所有会读配置的参数/选项均必填，不设全局默认**：`isSelfLoop(h, p, config)`、`upstreamAuthValue(config)`、`upstreamAuthHeaderLine(config)`、`guardPreDial({ config, access, ... })`、`createIdentity(opts, config)`、`createIdentityFromConfig(ctx)`、`ForwarderBase(ctx, services, connectors)` / 四个转发器的 `constructor(ctx, services, connectors)`、`Dialer(ctx)`、`createRequestScope({ ctx, ... })`、`readAcl/readAuthUsers` 的 `opts.config` 以及 `createFileAccessControl(config)` 都必须显式传依赖（`ConfigAccessor` 或 `CoreContext`）。**其中三条的依赖是端口而不是配置**：`resolveRoute(dest, policy)` / `resolveForwardTargets(url, host, policy, dial)` 收 `AccessControl` + `mode` 两事实（不再收 accessor），`isStrippableOutboundHeader(name, value, identity)` / `sanitizeHeaders(h, identity)` / `stripProxyHeaders(h, identity)` 收 `IdentityProvider`（不再收 accessor）——**判据归端口，工具层零配置导入**。`loadCerts` 自身不读配置键（材料来自显式 `TlsInput`）；`readUpstreamCa(config)` / `upstreamTlsOptions(..., config)` 才读取配置。三处统一从 `@/utils/tls/index.js` 取（别再从别处引 TLS 材料装载）。
- **`ProxyOptions.ctx` 是强制隔离位**：`BaseProxy` 将其原样归一进 `Required<ProxyOptions>`，不做冻结、不做 `?? global` 或其它回退。runtime/CLI/server 由各自 `ConfigContext.accessor` 组装成 `RuntimeContext`（`{ config, logger, events }`）后注入；低层调用方（测试、直构 core）则从自己的 `ConfigStore` 派生 accessor 自建上下文。
- **日志同样显式**：日志端口随 `ProxyOptions.ctx.logger` 一起注入，core 内无 noop 兜底（`BaseProxy` 只把它投影成 `this.log` getter）。`HttpsProxy` / `TlsSocksProxy` 只把该 `this.log` 传给证书加载（`loadCerts`）与 TLS 握手告警（`bindTlsClientError`）；文本格式经 `core/log-events.ts` 翻译，不在此层拼字符串；不得使用 `getLogger()`、默认 logger 或任何配置全局量。
- **生效模式唯一入口仍是 `resolveRoute(dest, policy)`**：判定使用 `policy.mode`（`ForwarderBase.routePolicy` 现读 accessor 的 `proxyMode`）+ `policy.access.checkRoute({ host })`，判定对象、server 模式短路（**不查名单、不带 reason**）、名单命中回落、真值表与 `[route]` 事件「过 preDial 每请求恰一条、server 模式零条」全部不变。请求路径仍禁止绕过该入口裸读配置；**upgrade 通道零 socks 早分支**，四个转发器一律经 `resolveForwardTargets` 出有效路由。
- 本节 Gotchas：显式 config **只决定「读哪份 store」**；runtime accessor 对 runtime 相位字段现读 live store，对 startup 字段读 runtime 构造时冻结值。`UPSTREAM_URL` 也属于 startup，loadConfig/纯内存 runtime 必须共用校验/拆项入口。`readJsonCached` 仍 1s 节流，ACL 编译结果按 `WeakMap<ConfigAccessor, CompiledAcl>` 隔离；相对路径在进入缓存前绝对化，只有 `ENOENT`/`ENOTDIR`/非普通文件算 missing，`EACCES` 等其它 stat 错误保留上一份有效值并发 error。`https.ts`/`TlsSocksProxy` 的 `loadCerts(this.options.tls, this.log, protocol)` 保持显式，不回落到 accessor 读取。回归护栏：`tests/unit/config-access.test.ts`（无全局、实例隔离、热改现读、`ProxyOptions`/identity/route 显式绑定）、`tests/unit/proxy-helpers.test.ts`、`tests/unit/self-loop.test.ts`（自环归一与 ACL 名单归一同一份实现）、`tests/unit/log-events.test.ts`（事件码与文本格式）、`tests/unit/identity.test.ts`、`tests/unit/base-lifecycle.test.ts`、`integration/tls-client-auth.test.ts`（显式 logger + 握手告警直写注入实例）、`tests/unit/access-control-port.test.ts`（三个旧导出函数在 `core/` 的直接调用点恰好 0 个）。

## 管道事件判别联合（`PipeEvent`）

- `PipeEvent` 是以 `type` 为字面量判别键的 14 变体判别联合：每个变体只暴露已声明字段，**不带索引签名**；生产者与消费者必须按同一契约演进，**禁止** `Record<string, unknown>` 式任意字段。
- 生产者为 `src/core/forward/**`、`src/core/guard.ts` 等 core 事实产生方。**唯一的出口是逐请求的 `RequestScope.emit`**（`ForwarderBase` 零 `emit` 实例字段、`PipeEventSink` 在 `core/forward/**` 与 `core/server/**` 里零出现）：`createRequestScope` 造的闭包把身份维度贴进载荷与 context 后**直接** `ctx.events.publish("pipe", …)`，`server/{http,socks-base}.ts` 只负责造 scope、不中转发布。`guard.ts` 侧的 `HelperEventSink` 仍在，但它的**类型**只是 `OpenContext.onEvent` 与 `guardDialing({ onEvent })` 的形参类型（channel 传进来的就是 `scope.emit`），不是「第二个事件槽」。消费者为 `src/runtime/event-log.ts:bindProxyEventLogs`（按 `type` 分支落盘，不做未知强转）与 `runtime/bridge.ts`（按 `type` 桥成公共事件），都不做未知强转。
- 变体清单：`PipeTargetUnresolvedEvent`（`target-unresolved`）、`PipeLoopDetectedEvent`（`loop-detected`）、`PipeRouteEvent`（`route`）、`PipeUpstreamRefusedEvent`（`upstream-refused`）、`PipeUpstreamErrorEvent`（`upstream-error`）、`PipeUpstreamTimeoutEvent`（`upstream-timeout`）、`PipeIpDeniedEvent`（`ip-denied`）、`PipeTargetDeniedEvent`（`target-denied`，**一个可选 `source`，类型是自由 `string`**——名单语义为 `global`/`user`，但端口对外之后判定实现可能不是名单而是限速 / 地理封锁，事件载荷要能装下它们的分层语义）、`PipeSocksEvent`（`socks`）、`PipeBadRequestEvent`（`bad-request`）、`PipeDialEvent`（`dial`）、`PipeEstablishedEvent`（`established`）、`PipeClientErrorEvent`（`client-error`）、`PipeDebugEvent`（`debug`）。**`source` 刻意不进 `PipeEventBase`**（那是 14 变体共享维度，`tests/unit/pipe-event.test.ts` 以 `toEqualTypeOf` 锁死其精确形状），它只属 `target-denied` 一个变体。
- **与 `LogEvent` 重名的 9 个判别键不另写字面量**：`types/proxy.ts` 以 `import type { LogEvent } from "../log-events.js"` 引入（**编译期擦除，零运行时边**；`log-events.ts` 不 import `types/proxy.ts`，故不成环），`type` 写成 `typeof LogEvent.TargetUnresolved` 等 9 处（`target-unresolved`/`loop-detected`/`upstream-refused`/`upstream-error`/`upstream-timeout`/`ip-denied`/`target-denied`/`bad-request`/`client-error`）。运行时字符串值一字未变；改码只动 `LogEvent` 一处。**两侧差集是事实差异，禁止补齐**：`client-timeout`/`tls-client-error` 只属握手/接入期日志（没有对应 pipe 事件），`route`/`socks`/`dial`/`established`/`debug` 是落盘不走的内部细节事件。
- `PipeRouteEvent.mode` 必填且限 `"server" | "client"`，`PipeRouteEvent.route` 必填且限 `"direct" | "upstream"`；`route` 事件与 runtime 层 `[route]` 日志行保持 1:1，不得删字段、改为可选或扩大为任意 `string`。
- 消费者覆盖全部 14 个 `case` 后须在 `default` 使用 `e satisfies never` 做穷尽性收口；新增变体时若遗漏消费分支，必须在编译期失败。
- `HelperEvent` 是 `PipeEvent` 的真子集，仅覆盖 `dial`、`established`、`upstream-timeout`、`upstream-error`、`client-error` 五个拨号守卫变体，可直接进入 pipe 事件槽，无须恢复索引签名或额外强转。
- 上述类型契约的回归护栏在 `tests/unit/pipe-event.test.ts`：固定 14 变体清单、route 必填字面量、公共可选维度、switch 收窄与穷尽性、HelperEvent 子集及无索引签名。

## 错误边界（`ErrorBoundary`）

- `error-boundary.ts` 是纯库错误基建：只做分类、生成安全消息，并可选经注入的 `EventHub` 发布 `request.failed` / `request.rejected` / `runtime.error`；不读环境或文件、不写协议、不打印日志，观察者异常不得改变分类结果或调用方控制流。
- 分类表：`DialTimeoutError` → `timeout` / `504` / expected；Node 网络错误码（如 `ECONNREFUSED`、`ENOTFOUND`、`EAI_AGAIN`、`ECONNRESET`、`EPIPE`、`EHOSTUNREACH`、`ENETUNREACH` 等）→ `upstream` / `502` / expected；`SyntaxError`/`URIError` 或明确的 bad request/协议解析语义 → `protocol` / `502` / expected；显式客户端入口 → `client` / `400` / expected；其余 → `internal` / `502` / unexpected。
- `statusForCause` 只表达拨号收尾的 504/502 分工：超时与其余错误的 502 语义必须复用 `classifyError`，不能让调用方在 catch 中再复制一套判断。
- 拒绝与失败分工：ACL、鉴权、解析等预期内拒绝走 `rejectRequest(reason, stage, status)`（400/403/407 等由协议调用方明确给出）；已发生但需归因的请求异常走 `failRequest(error, stage)`；运行时异常走 `failRuntime(error)`。`classifyError` 不猜测客户端 400。
- 分类结果的 `message` 取原始 `Error.message` 或 `String(error)`，复用 `core/helpers/headers` 的出站头剥离判据识别 `proxy-authorization`，并遮蔽 `authorization` / `cookie` 及 Basic/Bearer 形态后截断到 200 字符；原始值只保留在 `cause` 供调用方继续判断，不得直接展示。
- 错误边界已通过 `RequestTerminal` 接入 HTTP / SOCKS / WebSocket 的请求终态：协议入口只负责记录已经发生的 completed/rejected/failed，分类、脱敏与公共事件发布统一复用本模块；不得在协议 catch 中恢复分散的 502/504 判断。

## 请求作用域值对象（`request-scope.ts`）

- `RequestScope` = `{ emit(e: PipeEvent): void; terminal: RequestTerminal; user?; requestId?; connectionId? }`，**纯值对象 + 一个 emit 闭包**：无状态、无配置依赖、无日志、无 IO。工厂 `createRequestScope({ ctx, terminal, context?, user? })` 返回**冻结**对象（`terminal` 仍是同一个引用，互斥抢占语义对全链唯一）。
- **⚠️ 同名不同物，别 import 错**：本文件的 `createRequestScope` 造的是 `RequestScope`（core 内部用，**不进 `src/index.ts`**）；`core/events/scope.ts` 里还有一个**同名**的 `createRequestScope(runtimeId, requestId?, connectionId?)` 造的是 `EventScope`，**那个才是库入口 `src/index.ts` 导出的**。两者参数形态完全不同（一个收对象、一个收位置参数），类型上不会互相 assign，但同名足以让人读错文档就写错 import。core 内一律经 `@/core/request-scope.js` 直引（层内引用，无跨目录调用方）。
- **本对象存在的唯一理由**：给「易变的逐请求数据」一个只经参数逐次传入的载体，使它在类型层面就无法被误存到共享实例上。**不要**把它扩成「请求的全部上下文袋」——`context` 形参只放**这一条请求的关联事实**（`protocol` / `client` / `target` / 关联 id），身份维度由工厂从它派生后叠加。
- **关联 id 不走形参（同一个事实不许两个入口）**：`emit` 把 `identity` 合并进发布的 `context`，所以「id 在 `context` 里、却不算身份」是自相矛盾的形状。`RequestScopeOptions` 因此**只收 `{ ctx, terminal, context?, user? }`**，`identity` 里的 `requestId`/`connectionId` 从 `context.requestId`/`context.connectionId` 派生。SOCKS 那条事实（pipe 事件不带 id）因此表达为「`context` 里就没有这两个键」，而**不是**「忘了传形参」。护栏：`tests/unit/inbound-dispatch.test.ts`（调用点唯一 + 入参形状一致）与 `tests/unit/dead-optionality-cleared.test.ts`。
- **身份注入只在这一处发生**：`createRequestScope` 是**唯一**注入口（任何位置的第二个注入口都会把同一事实抄成两份）。四个转发器只管 `scope.emit(e)`。`unit/forwarder-request-path-allocation.test.ts` 断言 `emitWithUser` 在 `forward/` 与 `server/` 归零。
- `emit` 带 `createEventEmitter` 容错包装（观察面抛错不得反噬协议收尾），省略的身份维度**不写键**（而不是写 `undefined`）。
- **调用点只有一处：`server/admission.ts:createInboundAdmission` 里的 `scopeFor(user?)`**（全仓唯一）。两条入站路径都经 `admission.scopeFor(...)` 拿到作用域——`server/http.ts:handleForward`（每个 http/tunnel/upgrade 请求一条，`context` = `{protocol, client, target, requestId, connectionId}`）与 `server/socks-base.ts:sessionHost` 透传的 `scopeFor`（每会话一条，`context` = `{protocol}`；握手阶段不带 user，鉴权后带）。**别在 `server/**` 的别处再调 `createRequestScope`**，那是身份注入的第二个入口。
- 回归护栏：`tests/integration/forwarder-instance-reuse.test.ts`（实例复用 + 身份不串号，两侧都已用变异测试验证会真的变红）、`tests/unit/forwarder-request-path-allocation.test.ts`（请求路径零 `new`）。

## 请求作用域标识（`scope-ids.ts`）

- `connectionIdFor(socket)`：按连接对象缓存复用（`WeakMap`，socket 回收即释放），keep-alive 下同一 TCP 连接共享；`newRequestId()`：每请求一个 UUID。
- **注入点仅两处**：`core/server/http.ts:handleForward`（`connectionId` 来自 socket、`requestId` 每请求新建，同步注入 `RequestTerminal` 上下文 + 逐请求 pipe 事件槽 + `IdentityContext`）与 `core/server/socks-base.ts:onConn`（SOCKS 一连接一会话一请求，两者同值；经 `sessionHost` 的 `authorize` 包装注入）。
- **SOCKS 的 forwarder 是跨会话共享单例**，绝不在其上存会话态或闭包捕获 id（会串号）；id 一律经 `RequestScope`（每会话一条）/ `IdentityContext` 逐会话传递。**这条口头约定已由类型接管**：转发器入口签名里根本没有 `user` / `terminal` 形参，只有 `scope`。
- id 随**事件载荷**走（`PipeEventBase.requestId/connectionId`、`ProxyAuthEvent`、`IdentityContext`）：core **自己**把它们写进 `EventContext`（`request.started` / `auth.decided` / `pipe`），`runtime/bridge.ts` 只需从 pipe 载荷读出、补进它发布的 `access.*` / `route.selected`。使 `auth.decided` / `route.selected` / `request.started` 与 `request.completed` 终态可按 requestId 串联。缺失即不带（core 直构无入口注入时不臆造）。
- 回归护栏：`tests/unit/scope-ids.test.ts`、`tests/integration/request-scope-ids.test.ts`。

## 请求终态事件

- `request-terminal.ts:RequestTerminal` 是每个入站请求/连接的一次性终态守卫：`completed`、`rejected`、`failed` 首次 `claim` 成功后互斥且唯一；`complete` / `reject` / `fail` 在抢占后才发布，观察面异常不会反向改变协议收尾。
- **终态唯一来源原则**：每个请求终态**只由 `RequestTerminal` 抢占并发布一次**。`PipeEvent` 侧不得再单独为同一事实发一条公共拒绝/失败事件。典型：`target-unresolved` 的 `request.rejected(stage:"parse")/400` 由 `forward/channel/http.ts` 的 `requestTerminal.reject(...)` 发布，同一时刻发出的 `pipe: target-unresolved` **只服务日志面**（`[target-unresolved]` warn），`runtime/bridge.ts` 刻意不桥它（`RequestTerminal` 已是该事实的唯一发布方，桥它就是同一次拒绝发两条）。新增任何 pipe 变体前先确认它没有已由终态 publisher 覆盖的公共形状。
- **publisher 注册表按 accessor 隔离**：`registerRequestTerminalPublisher` / `createRequestTerminal` 走模块级 `WeakMap<ConfigAccessor, Map<protocol, publisher>>`，隔离**只**建立在「每个 runtime 派生自己的 accessor 对象」（`runtime/bridge.ts` 的 `bindRuntimeContext` 每次 `Object.freeze` 造新对象）这个隐含约定上；同 protocol 下后注册的会顶掉前一个，前者终态将静默消失。退订函数幂等且**不误删他人** publisher（`current?.get(protocol) !== publisher` 保护）。护栏在 `tests/unit/proxy-runtime.test.ts`（共享同一 context 的两个 runtime 各自持有自己的 publisher）。
- **`requestTerminals` WeakMap 的职责是跨事件通道，不是去重**：Node `clientError` 事件**只给 socket、拿不到 req**，`server/http.ts` 的 clientError handler 靠 `requestTerminalFor(socket)` 判断该连接上是否已有在途请求、有则复用其 guard（避免 malformed 拒绝与请求自身终态互相抢抢占），没有才新建一个专用于该次拒绝。请求自身不需要反查——id 与 guard 都由入口经参数逐层传递。
- runtime `CoreEventBridge` 按 `ConfigAccessor + protocol` 注册内部 publisher：`rejected` / `failed` 经 `ErrorBoundary` 发布到公共 `EventHub`，`completed` 直接使用既有 `request.completed` 契约；CLI 的 `pipe` 日志面不新增 core 事件。
- HTTP 接入点：`HttpProxy.handleForward` 的客户端名单/鉴权/入口异常与 `clientError`；`HttpForwarder` 的目标解析/目标名单、响应 `finish`、上游 error/timeout/提前 close；CONNECT 在 200 建隧、解析/名单和拨号失败收尾；Upgrade 在 101、非 101、状态行等待及拨号失败收尾。
- SOCKS 接入点：`SocksProxyBase.onConn` 的客户端名单（经 `admission.admitClientIp`）与连接异常；`socks-session` 的非法握手，以及**经 `admission.authenticate` 的凭证判定**（握手解析失败那类仍由 `socks-session` 自己结算终态——它们不是凭证判定）；`SocksForwarder.connect` 的目标校验/名单、建隧成功与上游失败。所有 SOCKS reply 仍由原 `replySuccess` / `replyFail` 写字节。
- HTTP 状态码、ServerResponse 早失败、SOCKS 二进制 reply、CONNECT 200、Upgrade 101 等既有判定与写报文逻辑不改；事件只在其旁边记录已经发生的终态。
- **`request.started` 是公共事件面**：`handleForward` 在准入三关全过、委派 forwarder 之前**直接发布 `request.started`**（不经 bridge），`data` 只带 `kind`（`http`/`tunnel`/`upgrade`），身份维度（含 `method`）走 context。**这是公共事件面唯一的非终态请求级事件**——`auth.decided` 要开了鉴权才有、`route.selected` 要 client 模式才有，所以在 **server 模式直连 + 关闭鉴权**这个最常见部署下，一次请求只剩终态，慢上游/长连接无法判断卡在哪一步。终态三件套是**结果**，`started` 是**过程**，缺过程的结果不可诊断。
- **`forward.request-headers` / `request.started` 的 `requestId` / `connectionId` 直接写进 `EventContext`**（core 直发，没有 `ProxyForwardEvent` 载荷承载）：`request.started` 据此与同请求的 `request.completed|rejected|failed` 串成一条链；core 直构（无入口注入）时缺失即不带，桥接器不臆造 id。注意 `request.started` 与终态事件的 `context.target` **同源于 `getAuthority(req)`**（非 CONNECT 只认 Host 头），absolute-form 请求下它是客户端写来的代理自身 authority；**真实目标要看 `route.selected` 的 context**（那是解析后的 dest）。
- `handleForward` **只把 terminal 关联到 socket，不关联 req**：Node `clientError` 只给 socket、拿不到 req，这是跨事件通道取回 guard 的唯一路径。req 不必关联——`RequestScope` 已携带 terminal，四个 forwarder 入口自己会再关联一次。
- 回归护栏：`tests/unit/request-terminal.test.ts` 锁定互斥语义；`tests/integration/request-terminal-events.test.ts` 通过真实 `ProxyRuntime` 验证 HTTP/SOCKS 的 completed/rejected/failed 生产与唯一性。
