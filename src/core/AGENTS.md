# src/core — 代理内核

`types/`（唯一类型源）→ `server/`（建服骨架）→ `forward/`（转发器）+ `auth.ts` / `guard.ts` / `access-control.ts` / `traffic/`（流量配额）/ `helpers/`（共享工具目录）+ `log-events.ts`（core 事实 → `[event-code]` 文本词汇层）。各文件头 `@fileoverview` 是第一手说明，本文件只收敛跨文件的约定与禁区。

**依赖方向单向**：`core/server → core/log-events → utils/logger`，core **不再反向依赖 `src/server`**（原 `server/log/events-log.ts` 已下沉为 `core/log-events.ts`，导出符号一字未改）。core 只允许 import `@/utils/*` 与 `@/config/*`；**禁止** import 任何 `@/server/*`。跨目录优先走层 barrel（`@/utils/{logger,constants,tls,json-file}/index.js`、`@/config/files/rules/index.js`、`@/core/helpers/index.js`）；`utils/ip.ts` 与 `utils/host-text.ts` 是单文件叶子、无 barrel，只能直接引。

**端口形状是裁决，不是实现细节**：
- `consume(user, dir, bytes)` **必须同步**。无锁的全部论证就是「一次 `consume` 从读到写没有 `await` 点，Node 单线程事件循环不可能在中间插入另一个 `consume`」。**若哪天把它改成 `async`（例如为了顺便把账本落盘），这条论证当场失效**，必须先补互斥。护栏：`tests/unit/traffic-account.test.ts` 的「consume 的同步性」**五条**（`consume` 返回的不是 Promise + 源码级 `零 async/零 await` + 连续调用的累计值单调精确 + **5b-1 追加的「零定时器/零微任务」** + **5b-2 追加的「挂了落盘账本之后仍是同步的、返回值仍不是 Promise、且落盘接线就写在 consume 路径上」**）。后两条是 5b-1/5b-2 给这条论证**加的约束**：窗口滚动的正确实现是「每次访问槽位时比对窗口键」，而「起个 `setInterval` 到点清账」这个直觉做法同时破坏两件事——① 引入让出点 → 无锁论证失效；② 让进程多一个要 `unref`/要摘的后台任务；落盘则只许在 `consume` 的**同步区间内**做一次数组 push（`sink?.record(...)`），IO 全在账本侧。护栏把「零定时器」钉成源码级事实，且 5b-2 起额外钉住「**全切片唯一的定时器站点是 `flush-loop.ts` 那一处 `setTimeout`**」（`ledger.ts`/`memory.ts` 零定时器）——定时器散进账本 IO 时那条断言就写不出来了。
- **超限必须在本次就返回 `allow:false`**，绝不允许「先放行、下次再说」。端口刻意**不**提供「先查后加」的两段式 API：两段式在并发下必然留窗口。
- 判定顺序 `bytesUp` → `bytesDown` → `bytesTotal`，**任一突破即拒**。推论是「配额耗尽 = **账号级封禁**」：撞了 `bytesUp` 之后该用户的 `down` 方向同样被拒（否则可以上传撞顶后改走下载继续白嫖）。代价是硬切后该账号在**当前窗口内**彻底不可用（跨过窗口边界自动恢复，见「窗口化」）。
- **恰好等于上限放行**（`<=` 语义，判据是「累计 **>** 上限才拒」）。`bytesTotal: 100` 允许用满 100 字节：配额是**上限**而不是「额度 + 1 的坑」，写成 1GiB 的运维最难受的就是「差一个字节传不完」。
- `usage` 与 `limit` **恒取同一 scope 的两个数**（`total` 被突破时 `usage` 是总量），消费方才算得出「超了多少」。
- `dir` 与 `scope` **可以不同**（本次流动 `down`、被突破的是 `up`）：方向由挂点如实上报，**绝不从 `scope` 反推**（撞 `total` 时两个方向都可能，反推有一半是假的，而 `dir` 是事件载荷必填项——假的比没有更糟）。故 `QuotaExceededHandler` 收 `(dir, verdict)` 两个参数。
- **未配 / 全 0 / 用户不存在 → 恒 allow**（**显式分支**，不是「默认上限 0 恰好放行」）。但**未配也照常累加 usage**：「没有上限」≠「不计量」，这样 `usage` 恒为真用量，将来加上限即刻按真账判定。唯一「不计量」的情形是**没有身份**。
- 已知限制（写在文件头免得被当成没想过）：账本是**纯内存无淘汰**的 `Map`。`users.json` 固定规模时天然有界，但 `authType=jwt` 的 `sub` 理论上可无限增长。**5b-2 的落盘压缩解决了这条限制的「持久」那一半，并如实记录没解决的那一半**：
  - **已解决**：落盘账本在**压缩**时按 `(用户, 窗口键)` 求和并**丢弃已过期窗口的条目**（`ledger.ts:compactEntries`），所以「28 个 `sub` 跨 28 天」在压缩后文件行数降到 0，重启恢复时这些过期槽位**根本不会回到内存**。也就是**磁盘上那一份（唯一会无界增长的那一份）现在是有界的**（阈值 8MiB）。
  - **未解决**：**同一个长跑进程内**的内存 `Map` 仍不淘汰（本文件零 `.delete(` 仍是护栏）。彻底解决需要重启一次进程 —— 这是自觉的取舍：进程内淘汰必须先定义「被淘汰的用户拿到一份清零的账 = 凭空多出一份额度」的语义，而那属于配额窗口的设计。
  **5a 记下的那条「处理窗口是 5b-2 的落盘压缩」到此结清**（护栏断言原文见 `tests/unit/traffic-window.test.ts`：文件头必须含 `jwt` 与 `5b-2` 两个词——文档也是契约的一部分）。
- 本切片**刻意不加** LRU 之类猜测性淘汰：淘汰策略必须与配额窗口一起设计，否则会出现「配额还没过期、账本先被淘汰」这种更糟的行为（被淘汰的用户拿到一份清零的账 = 凭空多出一份额度）。护栏把这条决策钉成源码级事实：`tests/unit/traffic-window.test.ts` 断言 `memory.ts` **零 `.delete(`、零 LRU/容量上限字样**；5b-2 的 `tests/unit/traffic-ledger.test.ts` 把同一条负向断言**扩展到 `ledger.ts`/`flush-loop.ts`**（账本里也不许有 LRU）——谁想加淘汰，必须先改那条护栏并说明淘汰语义。

**窗口化（Phase 5b-1）：每用户槽位带 `windowKey`，滚动即清账**

5a 的槽位是 `{up, down}`，用量**只增不减**（那时窗口语义还没定，先把「真用量」做对）。5b-1 变成 `{windowKey, up, down}`，并在**每次访问槽位时**（`consume` 与 `usage` 共用私有 `slotFor`）比对当前窗口键——**不同即用量清零并换键**。三条不变量：
- **惰性滚动，零定时器**：不引入任何 `setTimeout`/`setInterval`/`setImmediate`/`nextTick`/`queueMicrotask`。理由有两条，各自独立成立：① 定时器必然引入让出点 → **当场作废上面那条无锁论证**；② 账本是纯内存的，而 `consume` 是同步函数，「到点就清」在同步函数里只能靠后台任务，于是凭空多出一个要 `unref`、要摘、要处理停机的对象。真实需求只是「**跨过边界后别拿旧账当新账**」，而这在每次访问槽位时判一次就完备——没人访问的槽位清不清账**语义上不可观测**（`usage` 一读就现算）。护栏：上面「consume 的同步性」第四/第五条（源码级零定时器，且**全切片的唯一定时器站点是 `flush-loop.ts` 那一处**——落盘定时器在账本侧，不在滚动侧）。
- **已用量绝不跨窗口继承**（裁决）：继承等于白送「等窗口翻页」的重叠额度——卡在边界前用满的用户，等窗口一翻又能用满一份，配额立刻失去意义。故跨窗一律清零，**上一窗口的耗尽状态也随新窗口解除**（新窗口给完整额度）。**已用变异测试验证**：把清零改成「继承旧值」→ `traffic-window.test.ts` 8 条红。
- **清账 ≠ 除名**：跨窗只**替换**槽位，**从不删除**。删了就等于「清账」变成「除名」，而且「反复读一个未知用户」会变成无限增长。对称的一条：`usage` 对**从未计量过**的用户直接返回零值、**不建槽**（读一次不该凭空长出槽位）。

**落盘账本（Phase 5b-2）：`ledger.ts` + `flush-loop.ts`，两条铁律各自独立成立**

**铁律一：`consume` 仍同步，落盘完全异步。** 内存账本通过 `bindSink(sink)` 挂上 `JsonlTrafficLedger` 后，`consume` 只多一行 `this.sink?.record(user, dir, bytes, now)` —— **纯数组 push**（`TrafficSink.record` 是同步端口，无 Promise/无 IO）。真正的写盘在账本自己的后台 flush 里。三条性质因此全部保持：① `consume` 仍是**同步函数**（上面那条无锁论证分毫未动）；② `consume` 的**耗时与磁盘无关**（磁盘满/目录不可写都不影响判定与放行）；③ `consume` **绝不因账本失败而抛错**。`consume` 里**时刻只取一次**（`const now = this.clock()`）并同时喂给 `slotFor` 与 `record` —— 窗口键与落盘 `ts` 必须同源，否则同一批字节会被判定分到窗口 A、却按窗口 B 落盘（重启恢复后用量就错了）。

**铁律二：`src/core/**` 与 `src/runtime/**` 一律不许读 `process.env`，槽位是显式参数。** 传递链是 `cli.ts` 的 env 快照 → `runServer(…, workerSlot)` → `ProxyServer.trafficWorkerSlot` → `createProxyRuntime({ trafficWorkerSlot })` → `runtime/services.ts:buildDefaultServices` → `JsonlTrafficLedger`。理由与其它配置端口同源，但在这里**更硬**：槽位**会被拼进账本文件名**，一次「猜来源」就是一次「写错文件 / 读别人的账」。env 名 `PROXY_WORKER_SLOT` 的**唯一写入方**是 `server/cluster.ts` 的 fork（`core → server` 是被禁方向，所以这一环天然在 core 之外），且它**刻意不进 `FIELDS`**（它不是配置项，见 `src/config/AGENTS.md`）。护栏：`tests/unit/traffic-ledger.test.ts` 的「core/** 与 runtime/** 零 process.env」**逐文件扫全文**。

**槽位必须是稳定序号，不能用 PID**：每次重启换文件名的话，旧文件再无人问津，「持久化」等于「每次都从零开始」——那比不落盘更坏，因为运维会以为配了持久化。cluster 派发 `1..N`，进程退出时释放（重启复用同一个号，账本接得上）；单进程/库模式恒为 `"0"`。`normalizeSlot` 只认 `1..9999` 纯数字，其余（含 `../../evil`）一律按**路径穿越面**拒绝、回落 `"0"`。

**本轮明确否决的四个方向（文档里出现即为错，除非同时改掉对应的负向护栏）**：
- **禁限速 / 速率整形**：只能到 chunk 粒度（TLS record ~16KB），低限速值要靠延迟换平滑；且整形必然要 `pause()`/`resume()`，会与 `guardDialing` 的半关闭联动形成第三层流控。护栏：`tests/unit/user-quota.test.ts` 显式断言 `rateBps`/`rate` 被判非法、`tests/unit/traffic-ledger.test.ts` 断言源码零速率字段。
- **禁每用户最大并发连接数**：那是「连接数配额」不是「流量配额」，与窗口/字节两条轴都正交；真要做必须先定义「并发数按哪个窗口重置」。护栏同上（`maxConnections`/`concurrency` 被判非法）。
- **禁滚动时间窗**：理由（解释成本 / 聚合成本 / 不预留占位值）写在「窗口化」小节与 `window.ts` 文件头。护栏：`tests/unit/user-quota.test.ts` 断言 `week`/`hour`/`rolling` 整组非法。
- **禁跨 worker 共享账本**：每个 worker 写自己那份 `worker-<slot>.jsonl`，**没有**中心聚合、没有文件锁、没有 IPC 汇总。代价是「同一用户被分到两个 worker 时额度各算各的」——`cluster.fork()` 的负载分配不保证粘性，理论上可被绕开一点额度；接受它换来的是「账本 IO 完全不跨进程协调」这个简单得多的模型。真要共享必须先引入跨进程互斥，那与「`consume` 同步无锁」那条论证直接冲突。护栏：`tests/unit/traffic-ledger.test.ts` 的 slot 隔离档（两个 slot 写两个文件、互不污染）。

**格式：`<quotaLedgerDir>/worker-<slot>.jsonl`，一行一条 delta `{ ts, u, d, b }`，只写增量绝不写绝对值。** 绝对值一律在**读取时按 `(用户, 窗口键)` 求和**——写绝对值等于让「谁最后写」成为唯一真相（两次 flush 交错就互相覆盖，且崩溃后残留的绝对值无法与已追加的增量对账）。坏行**跳过而不是抛错**：一行脏数据让整本账打不开 = 配额整体失效，跳过只丢那一行的额度。

**两个压缩安全点**（Windows 上 `EPERM` 的经典来源：不允许 rename 覆盖一个仍打开的文件）。压缩流程被钉死为 `flush → close 句柄 → 读全量求和 → 写 .tmp → fs.rename → 重开句柄`，触发点是 ① **启动时**（`open()` 里读完立刻压，此时**还没有句柄**）② **运行期按文件大小阈值**（默认 8MiB，在同一轮 flush 内做完）。全程无并发压缩：Node 单线程 + `flush()` 走一条 **Promise 链**串行化。**「关句柄」这条真实踩过**：曾经 `open()` 在压缩之后又开了一次 append 句柄，泄漏的那个句柄让后续任何 `rename` 覆盖本文件直接 `EPERM`，表现是「压缩静默不生效、文件一字不变」——`compact(reopen: boolean)` 的参数就是为它留的。

**压缩是幂等的**，做法是**保留幸存条目里的最大 `ts`**（不是压缩时刻）：`ts` 必须落在该窗口内，重压才算出同一个键 → 两次压缩逐字节相同。若写成「压缩时刻」，两次压缩间隔只要跨过窗口边界就产出不同内容，幂等那条护栏也就测不出东西了。**`compactedAt` 门槛**保证「已经压不动的账本」不被反复全量重写（判据用 `rename` 次数而不是文件内容——幂等压缩产出同样的字节，看内容区分不出）。

**崩溃安全 = `.tmp` + `rename`**：崩溃点只有两种（`.tmp` 写了一半 → rename 未发生 → 原文件完好；rename 已完成 → `.tmp` 已消失），中间不存在「原文件被截断成半个」的态。本模块**从不读** `.tmp`（所以残留的临时文件**不可能污染原文件**），启动时顺手 best-effort 删掉它。

**压缩丢弃已过期窗口的条目**（`compactEntries`）与**恢复只认当前窗口**（`summarizeCurrent`）**必须用同一条判据**（同一个 `windowKey` 比较），否则会出现「恢复算进来的量比压缩保留的量多」。两条刻意不合并成一份带副作用的函数：一条产出恢复结果、一条产出可写回文件的条目，但对「什么算过期」必须有同一个定义。

**写盘失败韧性**（`EACCES`/`ENOSPC`/…）的正确形态只有一种：**内存计数继续 + 未落盘 delta 累积留待下次重试 + 一条可见事实**。整批 delta 放回队首（`concat` 而非 `unshift(...batch)`，大批次上展开调用会打爆调用栈），事件是公共的 **`traffic.ledger-error`**（`{ path, error }`，与 `config.file-error` 同形：同一类事实），CLI 落一条 `[quota-ledger-error]` **error** 级日志。**「直接失败」与「静默重试」都更坏**：前者等于「磁盘满 → 代理全挂」（配额是增强功能，不该有能力打垮数据面），后者让运维以为配额持久化了、几天后重启才发现用量全丢（比不落盘更坏，因为那是**被误导**的降级）。日志文案里必须写明「**不要为此重启**」——重启会把队列里未落盘的增量一起丢掉。**重试可能重复计一次账**，这是刻意选的**安全方向**：多算 = 少用一点额度（等下个窗口即可），少算 = 白拿额度。压缩会把重复行求和收敛回正确值。

**零成本档**：`enabled()`（= 注入的 `hasConfiguredQuota`：**没有任何用户配了非全 0 的 `quota`**）为 false 时 `open()` 在 **`mkdir` 之前**立刻返回 —— **不建目录、不开句柄、不起定时器、不注册任何 fs 事件**，`record()` 也全程 no-op（否则「没配配额」反而吃内存）。判据是**文件事实**而不是配置猜测，且与 `runtime.start()` 里 `quota-inert` 告警**共用同一个函数**（两处各写一份，迟早出现「告警说没配、账本说配了」）。护栏断言的是**「目录不存在」**（不是「建了但空」）——那才是可观测的硬证据。

**端口为什么拆成 `TrafficSink` 与 `TrafficLedgerController` 两个**：两个调用方、两种失败代价。`record` 由 `consume` 在**同步区间内**调用（每 chunk 一次），抛错就等于把「写盘失败」变成「转发失败」，所以必须是最小同步面；`open`/`close` 只在 `runtime.start/stop` 各调一次，**允许 Promise**。合在一个接口上最容易顺手让 `record` 也返回 Promise——那正是 5b-1 明确禁止的方向。同理 `seed(restored)` / `bindSink(sink)` 刻意**不进 `TrafficAccount` 端口**（同 `size` 的理由：端口是「用量与判定」的契约，落盘位置与规模诊断是装配决策）。

**窗口键夹取（5b-2）**：`clampShiftHours` 把 `shiftHours` 夹到 `[0,23]`，非有限值夹 0。`quotaResetHour` 在配置层已被 FIELDS 校验，但**库调用方可以绕过 `loadConfig`**（`createProxyRuntime({ config })` 走 `ConfigStore`，而 `ConfigStore` **零校验**），所以「配置层保证 0..23」对库路径**不成立**。不夹取的代价是具体的：畸形键会进恢复结果的 `windowKey` 并参与判定。夹到定义域的后果只是「按最近的一个合法边界算窗口」——位置错了但形状仍是合法键，账本里看到的是 `2026-03-15` 而不是一眼就知道坏掉的 `NaN-NaN-NaN`。`flush-loop.ts` 的间隔下限夹 1 同理（0/负数会变成 `setTimeout(fn, 0)` 的忙循环 = 纯 CPU 挂死）。

**事件**：新增公共契约 **`traffic.ledger-error`**（`AppEventMap`），载荷 `{ path, error }`（`path` 是账本文件，`error` 是原始异常，消费方据此区分 `EACCES` 与 `ENOSPC`）。生产点是 `JsonlTrafficLedger.report`（经 `runtime/services.ts` 注入的 `onLedgerError` 闭包）→ `runtime.ts` 只 `publish`，**不落日志**（日志是 CLI 面，`src/server/index.ts:bindProxyEventLogs` 订阅这条事件落 error 行；库调用方订阅不到就什么也不输出，与「日志落盘归 server 层」同纪律）。

**窗口键语义**（`traffic/window.ts` 是第一手说明）：
- `QuotaWindow` 只有 `day` / `month` 两个**日历窗**字面量，缺省 `month`（`DEFAULT_QUOTA_WINDOW`，由 `quotaWindow()` 归一——**归一在消费侧不在配置侧**，理由见 `src/config/AGENTS.md`）。磁盘上写其它值（`"week"`/`"hour"`/`"rolling"`/大小写变体/非字符串）由 `config/files/users.ts` 判**整组非法 → 启动期 abort**；**为什么不做滚动窗**（解释成本、聚合成本、不预留占位值）写在 `window.ts` 文件头。
- `windowKey(nowMs, window, shiftHours)`：先**减 `shiftHours` 小时再取本地日历字段**。故 `resetHour=3` 时当天 `01:00` 仍属**前一天**窗口、`03:00` 才是新窗口第一刻。`day` → `YYYY-MM-DD`，`month` → `YYYY-MM`（本地时区字段，**不是 `toISOString()`** —— 配额是运维所在时区的日历概念）。
- **「减毫秒再读字段」而不是手工日历进位**：闰年/月末/跨年的进位是这类代码的事故源，交给 `Date` 的本地字段就没有特例可漏。
- **DST 边界是近似（刻意接受并记录）**：夏令时让某一小时在本地重复或消失，窗口切换点因此最多偏移 1 小时。为「每天早上大致清零」引入一整条时区规则链不值得。护栏按这个取舍断言而非按「精确午夜」断言：逐小时走 48 小时（必覆盖任何一次切换），切换点必落在本地午夜 ±1h 内。
- `now` **必须可注入**（`TrafficWindowSource.now?`，缺省墙钟）：窗口边界是最容易写错的地方，靠真实时钟只能写出「今天大概对」这种测不出回归的用例。生产路径**不需要**注入它（账本只用它算键，滚动是惰性的），故做成可选。`shiftHours` 的 `0..23` **在本层夹取**（`clampShiftHours`，5b-2 起）——理由见上面「窗口键夹取」一节：库路径的 `ConfigStore` 零校验，配置层那条前置条件对库调用方**不成立**，而畸形键会一路进落盘账本并参与恢复判定。

**计量落点是唯一正确的那个**（`meter.ts` 文件头是完整的第一手说明，这里只列结论）：
- **被动计数**：在**源流**上挂一个 `data` 监听器，只读 `chunk.length`。**不插 Transform、不改 pipe 结构、不用 pause/resume 整形**。理由：插 Transform 就得配背压，背压必然要 `pause()`/`resume()`，会立刻改变 `guardDialing` 半关闭联动的时序，把一条已验证的收尾语义变成要重新验证的东西。护栏：源码级断言 `meter.ts` 零 `Transform`/`pause(`/`resume(`/`push(`/`pipe(`，且 `on("data")` **恰好一处**。
- 三个挂点（`base.ts:ForwarderBase`）：`openTunnelMeter`（隧道/SOCKS/WebSocket 复用，`up` 挂客户端流、`down` 挂上游流）+ `openHttpQuotaGate` + 两处 `meterStream`（HTTP：`up` 挂 **`req`**、`down` 挂 **`upRes``）。**HTTP 的 `up` 绝不能挂 `req.socket`**：入站 socket 被 keep-alive 的多个请求共享，在它上面计数就是账本串号（变异测试验证：改挂 `req.socket` → 3 条红）。
- **建链协议字节天然不计入**：`CONNECT` 请求行/请求头被 Node 的 HTTP 解析器摘走（我们是在解析器摘完之后才挂监听器）、`200`/`101` 应答由**我们** `write()` 出去（出站不产生本流 `data` 事件）、SOCKS 握手由 `SocksHandshakeReader` 逐段读走并在 `detach()` 里 pause。
- **首批载荷要计入**（`head` / `rest` / SOCKS 流水线余量）：它们不经 `data` 事件，由 `bridgeWithBuffered` / `upgradeOver` 经 `meter.charge(dir, n)` 显式补记；判定不通过就**不写**（写进已销毁的 socket 会抛 `ERR_STREAM_DESTROYED`）。护栏：CONNECT 请求头与载荷**同一次写**（载荷进 `head`）那条用例——变异测试验证：临时去掉 `head` 补记 → 该条立刻变红。

**已知不对称（诚实记录，不假装两侧对称）**：
- **隧道 / SOCKS / WebSocket 走裸 socket**：客户端首包与响应余量都经过 socket，加上 `data` 计数与首批补记，**两个方向都精确**（实测 4096B 载荷 → `usage = {up:4096, down:4096}` 逐字节相等）。
- **HTTP 普通转发**：`IncomingMessage` 流**只覆盖消息体**——请求行+请求头、状态行+响应头都是 Node 直接写进 socket 的，不经过请求/响应对象。故 HTTP 路径**两个方向各少算一个 HTTP 头**：`up` 少算请求行+请求头（实测典型 GET/POST 约 90–200B），`down` 少算状态行+响应头（实测典型 200 约 60–150B）。**不要为了「补齐」去在 core 里合成 Node 已经写出去的字节**——那就不是被动计量了。护栏按「显式说明的误差」断言：HTTP 路径断言的是**消息体字节数逐字节相等**，头字节的差额写在本文件与 `meter.ts` 里。

**耗尽语义（裁决，不许软化）**：**硬切**。不给「用尽后只拒新请求、已有连接放着」——一条长连接隧道能永远不触发耗尽判定，配额就成了摆设。
- **HTTP 转发**：`res.headersSent` 为假 → 回 **507 Insufficient Storage**（`@/utils/constants` 的 `STATUS_INSUFFICIENT_STORAGE`/`REASON_INSUFFICIENT_STORAGE`；**不是 403**——配额耗尽不是权限问题，403 会诱导客户端换凭证/换身份重试，而重试对「用完了」毫无意义）；已发出 → `destroy()`。**`down` 方向实际总是走 destroy 分支**（响应体只在 `writeHead` 之后流动，那时 `headersSent` 必为 true），**507 分支由 `up` 方向承载**（请求体撞顶时响应还没开始）——两条分支都要有。
- **隧道 / SOCKS / WebSocket**：应答早已发出（`200` / SOCKS reply / `101`），**改不了** → 双端 `destroy()`。
- **「恰好一次」由闭锁保证**（`openTunnelMeter` / `openHttpQuotaGate` 各自的 `fired` 标志）。HTTP 两个方向**共用同一个闭锁**：否则 `up` 撞顶恰好与 `down` 首个 chunk 落在同一轮事件循环时会发两条。socket 被 destroy 后本不会再有事件，但闭锁让这件事**不依赖时序**。
- **状态行不保证到达客户端**：`res.destroy()` 直接销毁 socket，尚在写缓冲里的应答头会一起丢掉，客户端可能看到 200、也可能只看到 ECONNRESET。两者都是「硬切」的正确表现。**不要**为了「让状态行一定送到」改成 `setImmediate` 延迟 destroy——那会在延迟窗口里漏掉本该被拒的字节，硬切就不硬了。

**无鉴权 → 配额整体不生效**（产品决策）：没有身份就没有归属，故 `meterStream` 在 `user === undefined` 时**一个监听器都不挂**（关鉴权的部署零开销），启动时若账号表里真有非全 0 的配额则打一条 `[quota-inert]` warn（文案 `core/log-events.ts:QUOTA_INERT_DETAIL`，**判据是文件事实而非配置猜测**——关鉴权本身是常态，没配配额时告警纯属噪音）。护栏那条断言「`consume` 一次都不许被调」而不是「usage 恒零」：后者区分不出「没调」与「调了但查不到配额」。

**服务装配**：`ProxyOptions.traffic?: TrafficAccount` **可注入**、缺省 = **显式禁用档**（`inertTrafficAccount()`，与本文件既有的 `auth ?? new Auth({enabled:false})` 先例**完全同构**，归一只发生在 `BaseProxy` 构造期**一处**）。**真正的默认实现（读 users.json 的内存账本）只在唯一组装根 `createProxyRuntime` 解析**（`runtime/services.ts:buildDefaultServices`），并经 `services.traffic` 落到 `ProxyOptions.traffic`——所以库调用方注入的替身一定原样生效。**窗口口径也只在那里注入**（5b-1）：`TrafficWindowSource.resetHour` 是经同一 accessor 的**闭包**（每次访问现读 `quotaResetHour`，故热改立即生效）、`now` 不注入（账本只用它算窗口键且滚动是惰性的，缺省墙钟）。**落盘副本也只在那里注入，且与默认内存账本同生共死**（5b-2）：调用方**显式注入** `services.traffic` 时 `services.trafficLedger` 恒为 `undefined`（那一本账归调用方管，我们不写它的文件、不给它起定时器）。**账本本身零配置依赖**：它不读 `ConfigAccessor`、不读 `process.env`，目录/间隔/窗口/「有没有配额」全部由装配点以闭包注入（`slot` 是显式的**字符串**）——与 5a/5b-1 的「core 零配置依赖」同一条纪律。**四个转发器必须共享同一个账本实例**（各建各的等于没配配额），故它们构造时都收 `ctx` + `traffic` 两个**必填**参数，由 `HttpProxy` 构造函数 / `SocksProxyBase` 字段初始化器从 `this.traffic` 传入（`forwarder-request-path-allocation.test.ts` 的「恰好 4 个构造点」静态计数不受影响）。

**身份铁律同样适用**：`traffic` 是**进程级**服务、可以存字段；`user` **绝不**——它逐请求产生，只在 `openTunnelMeter` / `openHttpQuotaGate` 的闭包里活一次。

**事件**：新增公共契约 **`traffic.quota-exceeded`**（`AppEventMap`），载荷 `{ user, dir, scope, usage, limit }`（`user` **必填**：无身份即不计量，这条事件不可能出现在无鉴权部署上；写成可选就等于允许消费方回答「配额是谁的」这个答不出来的问题）。生产点唯一：`base.ts:ForwarderBase.publishQuotaExceeded`，**直接发公共事件而不走 `pipe`**——刻意**不**给 `PipeEvent` 判别联合加第 15 个变体（那会让 14 变体的穷尽清单与两处既有测试同时要改，而这条事实本来就不需要「管道上下文」）。`EventContext` 恒带 `user`，其余关联维度取自 `scope.terminal.snapshotContext()`（协议入口已算好的同一份事实，重算会出现「同一请求两个 id 口径」）。落盘 `[quota-exceeded]` warn 行在 `src/server/index.ts:bindProxyEventLogs`（与 `[target-denied]` 同一面），文案「`<user> 配额耗尽 dir=<up|down> scope=<up|down|total> usage=<n> limit=<n>`」。**5b-2 追加的第二个公共事件 `traffic.ledger-error`**（`{ path, error }`）与它的落盘面见上面「落盘账本」一节。

## 依赖承载体（`context.ts`）

- `CoreContext` = 三件套的只读接口（`config: ConfigAccessor` / `logger: Logger` / `events: EventHub`），三项**全必填、无可选标记**；全部 type-only 引 `@/config/index.js`、`@/utils/logger/index.js`、`@/core/events/index.js`，编译期擦除、零运行期依赖边。**本文件刻意零兜底**：不出现 `createNoopLogger()` / `new EventHub()` / 任何 `??`，依赖缺失的兜底只允许发生在唯一组装根 `createProxyRuntime()`——在承载体里兜底会把「忘注入」变成静默的运行期怪问题。
- `ContextualBase`（`constructor(protected readonly ctx: CoreContext)`）只把 `ctx` 投影成 `config` / `log` / `events` 三个 **protected getter**，零副作用：不订阅事件、不读配置、不打日志、不碰 `process`/文件。getter 名字是契约：子类要换名字就得写转发，那这套 getter 就白存在了。
- **接线已落地**：`ProxyOptions` 的散装 `config` / `logger?` 两字段已删除，合并为**单个必填 `ctx: CoreContext`**（三件套一次性整体注入，core 内零缺省解析）。`ForwarderBase` / `Dialer` / **`BaseProxy`** 都已 `extends ContextualBase` 并删掉自己的 `config` 字段或投影 getter（`this.config` / `this.log` / `this.events` 统一走继承 getter，13 处 `Dialer` 读取、全部 `ForwarderBase` 读取与 `BaseProxy` 内的调用点一字未改）；四个转发器（http/tunnel/upgrade/socks）的构造参数随之收敛为 **`(ctx: CoreContext, traffic: TrafficAccount)` 两个必填**（事件槽已在 Phase 3 下沉到 `RequestScope`，故不再收 `PipeEventSink`；见下方「构造签名」条），**三个函数式入口 `forwardHttp/forwardTunnel/forwardUpgrade` 已整体删除**。**Phase 1.3b 已把 `BaseProxy` 从 `extends EventEmitter<ProxyEventMap>` 切到 `extends ContextualBase`**，那三个「临时形态」投影 getter 随之删除——`ProxyOptions.ctx` 与 `ContextualBase` 的 `this.ctx` 是**同一个对象**（`super(options.ctx)` 原样透传），语义零变化，且不再有「子类实例字段遮蔽继承 accessor」的隐患。构造顺序：TS 要求 `super()` 先执行，故 ctx 先落基类、再归一 `this.options`；`ContextualBase` 构造只做一次字段赋值（零副作用），构造期内没有任何代码读 `this.config`/`this.log`/`this.events`，不存在「读早于赋值」。
- **`core/index.ts` 刻意不导出本文件**：core 现有惯例是按扁平路径直接引用（`@/core/auth.js`、`@/core/access-control.js`、`@/core/events/index.js`），`core/index.ts` 本就是选择性出口（连 `access-control`/`error-boundary`/`request-terminal` 都不在其中），库入口 `src/index.ts` 也不经它。不要为了导出而导出。

配置类需求**不要**放进 core：`config/files/acl.ts` 只管读名单，请求期判定归 `core/access-control.ts`，配置契约/来源/归一化归 `src/config/`。

## 鉴权（`auth.ts`）

- 账号住在 `AUTH_USERS_FILE`（`cfg/users.json`），**不在** env。`createAuthFromConfig(config)` 的 config 为必填 `ConfigAccessor`；它每请求经该 accessor 现读 live store + 账号文件（热加载），改 runtime 配置下次请求即生效。
- `basic` 命中任一账号的用户名+密码；`uid` 只比用户名；`jwt` 用户名取 token 的 `sub/username/user/uid/id`。凭证索引住在 `helpers/credentials.ts`（`buildCredentialIndexes` / `credentialIndexesFor` 单槽记忆 / `matchBasicCredential` / `matchUidCredential`，`Auth` 只做薄委托，保证出站头剥离与鉴权用同一判据），结果带回 `username` 供逐连接日志。
- 失败闭环：账号形状非法 abort 启动（`validateAuthUsers`）；`authEnabled + basic|uid + 空表` abort（`assertAuthConfig`，见 `src/config/AGENTS.md`）；`authenticate()` 内异常一律 deny（`BaseProxy.authorize()` 捕获）。
- Token：`Proxy-Authorization` 优先、`Authorization` 回退（RFC 7235，scheme 大小写不敏感）。
- 凭证防泄漏：`isProxyCredentialValue()` 命中代理自身凭证时，`sanitizeHeaders` / Upgrade 报文必须剥掉该 `Authorization`；其余 `Authorization`（如目标 `Bearer`）原样转发。basic/uid 走**整份账号表**比对；**jwt 也参与出站剥离**——剥 scheme 前缀后按 `isJwtShape` + `verifyHs256Jwt`（内置 HS256 + `JWT_SECRET`）验签判定，不依赖账号表（jwt 允许空表，该分支必须先于空表早退）。判据唯一收口在 `isStrippableOutboundHeader`（任意 `proxy-` 前缀 + 凭证形态）。已知边界：自定义注入的 `jwtVerify` 不被剥离判据感知（只认内置 HS256；生产默认注入内置校验器），方向仍是「宁可多剥不泄漏」。
- JWT：默认注入内置 HS256 校验 `defaultJwtVerify`（薄 async 包装 `proxy-helpers:verifyHs256Jwt`，`node:crypto` 零依赖：验签 + `exp`，永不抛，与出站剥离共用同一实现）；显式注入优先；直构 `Auth` 未注入即 deny（审计照打）。
- `basic` 在 socks4/sockss4 额外接受 `USERID == username`（无密码字段）。
- 审计 `tag` 为 `"tunnel"` 仅当 `method === "CONNECT"` / `socks*` 协议 —— 不许用 `authority.includes(":")` 判定。`Auth` 零日志，审计经 `onAuthEvent` → `BaseProxy.authorize` 直发 `auth.decided`（`tag` 在 data、身份维度在 context）→ server 层落盘。
- SOCKS 鉴权发生在握手后：socks5/sockss5 走 RFC1929 user/pass（auth 启用时），socks4/sockss4 用 USERID。

## 转发器（`forward/`：**按两条正交的轴分目录**）

**目录形态**（`unit/forward-directory-layout.test.ts` 逐字锁住文件清单 + 依赖方向）：

```
forward/
  base.ts              ← 横跨两轴的公共基类，**刻意留在根上**（搬进 channel/ 会让基类依赖自己的子类目录）
  channel/             ← 入站协议轴：http / tunnel / upgrade / socks + 握手读取器 socks-reader
  upstream/
    dial.ts            ← 纯传输层（建链 + 桥接）
    connector/         ← 上游对接轴：四个连接器 + registry + barrel
```

- **为什么值得拆**：真实收益不是「好看」，是**依赖方向变得可断言**——`channel/**` 只能朝 `upstream/**` 单向，反向即目录级环。这条以前没法写（`dial.ts` 与四个转发器是平铺同级，「谁引谁」全靠人记），现在直接扫 import 钉死。`channel/**` 内部**同目录相对**、引 `upstream/**` 与 `base.ts` 一律 `@/` 别名。
- 四个转发器（`HttpForwarder` / `TunnelForwarder` / `WsForwarder` / `SocksForwarder`）继承 `base.ts:ForwarderBase`（本身已 `extends ContextualBase`）：共享 `dialer`（**2c 起只服务 `bridge`**） / `config`（继承 getter） / `preDial` / `connectorForRoute` / `preDialPeerTarget` / `denyUpstreamLoop` / `denyUpstreamLoopOf` / `settleDenied` / `settleDialFailure` / `emitRoute`（路由事件，core 零日志）/ `refuse` / `refuseByCause`。**`emit` 字段与 `emitWithUser` 方法已删除**（Phase 3）：发事件一律走 `scope.emit(e)`，身份维度由 `RequestScope` 携带。四个类的构造函数都显式写 `constructor(ctx: CoreContext, traffic: TrafficAccount)` 后 `super(ctx, traffic)`（不靠隐式继承构造），**不再收 `PipeEventSink`**。事件统一为 `PipeEvent`（泛型已删；`HelperEvent` 现为 `PipeEvent` 的真子集、可直接传入，索引签名已随判别联合一并去除）。

### 三个入口方法名互不相同，且与 `InboundKind` 逐字对齐

| 入站事件（`InboundKind`） | 转发器 | 入口方法 | 文件 |
|---|---|---|---|
| `"request"` | `HttpForwarder` | `handleRequest(req, res, scope)` | `channel/http.ts` |
| `"connect"` | `TunnelForwarder` | `handleConnect(req, socket, head, scope)` | `channel/tunnel.ts` |
| `"upgrade"` | `WsForwarder` | `handleUpgrade(req, socket, head, scope)` | `channel/upgrade.ts` |

- **此前三者都叫 `handle`**，于是「派发表的三项各自指向不同实现」这条护栏**写不出来**（按方法名断言等于没断言），只能退而落在 `forwardKind` 这个显式标签上，并把「方法名无法区分」记成一条限制。改名之后那条限制消失，护栏回到最直接的形式：**按名字断言**（`unit/inbound-dispatch.test.ts`）。**名字自带身份**也让「派发到哪」从表里一眼可读，不必去翻转发器类名。
- **`websocket.ts` → `upgrade.ts`**：该文件**不实现 WebSocket 协议**——不做帧解析、不做分片重组、不做掩码、不做 ping/pong、不做 close 握手（`buildUpgradeReq` 只改写 HTTP 握手报文，`relay` 等 101 之后就是一条透传管道）。叫 `websocket` 会让人以为「帧的处理归这里」。**类名 `WsForwarder` 与 `logPrefix: "upgrade"` 不改**：前者是导出符号改名会波及调用面与既有护栏的字面量，后者是**落盘日志文本契约**（`forwarder-connector-wiring` 逐字断言 `[upgrade] error …`）。**文件名的 `upgrade` 与 `InboundKind` 的 `"upgrade"` 同字**，这一致性是本切片想要的。

  - **协议实现住哪儿（2b-2b 起的硬不变量，2c 起零例外）**：`connector/socks4.ts`（SOCKS4/4a 握手）、`connector/socks5.ts`（SOCKS5 握手 + CONNECT 应答解析）、`connector/http-connect.ts`（CONNECT 上游对接）、`connector/direct.ts`（**无协议实现**——直连不与任何代理对话，`open()` 由传输层建链原语直接组成）。抽象建起来之后最容易出的事是「实现没跟上抽象」：连接器只剩薄委托、真实现还躺在 `forward/upstream/dial.ts`，于是想读「我们怎么做 SOCKS5 上游」的人去 `connector/socks5.ts` 找不到东西——**可发现性比改造前更差**。所以 `open()` / `transport()` **就是**实现本体，不许再写回委托。`socks-upstream.ts` 的抽象基类只装两版共用的东西（拨号外壳 + **握手应答读取器 `readReply`（2c 从 `Dialer` 搬来，文案带 SOCKS 字样故只能住这儿）** + 4 个逐字相同的声明式成员），**协议体一律由子类以 `handshake` 提供**。
  - **`OpenContext` 只有 `client` / `dest` / `onEvent` / `logPrefix` / `clientLifetime`**：没有 `viaUpstream` 标志位（`kind` 就是连接器的身份声明），**也没有 `user` 身份字段**（`HelperEvent` 载荷只有 `type`/`message`/`err`；身份一律由 channel 侧的 `scope.emit` 带上，`RequestScope` 每请求一条闭包、身份在其中注一次）。四个 channel 传的都是 `onEvent: scope.emit`（同一个函数引用，与本通道其它 pipe 事件共用一个出口，server 层按 `type` 统一分派）。`clientLifetime`（`"linked"` 缺省 / `"independent"`）是**必须由 channel 如实申报**的那一个：只有 channel 知道这次要的是隧道（`open()`，两端同一资源）还是每请求新建的传输层（`transport()` → `http.request`），connector 无从推断，故只透传、不自己设默认。**`logPrefix` 必填**（四个 channel 恒传 `"http"`/`"tunnel"`/`"socks"`/`"upgrade"`）：历史遗留的 `logPrefix?` + 三处 `?? DEFAULT_LOG_PREFIX` 兜底已删——那份缺省**从来没被任何调用方触发过**，却在三个连接器里各抄了一份常量。**它刻意不由入站派发表给**：① 派发表只覆盖三个 `server.on` 事件，**SOCKS 根本不在表里**，那条通道的 `"socks"` 前缀无处可取；② 本字段的使用点在**转发器深处**（`openUpstream` / `transportVia` / `openVia` / `forwardViaTransport`），要由派发表给就得给四个通道的入口方法逐请求加一个形参——把一个**通道的编译期常量**降级成**调用方可能传错的每请求参数**。前缀值是**落盘日志文本契约**（`forwarder-connector-wiring` 逐字断言），由各 channel 如实申报自己是谁。
    - **`"independent"` 的唯一使用方是 http 请求路径**（`forward/channel/http.ts:clientLifetime: "independent"`）。它解的是一条真实的回归：守卫 `upstream.on("close") → client.destroy()` 是**隧道语义**，套到请求路径上会让「源站关掉自己的连接」打死**入站 keep-alive**（实测客户端 `reusedSocket` 恒 false、入站 TCP 连接数 = 请求数，第 2 个请求还会吃到 ECONNRESET）。入站连接的存活是**客户端侧属性**，与上游连不连得上无关。
    - **不要**把它挪到隧道路径（CONNECT / upgrade / SOCKS）：那里 `ctx.client` 与管道确实是同一资源的两端（`bridge()` 双向 pipe），解耦会让「上游已死、客户端还在等字节」变成挂死。护栏：`integration/http-inbound-keepalive-decoupled.test.ts`（正向 + 反向两向）+ `unit/guard-client-lifetime.test.ts`（机制逐条）。
    - 附带事实：`"independent"` 形态下守卫的**客户端侧**监听随上游 socket 的 `close` 摘除。不摘的话入站是长连接、每请求挂一对 → 11 个请求就触发 `MaxListenersExceededWarning` 且闭包线性累积（实测 20 请求 → 22 个 `close` 监听）。挂 `upstream.close` 可靠：出站恒带 `Connection: close`，实测 Node 在响应收尾时必定销毁 `createConnection` 提供的 socket（源站遵守或不遵守都一样）。
  - **`open()` 与 `transport()` 是两种「要什么」**（2b-2 新增）：`open()` 给「到 dest 的字节管道」（CONNECT / socks 入站拿它自己桥接）；`transport()` 给「到**本连接器对端**的传输层连接、**不做协议级协商**」——http 普通请求要的是「连到我、但你自己写报文」（`http.ts` 经 `http.request({ createConnection })` 用），**Upgrade 通道 2c 起也是它**（对端要的是完整请求而不是裸流，先发 CONNECT 会把上游代理的状态机带偏 → 死锁）。四类实现：direct 与 socks4/5 的 `transport()` 就是 `open().sock`；`HttpConnectConnector` **只拨号到上游**（`secure` 决定 net/tls），**不发 CONNECT、不等状态行**（发了会把上游代理的协议状态机带偏：它先回 200 再等 CONNECT，而 `http.request` 已在等 HTTP 响应 → 死锁）。
  - **因此 TLS 承载整体搬进连接器**：`transport()` 返回的 socket 已是握手完成的 `net.Socket`/`TLSSocket`，`http.ts` 侧的 `upstreamTlsOptions(...)` 调用**已整体删除**，且 `https` 模块 import 一并消失。**不要**在 http 通道「顺手」把 TLS 选项加回来——那会出现两处协商。
  - **`peerTarget(dest)` 刻意带 `dest` 参数**（2b-2 新增）而 `selfLoopTarget()` 无参：后者答「**我自己的**上游地址」（纯配置事实、连接器独占）；前者答「本次请求的传输对端」——对直连/SOCKS 就是 `dest`，是**请求作用域事实**，连接器并不拥有，无参无从回答。传 `dest` 而非整个 `OpenContext`，是为了让这个纯查询不必拖上 `client`/`onEvent`（声明式方法不该有机会碰事件汇）。两个成员是**两种形状的刻意并存**，不是签名不一致。用途：`http.request` 的 `host`/`port` + 上游失败日志路由 + 「传输对端 ≠ 有效拨号地址时补判自环」（SOCKS 隧道直达 dest，而 client 模式下 `targets.dial` 是上游）。
  - **通道侧只剩一处「两种判据并存」的例外**（`http.ts` 的 Host 回写，直连与 SOCKS 规则不同）：见 Gotchas。**其余差异全部由连接器的声明式数据（`kind`/`targetForm`/`upstreamAuthHeader()`/`peerTarget()`）承担**，`http.ts` 不再自己推协议。
  - **`selfLoopTarget()` 是上游自环预检的唯一数据源**：返回 `undefined`（直连）就跳过预检，返回 `{host, port}` 才喂给 `denyUpstreamLoop`。上游地址**不再由 channel 读 `UPSTREAM_HOST`/`UPSTREAM_PORT` 猜**——`denyUpstreamLoopAuto` 已随本层删除（它正是那个「自己读配置猜上游地址」的第二真相源）。
  - **`OpenedUpstream.refusal`（仅 http-connect 的非 200）由 channel 处置，语义刻意不同**：`tunnel.openUpstream` 是「原样透传 `head`+`rest` 给客户端再销毁上游」（不断链语义，`Proxy-Authenticate` 必须送达客户端），`socks.connect` 是「发 `upstream-refused` 事件 + 回 SOCKS 失败应答再销毁上游」（回 HTTP 报文会污染协议）。**连接器绝不销毁、绝不向 `ctx.client` 写任何字节**，成败应答一律归 channel。
  - **接线护栏在 `tests/integration/forwarder-connector-wiring.test.ts`**：锁三条通道的守卫 route 文本（逐字，`[prefix] error <clientAddr> -> <dest> [via …]`，**upgrade 三档齐全：经 SOCKS 上游 / 有效 client 经 http(s) 上游 / 主路径回落直连**）、tunnel 的 refusal 透传（逐字节）、以及「有效路由 direct 时必须选 directConnector」（双桩互斥判别）。**route 文本自此是契约**，改它必须先改该文件并说明理由。
  - **upgrade 通道是单一路径（2d 收口）**：`WsForwarder.handleUpgrade` 此前有**一条结构性早分支**——`mode === "client" && isSocksProto(proto)` 时在**目标尚未解析**的情况下跳进私有方法 `viaSocks`（内含自己一份 `parseTargetParts` / `preDial` / `resolveRoute` / `emitRoute` / `denyUpstreamLoop`）。2d 把它与 `viaSocks` 整体删除，入口现在与 `handleRequest` / `handleConnect` / `socks.connect` **同形状**：`resolveForwardTargets` → `preDial` → `emitRoute` → `connectorForRoute` → `preDialPeerTarget` → `transportVia` → `upgradeOver` 等 101。四个 channel 由此**全部零 `isSocksProto` / `socksVersionOf` / `isTlsUpstreamProto`**（护栏在 `tests/unit/dialer-protocol-boundary.test.ts`）。
    - **⚠️ 唯一有真实风险的点：真实目标的自环判定**。统一后第一次 `preDial` 判的 `dial` 在 client 模式下是**上游**，而 SOCKS 隧道实际落到**真实目标**——只跑一次 `preDial` 的话，「客户端请求代理自己的监听地址」就没人判，客户端能让本代理经 SOCKS 隧道连回自己。保住它的是基类 `preDialPeerTarget`（**窄抽后 http 与 upgrade 两条通道共用这一份**，此前是两份逐字同构），**删掉/短路它 = 一个真实的自环漏洞**。护栏：`tests/integration/websocket-single-path.test.ts`（真 `HttpProxy` + 手写 Upgrade，请求代理自己的监听地址，断言 502 + 恰好一条 `loop-detected` + 上游零建链；**已用变异测试验证**：把补判短路掉 → 恰好这一条红、其余 6 条绿）+ `unit/forward-directory-layout.test.ts`（源码面：`upgrade.ts` 必须经 `this.preDialPeerTarget(`、且不得自己调 `peerTarget(`）。同一档还钉住**上游自环**也仍被拒（2d 同时删掉了 `viaSocks` 里的 `denyUpstreamLoop` 调用，现由第一次 `preDial` 承担）。
    - **事件顺序变了，是有意的收敛**（早分支把 `preDial`/`route` 发在 `viaSocks` 内部，顺序与另外三条通道不同）：统一后与别处一致。**绝不允许同一条请求发两条 `route` / `target-denied`**——`viaSocks` 内部那份 `resolveRoute`/`preDial`/`emitRoute` 已随方法一并删除（`upgrade.ts` 里 `emitRoute(` 恰好一处、`preDial(` 恰好一处 + `preDialPeerTarget(` 恰好一处，源码级断言在 `dialer-protocol-boundary.test.ts`，行为级「每请求恰好一条 route」在 `websocket-single-path.test.ts`）。
    - **守卫前缀恒为 `"upgrade"`**（`transportVia` 里的 `logPrefix`）：三条路径的 route 文本是**锁死的契约**（`forwarder-connector-wiring` 逐字断言 `[upgrade] error …`），**不得**按连接器身份改成 `[socks]`。「是否经 SOCKS 隧道」只影响**报文形态与失败文案**：`upgradeOver` 的 `viaSocksTunnel`（由 `connector.kind` 推出的模块内 `isSocksTunnel(connector)` 判定，**不从 `upstreamProtocol` 推导**）决定 `toUpstreamProxy`（SOCKS 隧道必须 origin-form 且不带上游凭证）与失败日志的 `"via socks "` 尾巴。`targetForm` **判不出这件事**（直连与 SOCKS 同为 `"origin"`），故用 `kind`。
  - **upgrade 通道的 client 模式已不再绕过连接器层（2c 收口）**：`WsForwarder.handleUpgrade` 的「有效 client」分支原先是**全仓最后一处绕过抽象层的直接拨号**（`this.dialer.choose(socket, targets.dial.host, ..., isTlsUpstreamProto(proto), ...)` + 手工 `socksUpstreamGuard`），现为 `this.transportVia(this.connectorForRoute(route), socket, targets.dest)`。**随之变化的两点**：① TLS 承载不再由 channel 用 `isTlsUpstreamProto` 推导（registry 构造期定死，`channel/upgrade.ts` 已不再 import 它）；② 守卫 route 文本由只有 `<upstream>` 变为 `"<dest> via <upstream>"` 全量形式，与 http/tunnel 同源——**旧文本是各调点随手写出来的差异、不是契约**（详见 `tests/AGENTS.md` 与 `forwarder-connector-wiring` 里那条用例注释）。**不要**把它改回 `open()`：那会让上游先收一条 CONNECT、随即等一条 Upgrade（实测死锁：上游回 200 后本通道在等 101，响应超时）。
- **刻意不收的**：各协议应答形态（HTTP `ServerResponse` 早失败、SOCKS 二进制应答、tunnel 回 200、upgrade 等 101）——强行模板化是假抽象；余量回灌 + 桥接已由 `bridgeWithBuffered` 收口（`establishTunnel`/`establish` 只剩应答 + 委托）。
- `dial.ts:Dialer`（`extends ContextualBase`，`constructor(ctx: CoreContext)`、无自有字段，`this.config` 全走继承 getter）**是纯传输层，建链 + 桥接两块职责**：
  - **建链**：`dialDirect` / `dialTls` / `choose`（按是否加密自动选 net/tls）+ private `dialWith`（open 回调 / error / timeout 三源竞态的统一收敛）。只负责「连上」，连上之后的对端协议协商不归这里。**四个方法的守卫形参一律必填**（`guard: DialGuardOptions`）：历史遗留的 `opts?` / `guard?` 全部删除。**判据是「缺席会走到哪条路」而不是「谁在用」**——`guardDialing` 的缺省档会**向客户端写 502/504 原始 HTTP 报文**且让上下游同生命周期，恰好违反「连接器绝不向 `ctx.client` 写任何字节」这条硬契约。那不是一条自洽的备用路径，是**会静默破坏契约的兜底**（客户端要等到那个时刻才知道自己被写坏了）。护栏：`tests/unit/dead-optionality-cleared.test.ts`（负向源码断言 + 变异测试）。
  - **桥接**：`bridge`（稳态双向 pipe + 仅上游出错即双关；client 侧由上层 close 守卫接管）。**它不是拨号**（不建连接、不读配置），而是「把已建好的两条流接起来」；调用点只有 `ForwarderBase.bridgeWithBuffered` 与 `WsForwarder.relay` 两处（2c 起**这是 `ForwarderBase` 持有 `dialer` 的唯一理由**），搬走换不来解耦，故仍住传输层。

## 服务端骨架（`server/`）

- `base.ts:BaseProxy`：**`extends ContextualBase`**（1.3b 起，零 Node EventEmitter），状态机 `idle → starting → running → stopping → stopped`（可重入 `starting`），`start()`/`stop()` 幂等模板方法；`stop()` 在 `starting` 态先等在途 start。`ProxyOptions.ctx` 必填并**原样**（不冻结、不兜底）归一进 `Required<ProxyOptions>`，并**同时**经 `super(options.ctx)` 落到基类（同一个对象）；core 内不存在任何依赖缺省解析；未给 `auth` 时明确创建 `new Auth({ enabled: false, enableLogging: false })`，即显式 disabled；**未给 `traffic` 时归一成 `INERT_TRAFFIC_ACCOUNT`（`inertTrafficAccount()` 的单例），即显式禁用**——与 `auth` 的兜底完全同构，且是**全仓唯一**做这件事的地方（护栏：`tests/integration/traffic-quota.test.ts` 的「直构 core 不注入 traffic → 归一成显式禁用档」）。`createNoopLogger()` 已从本文件删除 —— 缺省解析只允许发生在唯一组装根 `createProxyRuntime()`。`this.config` / `this.log` / `this.events` 是 `ContextualBase` 的**继承 protected getter**（本文件不再自带任何投影）；**必须每次现读、绝不允许把 `events` 缓存成字段**——`RuntimeContext.setEvents()` 能在运行期换总线，缓存会把「换完立刻生效」变成半个进程级暗改（`setState` 就是每次现读后 publish）。`setState` 发 `lifecycle.changed`（**唯一来源**，见下「事件单通道」）。`ConnRegistry`（`track`/`drain`，http/socks 共用一份）+ `closeServer()` 关服模板 + `authorize()`（异常转 deny，并**直接发布 `auth.decided`**）。**建服对称面也住这里**：`listenAsync(server, port, host)` 与 `ListenableServer`（net/tls/http.Server 均结构满足的最小形状：`listen`/`once`/`off`）——原在 `utils/net.ts`，该文件已删；`http.ts`/`https.ts`/`socks-base.ts` 一律从 `base.js` 取，禁止再各自包 `listen` Promise。根 AGENTS.md 只保留状态机契约。
- `factory.ts` 按 `ProxyProtocol` 建实例；`http.ts`（`HttpProxy`：三个 `server.on` 回调 + **派发表 `buildInboundChannels`** + `handleForward` 走两阶段准入 + `writeRejected`）被 `https.ts` 继承复用（仅重写 `doStart` 建 TLS 服：证书材料经 `@/utils/tls/index.js:loadCerts` 读、选项经 `tlsServerOptions` 拼、握手告警经 `./tls-alarm.js:bindTlsClientError` 挂）。**Phase 3 起 `HttpProxy` 持有三个 `protected readonly` 转发器字段（`httpForwarder` / `tunnelForwarder` / `wsForwarder`），在构造函数里一次组装**；`bindServer` 的三个回调只调它们的方法，**方法体内零 `new`**。`protected` 是刻意的：子类（含测试探针）能拿到实例断言复用行为。
- **入站派发表（「哪种事件走哪个转发器的哪个方法」的唯一一处）**：`http.ts` 导出 `InboundKind = "request"|"connect"|"upgrade"`、`InboundEvent`（判别联合，每支字段由该事件的 Node 回调参数决定）、`InboundChannel<K>`（`forwardKind` + `rejectTarget(event)` + `dispatch(event, scope)`）、`InboundChannels`（映射类型）、`buildInboundChannels(forwarders)` 与 `channelFor(channels, kind)`。`HttpProxy` 在**构造期**建一次表（`private readonly channels`），`handleForward` 只做一次表查。
  - **三个 `server.on` 回调只做「Node 参数 → 统一形状」的适配**：回调体内**零 `if (kind …)`、零三元选转发器、零 `Forwarder` 字样**。加第 4 种入站事件的动作是「往表里加一项 + 加一个回调」，**不是复制一遍前置接线**。护栏：`tests/unit/inbound-dispatch.test.ts`（恰好三项 / 三种 `forwardKind` 互不相同 / 三个不同 `dispatch` 闭包 / 派发参数逐字 / 回调源码级负向）。
  - **`channelFor` 不是运行期逻辑，是「把种类已确定这件事告诉类型系统」**：`channels[kind]` 在 `kind` 放宽成 `InboundKind` 时会退化成三个通道类型的**并集**，其 `dispatch` 收不了 `InboundEvent`（三个形参类型求交等于无解）。`channelFor` 按映射类型的索引访问（`InboundChannels[K]`）把泛型带回来，事件的判别键与通道签名因此逐字对齐——`connect` 那支写 `event.head` 能编译，误写成 `event.res` 立刻编译期红。**别把它「简化」成 `channels[kind]`**，也别给它加查表失败的兜底。
  - **`InboundChannel.forwardKind`（`ProxyForwardKind`）现在只服务一件事**：公共事件面 `request.started` / `forward.request-headers` / `forward.error` 的 `data.kind`（逐字契约，`request-scope-ids` 与 `core-event-bridge` 锁着）。**它不参与任何控制流**，改它不改行为。第二个用途（「本种类归哪个转发器」的可断言标签）**在入口方法改名后已不再需要**——三个方法名现在互不相同且与 `InboundKind` 逐字对齐，护栏直接按名字断言（见上方「三个入口方法名互不相同」一节与 `unit/inbound-dispatch.test.ts`）。**别再拿「方法名都叫 handle」当保留两条标签的理由**，那个前提已经没了。
  - **SOCKS 不进这张表**（它不是 `server.on` 事件，而是连接内的握手状态机），但它与本表共用 `admission.ts` 的两阶段准入与 scope 组装。
- **`admission.ts`（入站两阶段准入）**：`createInboundAdmission({ ctx, protocol, socket, requestId, scopeContext, authorize })` 造一个 `InboundAdmission`，持有**客户端 TCP 对端 / connectionId / requestId / 终态守卫**四样事实，并提供两个阶段方法：

  | | 阶段 A（握手前） | 阶段 B（握手后） |
  |---|---|---|
  | HTTP（`handleForward`） | `admitClientIp(403, respond)` | `authenticate(credentials, 407, respond)` → `scopeFor(user)` → 派发 |
  | SOCKS（`onConn` → `socks-session`） | `admitClientIp(undefined, respond)` | **握手**（greeting / RFC1929 / SOCKS4 目标）→ `authenticate(credentials, undefined, respond)` → `scopeFor(user)` → 派发 |

  - **两阶段而非「一函数走完三关」是硬裁决**：SOCKS 的握手**夹在**阶段 A 与鉴权之间，塞进通用流程就是把「连接内的字节状态机」硬合并。握手仍住 `socks-session.ts`。
  - **判定与应答分离**：`admitClientIp` 只判定准不准 + 发 `pipe: ip-denied` + 结算 `access` 终态；**协议应答由调用方的 `respond` 回调给出，且它在这两步之间执行**（顺序是契约：`pipe: ip-denied` → 协议应答 → 终态）。`rejectedStatus` 显式传 `403` / `undefined`——SOCKS 无状态码协议传 `undefined` **不是「忘了传」**。
  - **`authenticate` 只覆盖「凭证判定不通过」**（reason 恒 `"proxy-auth-required"`、stage 恒 `"auth"`）；握手解析失败那类**不是凭证判定**的拒绝（非法 SOCKS4 报文 `invalid-socks4-request`/parse、非法 RFC1929 帧 `invalid-auth-message`/auth、非法 greeting `invalid-socks5-greeting`/parse）仍归 `socks-session.ts` 的状态机。凭证侧事实由 SOCKS 侧合成（RFC1929 → `proxy-authorization: Basic …`、`req` 只有 `{headers, socket}`），`requestId`/`connectionId` 由准入层注入。
  - **`scopeContext` 同时决定哪些关联 id 进入 scope 的身份维度**（`createRequestScope` 把 `identity` 合并进发布的 context，「在 context 里却不算身份」是自相矛盾的形状）。HTTP 传 `{protocol, client: getClientAddress(req), target?, requestId, connectionId}`；**SOCKS 刻意只传 `{protocol}`**——它的 pipe 事件历史上不带 id（改造前是一条跨会话共享的 sink），**补 id 就是改事件载荷**。这是**内容**差异、不是**形状**差异。
  - 终态的 `client` **恒为 TCP 对端**（两条路径一致）；`eventContext.client` 恒为 `getClientAddress(req)`（展示/审计口径）。**两者是不同的事实，刻意不合并**。终态不含 `scopeContext.client`。
  - 护栏：`tests/integration/inbound-admission-order.test.ts`（HTTP 与 SOCKS 各自三关的顺序与事件逐条锁死，含「SOCKS 握手应答字节先于 `auth.decided` 出现」这条把**结构差异**钉成可观测顺序的断言）。
- `tls-alarm.ts:bindTlsClientError(server, log: EventLog, protocol)`：TLS 握手/客户端证书告警接线，`https.ts:doStart` 与 `socks-base.ts:onListenerReady` 共用一份实现。**它住在 core 而非 utils**（原 `utils/cert.ts`）：`utils` 是依赖树最底层，握手告警需要「core 事实 → 日志文本」翻译层，放 utils 会逼出 `utils → core` 的反向依赖。事件码/文本格式在 `../log-events.js`。
- `socks-base.ts`（`SocksProxyBase` + `PlainSocksProxy` / `TlsSocksProxy`：`createListener` 是明文/TLS 唯一差异点）+ `socks-session.ts`（`runSocks4Session` / `runSocks5Session`，经 `SocksSessionHost` 最小接口注入，**不含日志器**）。四个 SOCKS server 文件是 21 行薄壳；监听器 `error` 与 http 同形发 `server.error` 事件。
- **`SocksProxyBase` 的转发器字段**（Phase 3）构造器同样只收 `this.options.ctx`（事件槽下沉到 `RequestScope`），仍是**跨会话共享单例**。**`sessionHost` 现收 `InboundAdmission` 而不是 `terminal`**：`authenticate` 与 `scopeFor` 都是准入层方法的透传（`authenticate: (creds, respond) => admission.authenticate(creds, undefined, respond)` / `scopeFor: (user) => admission.scopeFor(user)`），**本地不再实现任何准入逻辑**。握手解析阶段调 `scopeFor()`（不带 user，此时还没鉴权），鉴权命中用户名后调 `scopeFor(ok.username)` —— 逐次传入，绝不落 forwarder 字段。SOCKS 的 pipe 事件**历史上不带 `requestId`/`connectionId`**，**仍刻意不补**（补上就是改事件载荷）；需要按 id 串联时读 `terminal.snapshotContext()`。
- `socks-base.ts:onConn()` 的**第一件事是造 `InboundAdmission` 并过阶段 A**（拒绝走 `pipe` 的 `ip-denied`，与 http 同形；`respond` 是 `socket.destroy()`，SOCKS 侧 `rejectedStatus` 恒 `undefined`）；握手后 `authorized` 兜底是保险，主力是 `tlsClientError`（接线与边界见下条「core 零日志禁区」与 `core/log-events.ts`）。`doStart` 以 `.catch` 兜住 `onConn` 的意外抛错：销毁 socket 并发 `clientError` 上抛（core 零日志），避免 unhandledRejection。

## 本目录 Gotchas

- `http.Server` 的 `connect` socket 是 `Duplex` 不是 `net.Socket` —— 全链路用 `Duplex`。
- **请求路径不再 `new` 任何转发器**：`HttpProxy` 的三个 `server.on(...)` 回调、`handleForward`、`SocksProxyBase.onConn`、两个会话处理器体内都**不许**有 `new XxxForwarder`（它们拿到的都是构造期建好的实例 + 每请求一条 `RequestScope`）。想「顺手改成懒加载」之前先看 `ForwarderBase` 的铁律注释——懒加载会诱使人把逐请求数据挂到实例上。
- Status-line 等待（CONNECT 的 200、Upgrade 的 101）统一走 `awaitStatusLine`；`upstreamTimeout` 只兜时间不兜内存（另有字节封顶）。
- **`tunnel.establishTunnel` 的 `opts` 必填且两个字段都必填**（历史遗留的 `{ head?: Buffer; rest?: Buffer } = {}` 已删）：唯一调用点在 `openUpstream` 的成功分支上，`head` 来自 Node 的 `connect` 事件（**恒为 Buffer**，可为空）、`rest` 来自 `OpenedUpstream.rest`（**端口契约上恒为 Buffer**，直连/SOCKS 传共享空缓冲）。两者的「可能为空」表达在**值的层面**（零长 Buffer），不表达在**类型的层面**——给一个恒有值的字段留可选项，等于让「忘了传」和「传了空」在类型上无法区分。
- SOCKS 域名是客户端原始字节（不过 HTTP 解析器）：解析/建握手前必过白名单。
- SOCKS4a 哨兵判 `DSTIP ∈ 0.0.0.0/24`：规范草稿写全 0、curl/PySocks 发 `0.0.0.1`，两者都得认；漏全 0 会误判纯4、域名残渣被当载荷打进隧道（客户端拿假 90 后收到 400）。护栏在 `tests/integration/socks-handshake.test.ts`，脚手架 `socks4aRequest(..., dstip)` 可改哨兵。
- client 模式经 http/https 上游的 Upgrade 报文保留 absolute-form + 注入 `Proxy-Authorization`（`buildUpgradeReq(..., toUpstreamProxy)`）；经 SOCKS/直连用 origin-form 且绝不带上游凭证。分流唯一依据是 `resolveRoute` 的**有效模式**（`route.mode`）：client 配置命中 `upstream` 路由名单即回落 server（直拨真实目标），请求路径不许裸读 `proxyMode`（见上方 `helpers/` 条）。
- **⚠️ Upgrade 通道走 `transport()`，绝不走 `open()`（2c 实测踩到）**：`WsForwarder.transportVia` 调的是 `connector.transport()`。对 `HttpConnectConnector` 而言 `open()` 会**先发一条 `CONNECT` 再等 200**，而本通道紧接着要发 absolute-form 的 Upgrade 并**等 101**——上游代理回完 200 就进入「等 CONNECT」的状态机，本通道却在等 101，实测结果是客户端只拿到 `[upgrade] upstream response timeout`（`integration/forward-tunnel-guard.test.ts` 的两条非 101 用例会直接红）。`DirectConnector` 与 `SocksUpstreamConnector` 的 `transport()` 恒等于 `open().sock`，故只有 http(s) 上游这一档会踩。判据一句话：**Upgrade 通道的「先发字节」是本通道自己写的报文，不是裸流**——要传输层，不要隧道。
- **`http.ts` 三支路已合并成一条（2b-2a）**：`handleRequest()` 只做「解析目标 → 选连接器 → 单一路径 `forwardViaTransport`」，`forwardViaRequest`(×2 档) / `forwardViaSocks` / `dialViaSocksAndForward` / `dialer.dialSocks` / `upstreamTlsOptions` / `node:https` import **全部删除**。合并后差异只剩连接器的声明式数据：`targetForm` 决定 request-target 形态、`kind` 决定 Host 回写规则、`upstreamAuthHeader()` 决定凭证面、`peerTarget()` 决定 `http.request` 的 host/port 与失败日志路由。
  - **Host 回写是「两种判据并存」，不是同一个东西抄了两遍——不要统一**：`targetForm === "absolute"`（对端是代理）**原样保留**客户端 Host（absolute-form 请求行的权威值已经是「客户端要访问谁」，改写会与请求行自相矛盾）；直连（`kind === "direct"`）在客户端发 absolute-form 时按 RFC 7230 §5.4 **条件回写**（触发条件＝客户端 Host 与 request-target 冲突）；经 SOCKS 隧道**无条件回写**为 `formatAuthority(dest.host, dest.port)`（前提＝request-target 已被本代理改写成 origin-form、客户端的 Host 不可信）。实测两种判据在**可达**请求上产出的字节逐字相同，差异只在「URL 省略缺省端口」那种 `absoluteFormAuthority` 会丢端口的形态上——**所以更不能因为「看起来等价」就顺手统一**。
  - **上游凭证的注入条件不在 `http.ts`**：只由 `connector.upstreamAuthHeader()` 决定（直连与 SOCKS 恒返回 `undefined`，凭证在 SOCKS 握手里）。本文件曾按 `toProxy` 再判一次，那是冗余的第二判据。
  - **`upstreamTimeout` 必须自行装订在 socket 上**（合并引入的新事实）：Node **不会**把 `http.request({ timeout })` 应用到 `createConnection` 提供的 socket（实测传了 `timeout` 后 `socket.timeout` 恒为 `undefined`、`req.on("timeout")` 永不触发）。用 `proxy.setTimeout()` 也不行——那是「从请求起算的一次性」定时器，会把耗时超过 `upstreamTimeout` 的**慢速大响应误杀**；要保持的是**空闲**超时，故装在 socket 上。`<= 0` 即禁用（同 `socket.setTimeout(0)`）。
  - **`sanitizeHeaders` 已统一强制 `Connection: close`**：原 SOCKS 分支那句显式 `connection = close` 是它的重复，删除不改变任何字节（三条支路都经过 `sanitizeHeaders`）。
  - **⚠️ 面向运维的已知特性：本代理不复用上游连接，每个转发请求新建一条上游连接。** 实测同一源站连发 20 个请求 → 源站侧 20 条 TCP 连接，且源站看到的 `Connection` 恒为 `close`（即使源站本身完全支持 keep-alive）。**成因与取舍**：`Connection: close` 由 `sanitizeHeaders` 无条件强制（`helpers/headers.ts`），而出站传输层由连接器/守卫掌管（每请求新建 socket + 拨号守卫 + 每 socket 空闲超时），**池化与这套传输层管理不兼容**（池里的 socket 无法逐个绑定请求作用域的守卫与超时，且后续流量计量还要在这些 socket 上包一层）。**这是自觉的性能取舍，不是缺陷**：入站 keep-alive 不受影响（客户端侧连接由 Node 的 http 服掌管，正常复用，见 `http-inbound-keepalive-decoupled.test.ts`）。**不要**以「复用连接省资源」为名在 http 通道把 `Connection: close` 去掉或引入 agent 池——那会让每请求新建的守卫与上游 socket 的归属重新变得含糊。
  - **出站失败日志统一为 `[http] upstream error <peer.host>:<peer.port>`**（原 SOCKS 支路的 `via socks` 字样已删）；「经哪种上游」的信息改由守卫 route 文本承担（`[<prefix>] error <clientAddr> -> <dest> via socks<N> <upstream>`，见 `forwarder-connector-wiring` 护栏），信息量只增不减。
- 拨号失败成因区分：超时（`DialTimeoutError`）→ 504，其余 → 502；SOCKS 回 FAIL 不区分。catch 里一刀切 502 会吃掉超时成因。
- **转发报文 authority 一律经 `formatAuthority` 补 IPv6 方括号**：解析侧 `parseTargetParts`/`parseAuthority` 刻意剥方括号以便 `net.connect` 直用，拼装侧不补会产出 `CONNECT ::1:443` / `Host: ::1:443` 畸形报文。已收口：`buildConnectRequest`、`buildUpgradeReq` 的 Host 回写、`http.forwardViaTransport` 的 SOCKS 分支 Host 重写。
- `tunnel.handleConnect` 解析 authority 失败回 **400**（客户端请求报文非法，与 http/upgrade 解析失败语义一致）；502 只留给网关侧失败。
- **上游协议 fail-closed（安全属性，理由已更正——2b-2a）**：`tunnel.handleConnect`（2b-1）与 `http.handleRequest`（2b-2a）都不再有「未知 `upstreamProtocol` → 降级 direct 保连通」的兜底；非法协议由 `registry:connectorFor` **抛错**，server 层 `handleForward` 的 catch 转 `forward.error`。
  - **正确理由是「静默降级直连 = 流量旁路」**：对一个代理服务，「上游协议配错 → 全部静默直连」意味着流量**绕过上游直出**，外部表现是「服务还在跑、请求还成功、但根本没走你配的链路」——这比直接报错糟糕得多（报错至少让运维知道配置错了）。所以必须 **fail-closed**。
  - **别再拿「那条分支不可达」当理由**（2b-1 当时记错了，2b-2a 更正）：CLI 路径的 `upstreamProtocol` 确实经 `FIELDS.parseEnum` fail-fast，但**库路径不经**——`createProxyRuntime({ config })` 走 `new ConfigStore(...)`，而 `ConfigStore` **零校验**（不跑 FIELDS 的解析/范围/交叉校验），`upstreamProtocol: "ftp"` 能被直接注进去。该分支**可达**。
  - **不要以「增强健壮性 / 保持连通」为名把静默兜底加回来。** 想要健壮，正确的位置是**配置校验层**（`loadConfig` 与纯内存 runtime 的构造期校验），让它**启动就报错**，而不是让请求期偷偷换一个上游形态。
  - 回归护栏 `tests/integration/upstream-protocol-fail-closed.test.ts`（库路径注入非法协议 → `forward.error` + **源站零字节** + 客户端拿不到 200；带一条合法协议的对照组证明不是「怎么都不通」）、`tests/unit/connector-registry.test.ts`（`connectorFor("ftp")` 抛错）。
- **三条通道的「上游自环预检」入口已统一**：`connector.selfLoopTarget()` 为 `undefined`（直连）就跳过，否则喂 `denyUpstreamLoop(host, port, …)`。channel 里**不许**再出现「读 `UPSTREAM_HOST`/`UPSTREAM_PORT` 调 `denyUpstreamLoopAuto`」的写法（该方法已删）。**`denyUpstreamLoop` 只有 4 个形参、不收 `req`**：它的两个调用点（tunnel / socks）都在 `connector.open()` **之前**，那里没有 `IncomingMessage`；`loop-detected` 事件上的 `req` 维度由 `preDial` → `guardPreDial` 那条路径带（那里才真的手上有 req）。曾有一个 `extra?: { req?: unknown }`，全仓零调用方（它服务的 `viaSocks` 早分支已随 2d 删除），已删——**别加回来**。
- `WsForwarder.relay` 非 101：透传 `head`+`rest` 后按 `upstream.readableEnded` 分流——已 EOF 则 `client.end()`，否则 `upstream.pipe(client)` 续传剩余 body（`Content-Length` 大于首包时客户端不挂等）；**`readableEnded` 分支不可删**（`'end'` 可能早于续体挂 pipe 前发出）；上游错误/关闭收尾归 `guardDialing` 既有 handler，不额外 destroy。
- `cfg/users.json` / `cfg/acl.json` 热加载语义（1s 节流、坏文件保留旧值、缺失=空；仅 `ENOENT`/`ENOTDIR`/非普通文件算缺失，其它 stat 错误如 `EACCES` 保留旧值并发 error，ACL 不静默全放行；相对路径先绝对化）见 `src/config/AGENTS.md`。
- **core 零日志禁区（保留一条既有例外）**：`src/core/**` 禁止直接打印日志（生命周期行也不行），**请求期**事实一律经 `this.events.publish(...)` 上抛（`pipe`/`server.error`/`auth.decided`/`request.started`/`forward.error`/`server.client-error`/`server.listening`/`server.closed`），落盘收在 `src/server/index.ts:bindProxyEventLogs`。**唯一保留的例外**：`core/server` 在**握手/接入期**（请求尚未成立、无 pipe 事件可挂）把 SOCKS 非法握手、首包超时、TLS 握手失败经 `@/core/log-events.js` 的 `logBadRequest` / `logClientTimeout` / `logTlsClientError` **直接写进当前实例注入的 `this.log`**。这是「进程内告警端口」而非转发管道落盘，DI 契约被 `tests/integration/tls-client-auth.test.ts` 锁定（直构 core 并 spy 注入实例的 `warn`），改这里必须同步改那个测试。`this.log` 的其余唯一用途是把 logger 显式传给 `@/utils/tls/index.js:loadCerts` 等告警端口；**不得**调用 `getLogger()` 或任何全局 logger 回退。事件码词汇表 `LogEvent` 与各事件文本格式住在 `core/log-events.ts`（**不在** `server/log/`），`server/index.ts:bindProxyEventLogs` 也从那里取事件函数。**事件码是类型级唯一真相源**：`LogEventCode = (typeof LogEvent)[keyof typeof LogEvent]`，`makeEvent` / `makeExtraEvent` 的 `code` 形参一律收口到它（表外或拼错的码在编译期即失败，新增码只加 `LogEvent` 一行）。
- 串联矩阵回归：新增入站×上游×证书组合时必须在 `tests/integration/upstream-matrix.test.ts` 补一档；名单语义与 `[route]` 路由事件护栏在 `tests/integration/client-mode-acl.test.ts`、`[route]` 落盘全链路在 `tests/integration/log-structured.test.ts`。
- **`ConnRegistry.drain(server)`：原生优化 + 兜底销毁，两样都做，不是二选一**（缺陷已修）。原实现对 `http.Server` 只走原生 `server.closeAllConnections()` 就 `clear()`，而 **Node 的 `closeAllConnections()` 只覆盖它自己的连接表**——`connect`/`upgrade` 事件发出后该 socket 已脱离这张表，故**活着的 CONNECT/WebSocket 隧道拆不掉**，`BaseProxy.closeServer` 的 `server.close(cb)` 永不回调、`HttpProxy.stop()` 挂死。现语义：先按需 `closeAllConnections()`（http/https 有；SOCKS 的 `net.Server`/`tls.Server` 没有，走不到），**之后一律**遍历 `this.conns` 逐条 `destroy()`（`destroyed` 判断保证重复销毁无害）再 `clear()`。分工：原生调用一次性覆盖 idle keep-alive 那一大类，兜底循环负责它结构上覆盖不到的升级连接与任何非 http 承载。**SOCKS 分支行为与修复前逐字一致**（无原生方法，修复前后走的都是那个循环）。回归护栏 `tests/integration/stop-drain-live-tunnel.test.ts`（活隧道 / idle keep-alive / 零连接三档，`stop()` 各自带明确超时预算 + 停服后同端口可重绑断言）。写涉及活隧道的测试不再需要绕开 `BaseProxy` 生命周期（真 `HttpProxy` + 真 CONNECT 可直接放进 `withProxy`）。

## 事件单通道（Phase 1.3a + 1.3b 已完成）

**core 的全部事实（含生命周期跃迁）都直接发布到注入的 `EventHub`**（`this.events.publish`），`src/core/**` **零 `EventEmitter`**：1.3a 迁完请求期/服务期事实，1.3b 把最后的 `setState` 生命周期跃迁也迁完，并删掉 `ProxyEventMap`、`BaseProxy extends EventEmitter<ProxyEventMap>` 与三个临时投影 getter。`grep -rn "node:events" src` 现在**零命中**。（Phase 3 起 `forward/**/*.ts` 里的 `this.emit(...)` 也**零命中**——那个容错包装字段已删，发事件一律 `scope.emit(e)`；`this.emitRoute(...)` 是**路由事件**的独立方法名，与 EventEmitter 无关，grep 时别把它误当成 `emit`。）

- **`lifecycle.changed` 一个事实一个来源**：`BaseProxy.setState` 直接发布；`runtime.ts` **订阅**它并只派生 `runtime.*`，**绝不再自己发一遍**（core 与 runtime 同时发布会重复）。因此事件顺序也一并翻转为「`lifecycle.changed` 先、它派生出的 `runtime.*` 后」——core 是发布方、runtime 是观察方，`tests/unit/proxy-runtime.test.ts` 按新顺序断言。**发布次数未变**：每个状态跃迁恰好一条（`setState` 的「相同状态直接 return」仍在）。

- **两个 `client` 是不同事实，刻意不合并**：`request.started`/pipe 的 context 用 `getClientAddress(req)`（XFF → X-Real-IP → Forwarded → socket，展示/审计口径，与 `[auth]`/`[forward]` 日志行同源）；名单判定与 `ip-denied` 的 `client` 恒为 `getSocketAddress(socket)`（只认 TCP 对端）。
- **`auth.decided` 的 `tag` 在 data 不在 context**：`tag`（CONNECT/socks 隧道场景标签）是「本次判定独有的事实」，不是跨事件复用的关联维度，放 context 会让每个事件的 context 都背上它。
- **头掩码住在 `core/server/http.ts`，不进 `helpers/`**：还原改造前那条 `[{kind}] headers` debug 行需要一份「入站头 → 可展示形态」的翻译，归属判据是「core 事实 → 可展示形态」而非「日志文本拼装」。`@/core/log-events.ts` 是 `[event-code]` **文本**词汇层（函数直接 `log[level](msg, fields)`，且编一个假的 `LogEvent` 码会改掉 `[http] headers` 的 msg 文本）；`@/utils/logger/sanitize.ts` 是**渲染**层（值→文本 / `k=v`），且 `utils/AGENTS.md` 明写「logger/ 只负责写文本，不拥有事件词汇」；`@/core/helpers/headers.ts` 的全部导出都是**出站**判定，其不变量是「`proxy-` 前缀 + 本代理凭证形态的 `authorization` 才剥离」——目标的 `Authorization: Bearer <token>` 出站**保留**、日志里却必须**掩码**，两种判据方向相反，混在一处迟早被「顺手统一」掉而放大泄漏面。`maskSensitiveHeaders` 只被 `handleForward` 一处调用（它已覆盖 http/tunnel/upgrade 三种 kind），故就近放 `server/http.ts`，不进 `helpers/` 的公共导出面。**掩码必须在 publish 之前完成**（事件总线对库调用方可见）；`req` / `IncomingMessage` 绝不进入任何事件载荷。
- **`PipeEventSink` 保留**（与 EventEmitter 无关）：它仍是 `(e: PipeEvent) => void` 函数类型别名，但**生产端已整体换成 `RequestScope.emit`**（`PipeEventSink` 在 `src/core/forward/**` 与 `src/core/server/**` 里零出现，护栏见 `unit/forwarder-request-path-allocation.test.ts`）。作用域携带的逐请求闭包内部把 `identity` 同时贴进 `PipeEvent` 载荷与 `EventContext`，投递方式仍是 `this.events.publish("pipe", …)`，`PipeEvent` 载荷形状与日志面零改动。
- **`ProxyAuthEvent` 保留**（长得像载荷但不是）：它是 `AuthContext.onAuthEvent` 的**内部审计回调契约**（`core/auth.ts` → `BaseProxy.authorize`），`authorize` 读到后转成 `auth.decided` 并把原对象交给前一个 `onAuthEvent` 继续走旁路。**别因为它像事件载荷就当成 1.3b 的删除对象**。

## 事件内核（`events/`）

- `src/core/events/types.ts` 是新事件契约的类型单一来源：`AppEventMap` 以元组声明参数，`EventData` 取元组首项作为实际 payload；`EventEnvelope` 携带只读事件名、关联上下文、payload 和时间戳，`EventContext.runtimeId` 必填，connection/request 作用域可选。`EventContext` 另带 `method?`（见上「事件通道中间态」）。`"pipe"` 的 data 类型是 `import type { PipeEvent } from "@/core/types/proxy.js"`（编译期擦除；`core/types/proxy.ts` 不 import `events/types.ts`，故无环）。
- `EventHub` 只公开 `publish` / `subscribe` / `once` / `listenerCount` / `removeAll` / `EventHub.merge`，内部订阅表和分发实现不得暴露 Node `EventEmitter`；runtimeId 缺省由 `crypto.randomUUID()` 生成。发布时 context 浅拷贝并补齐 runtimeId，订阅返回的 `EventSubscription.dispose()` 幂等。
- 分发使用 listener 快照：emit 期间新增或 dispose 不改变当前这次迭代；单个 listener 抛错会被隔离并交给 `onListenerError`。缺省完全静默，既不打印也不读取 `process.env.NODE_ENV`；只有显式 `reportListenerErrors: true` 才走 `process.emitWarning`，或由调用方直接传 `onListenerError`。listener 异常不得影响其它 listener 或 `publish` 返回；`removeAll()` 释放全部订阅，后续 publish 是安全空操作。
- 作用域层级固定为 `runtime → connection → request`：`EventScope.child()` 继承父级 id，可覆写/补 protocol/client/user/target；`toContext()` 只返回不含 runtimeId 的 publish 上下文，`withIdentity()` 返回身份补全后的独立快照。作用域只承载关联事实，不保存日志或控制状态。
- 事件只发布已经发生的事实，不驱动控制流：鉴权、访问控制、路由、请求完成/拒绝/失败等结果由生产方发布，订阅方只观察；事件内核不直接打印日志，日志落盘仍收在 server 层。
- 当前 `AppEventMap` 事件清单：`runtime.starting`、`runtime.started`、`runtime.stopping`、`runtime.stopped`、`runtime.error`、`runtime.dependencies-changed`、`lifecycle.changed`、`config.loaded`、`config.changed`、`config.restart-required`、`config.file-error`、`config.file-recovered`、`config.file-reloaded`、`auth.decided`、`access.client-denied`、`access.target-denied`、`route.selected`、`request.started`、`request.completed`、`request.rejected`、`request.failed`，以及 1.3a 新增的 7 个 core 直发事实 `forward.error`、`forward.request-headers`、`server.error`、`server.client-error`、`server.listening`、`server.closed`、`pipe`，以及 5a 新增的 `traffic.quota-exceeded` 与 5b-2 新增的 `traffic.ledger-error`（**都是 core 直发公共事件，刻意不进 `pipe` 判别联合**，见「每用户流量配额」一节）。

## 配置访问器（`ConfigAccessor`）

- `src/config/context.ts` 是 core 读配置的**唯一端口**（一律经 `@/config/index.js` barrel 引用）：`ConfigAccessor` **只有泛型 `get`**，没有 `getAll`、`set` 或任何隐式全局状态；`configAccessorFromStore(store)` 从调用方实例派生 live reader。core 不创建配置状态、不导入模块级 Map，也不存在 `globalConfigAccessor`。
- **数据层与策略层分离**：`config/files/acl.ts` 只负责读文件、校验结构、返回 `AclConfig`；`config/files/users.ts` 同理只提供账号表与 `loadUserPolicy`；**请求期判定全在 `core/access-control.ts`**（`checkClientIp`/`checkTargetHost`/`checkUpstreamRoute` + 按 accessor 隔离的编译缓存 `WeakMap` + `bindAclFileEvents`）。core 侧只 import 判定层，config 侧不认识请求语义；改名单语义只动 core，改文件格式只动 config。
- **每用户名单与全局名单的合流（Phase 4b）**：`checkTargetHost(host, config, user?)` 是**两层**判定，`放行 ⇔ 全局 target 组放行 ∧ 该用户 target 组放行`：
  - **先全局、后个人、全局短路**：全局拒绝是**绝对**的（个人名单只能更严、不能更松），故全局拒时**连 `users.json` 都不读**；两关都拒时报**全局那一条**（`source:"global"`）——全局是权威层，运维先看到自己的全局配置问题，而不是「某用户碰巧也被全局禁了」。
  - 两层判定走**同一个私有 `hostDenied(host, whitelist, blacklist)`**：个人组与全局 target 组「同形」是硬要求，抄两份迟早漂移（源码级断言锁在 `tests/unit/user-acl-merge.test.ts`）。
  - `user === undefined` / 用户不存在 / 未配 `acl` / 两组皆空 → 个人层**中性放行**（等价于只有全局生效）。
  - **个人名单绝不参与 `checkClientIp`（鉴权之前没有身份）与 `checkUpstreamRoute`（client 模式的路由决策与「你是谁」正交）**——那两个函数体里连 `user` 三个字母都不许出现（同上护栏的源码级断言）。
  - 编译缓存：全局一份 `WeakMap<ConfigAccessor, CompiledAcl>`，个人一份 `WeakMap<ConfigAccessor, Map<username, CompiledUserTarget>>`；失效判据都是**源对象身份**（`cached.source === 当前快照`），与 `credentials.ts:indexMemo` 同一手法。个人层在账号被删/撤掉 `acl` 时顺带清槽，缓存规模恒 ≤ 账号表规模。
  - `AclDecision.source` 是**只在拒绝时写**的可选字段（放行恒为 `{allowed:true}`，不写键）。**`AclReason` 必须保持 `whitelist | blacklist` 两字面量不变**——分层信息一律走 `source`，写成 `"user:blacklist"` 会让 `runtime/bridge.ts:aclReason` 认不出、`access.target-denied` **静默不发布**（安全事实消失）。字面量联合 `AclSource = "global" | "user"` 声明在 `types/proxy.ts`（事件契约 SSOT，判定层与公共载荷都从那里 type-only 引，三处不许各抄一份）。
  - **身份只经 `preDial` 流动**：`ForwarderBase.preDial` 是全仓唯一读 `scope.user` 的地方（`predial.ts` 自己不读任何全局/实例状态）。`channel/http.ts`（2b-2a 起）与 `channel/upgrade.ts`（**2d 起**）各有两次守卫（①有效拨号地址 ③传输对端，且**仅当两者地址不同**才补判——③那条现由基类 `preDialPeerTarget` 承担，窄抽后两条通道共用同一份），判的是同一个 `dest`，且第一次拒了就 return，**故 `target-denied` 不会重复发**（护栏：`tests/integration/user-acl-enforcement.test.ts` 的 client 模式 + SOCKS5 上游那条；`websocket-single-path.test.ts` 另有一条「补判那次不得重复发」的同类断言）。**名单条目原语**（`normalizeIp`/`ipToString`/`parseIpRule`/`compileIpRules`/`ipMatches` 与 `normalizeHost`/`parseHostRule`/`compileHostRules`/`hostMatches`）住在 `config/files/rules/{ip,host}.ts`（acl.json 的规则/数据层，原 `utils/ip-list.ts` + `utils/host-list.ts`），core 侧（`access-control.ts`、`forward/upstream/dial.ts`、`forward/channel/socks.ts`、`helpers/self-loop.ts`）一律经 `@/config/files/rules/index.js` 取，config 目录内部则用相对路径。
- **core 全链路只经必填访问器读配置**：`helpers/{route,predial,headers}`（路由/自环/凭证剥离）、`forward/base.ts`、`forward/upstream/{dial,connector/**}`、`forward/channel/{http,tunnel,upgrade,socks,socks-reader}`、`auth.ts`、`server/{base,http,socks-base}` 一律读构造期注入的 `this.config`（`BaseProxy` 侧是 `ctx.config` 的 getter 投影）；HTTP/SOCKS server 把 `this.options.ctx` 整体透传给转发器，转发器/拨号器再经继承 getter 透传到 `Dialer(ctx)`，保证同一实例全链路读同一 accessor。
- **所有会读配置的参数/选项均必填，不设全局默认**：`resolveRoute(dest, config)`、`resolveForwardTargets(url, host, config)`、`isSelfLoop(h, p, config)`、`upstreamAuthValue(config)`、`upstreamAuthHeaderLine(config)`、凭证判定/清洗函数、`guardPreDial({ config, ... })`、`createAuthProvider(options, config)`、`createAuthFromConfig(config)`、`ForwarderBase(ctx, traffic)` / 四个转发器的 `constructor(ctx, traffic)`、`Dialer(ctx)`、`createRequestScope({ ctx, ... })`、`readAcl/readAuthUsers` 的 `opts.config` 以及 ACL load/check 函数都必须显式传依赖（`ConfigAccessor` 或 `CoreContext`）。`loadCerts` 自身不读配置键（材料来自显式 `TlsInput`）；`readUpstreamCa(config)` / `upstreamTlsOptions(..., config)` 才读取配置。三者现统一从 `@/utils/tls/index.js` 取（原 `utils/cert.ts` 已拆成 `tls/{certs,server-options,upstream}.ts` + barrel）。
- **`ProxyOptions.ctx` 是强制隔离位**：`BaseProxy` 将其原样归一进 `Required<ProxyOptions>`，不做冻结、不做 `?? global` 或其它回退。runtime/CLI/server 由各自 `ConfigContext.accessor` 组装成 `RuntimeContext`（`{ config, logger, events }`）后注入；低层调用方（测试、直构 core）则从自己的 `ConfigStore` 派生 accessor 自建上下文。
- **日志同样显式**：日志端口随 `ProxyOptions.ctx.logger` 一起注入，core 内无 noop 兜底（`BaseProxy` 只把它投影成 `this.log` getter）。`HttpsProxy` / `TlsSocksProxy` 只把该 `this.log` 传给证书加载（`loadCerts`）与 TLS 握手告警（`bindTlsClientError`）；文本格式经 `core/log-events.ts` 翻译，不在此层拼字符串；不得使用 `getLogger()`、默认 logger 或任何配置全局量。
- **生效模式唯一入口仍是 `resolveRoute(dest, config)`**：判定使用该 accessor 的 `proxyMode` + `checkUpstreamRoute(host, config)`，判定对象、server 模式短路、名单命中回落、真值表与 `[route]` 事件「过 preDial 每请求恰一条、server 模式零条」全部不变。请求路径仍禁止绕过该入口裸读配置；**2d 起 upgrade 通道的 socks 早分支也已删除**，四个转发器一律经 `resolveForwardTargets` 出有效路由。
- 本节 Gotchas：显式 config **只决定「读哪份 store」**；runtime accessor 对 runtime 相位字段现读 live store，对 startup 字段读 runtime 构造时冻结值。`UPSTREAM_URL` 也属于 startup，loadConfig/纯内存 runtime 必须共用校验/拆项入口。`readJsonCached` 仍 1s 节流，ACL 编译结果按 `WeakMap<ConfigAccessor, CompiledAcl>` 隔离；相对路径在进入缓存前绝对化，只有 `ENOENT`/`ENOTDIR`/非普通文件算 missing，`EACCES` 等其它 stat 错误保留上一份有效值并发 error。`https.ts`/`TlsSocksProxy` 的 `loadCerts(this.options.tls, this.log, protocol)` 保持显式，不回落到 accessor 读取。回归护栏：`tests/unit/config-access.test.ts`（无全局、实例隔离、热改现读、ProxyOptions/auth/route 显式绑定）、`tests/unit/proxy-helpers.test.ts`、`tests/unit/self-loop.test.ts`（自环归一与 ACL 名单归一同一份实现）、`tests/unit/log-events.test.ts`（事件码与文本格式）、`auth.test.ts`、`base-lifecycle.test.ts`、`integration/tls-client-auth.test.ts`（显式 logger + 握手告警直写注入实例）。

## 管道事件判别联合（`PipeEvent`）

- `PipeEvent` 以 `type` 为字面量判别键的 14 变体判别联合取代原弱类型事件袋：每个变体只暴露已声明字段，不带索引签名；生产者与消费者必须按同一契约演进，禁止恢复 `Record<string, unknown>` 式任意字段。
- 生产者为 `src/core/forward/**`、`src/core/guard.ts` 等 core 事实产生方。**唯一的出口是逐请求的 `RequestScope.emit`**（Phase 3 起 `ForwarderBase` 那个 `emit` 实例字段已删除，`PipeEventSink` 在 `core/forward/**` 与 `core/server/**` 里零出现）：`createRequestScope` 造的闭包把身份维度贴进载荷与 context 后**直接** `ctx.events.publish("pipe", …)`，`server/{http,socks-base}.ts` 只负责造 scope、不再中转发布。`guard.ts` 侧的 `HelperEventSink` 仍在，但它的**类型**现在只是 `OpenContext.onEvent` 与 `guardDialing({ onEvent })` 的形参类型（channel 传进来的就是 `scope.emit`），不是「第二个事件槽」。消费者为 `src/server/index.ts:bindProxyEventLogs`（按 `type` 分支落盘，不做未知强转）与 `runtime/bridge.ts`（按 `type` 桥成公共事件），都不做未知强转。
- 变体清单：`PipeTargetUnresolvedEvent`（`target-unresolved`）、`PipeLoopDetectedEvent`（`loop-detected`）、`PipeRouteEvent`（`route`）、`PipeUpstreamRefusedEvent`（`upstream-refused`）、`PipeUpstreamErrorEvent`（`upstream-error`）、`PipeUpstreamTimeoutEvent`（`upstream-timeout`）、`PipeIpDeniedEvent`（`ip-denied`）、`PipeTargetDeniedEvent`（`target-denied`，**Phase 4b 多一个可选 `source: "global"|"user"`**）、`PipeSocksEvent`（`socks`）、`PipeBadRequestEvent`（`bad-request`）、`PipeDialEvent`（`dial`）、`PipeEstablishedEvent`（`established`）、`PipeClientErrorEvent`（`client-error`）、`PipeDebugEvent`（`debug`）。**`source` 刻意不进 `PipeEventBase`**（那是 14 变体共享维度，`tests/unit/pipe-event.test.ts` 以 `toEqualTypeOf` 锁死其精确形状），它只属 `target-denied` 一个变体。
- **与 `LogEvent` 重名的 9 个判别键不另写字面量**：`types/proxy.ts` 以 `import type { LogEvent } from "../log-events.js"` 引入（**编译期擦除，零运行时边**；`log-events.ts` 不 import `types/proxy.ts`，故不成环），`type` 写成 `typeof LogEvent.TargetUnresolved` 等 9 处（`target-unresolved`/`loop-detected`/`upstream-refused`/`upstream-error`/`upstream-timeout`/`ip-denied`/`target-denied`/`bad-request`/`client-error`）。运行时字符串值一字未变；改码只动 `LogEvent` 一处。**两侧差集是事实差异，禁止补齐**：`client-timeout`/`tls-client-error` 只属握手/接入期日志（没有对应 pipe 事件），`route`/`socks`/`dial`/`established`/`debug` 是落盘不走的内部细节事件。
- `PipeRouteEvent.mode` 必填且限 `"server" | "client"`，`PipeRouteEvent.route` 必填且限 `"direct" | "upstream"`；`route` 事件与 server 层 `[route]` 日志行保持 1:1，不得删字段、改为可选或扩大为任意 `string`。
- 消费者覆盖全部 14 个 `case` 后须在 `default` 使用 `e satisfies never` 做穷尽性收口；新增变体时若遗漏消费分支，必须在编译期失败。
- `HelperEvent` 是 `PipeEvent` 的真子集，仅覆盖 `dial`、`established`、`upstream-timeout`、`upstream-error`、`client-error` 五个拨号守卫变体，可直接进入 pipe 事件槽，无须恢复索引签名或额外强转。
- 上述类型契约的回归护栏在 `tests/unit/pipe-event.test.ts`：固定 14 变体清单、route 必填字面量、公共可选维度、switch 收窄与穷尽性、HelperEvent 子集及无索引签名。

## 错误边界（`ErrorBoundary`）

- `error-boundary.ts` 是纯库错误基建：只做分类、生成安全消息，并可选经注入的 `EventHub` 发布 `request.failed` / `request.rejected` / `runtime.error`；不读环境或文件、不写协议、不打印日志，观察者异常不得改变分类结果或调用方控制流。
- 分类表：`DialTimeoutError` → `timeout` / `504` / expected；Node 网络错误码（如 `ECONNREFUSED`、`ENOTFOUND`、`EAI_AGAIN`、`ECONNRESET`、`EPIPE`、`EHOSTUNREACH`、`ENETUNREACH` 等）→ `upstream` / `502` / expected；`SyntaxError`/`URIError` 或明确的 bad request/协议解析语义 → `protocol` / `502` / expected；显式客户端入口 → `client` / `400` / expected；其余 → `internal` / `502` / unexpected。
- `statusForCause` 只表达拨号收尾的 504/502 分工：超时与其余错误的 502 语义必须复用 `classifyError`，不能让调用方在 catch 中再复制一套判断。
- 拒绝与失败分工：ACL、鉴权、解析等预期内拒绝走 `rejectRequest(reason, stage, status)`（400/403/407 等由协议调用方明确给出）；已发生但需归因的请求异常走 `failRequest(error, stage)`；运行时异常走 `failRuntime(error)`。`classifyError` 不猜测客户端 400。
- 分类结果的 `message` 取原始 `Error.message` 或 `String(error)`，复用 `core/helpers/headers` 的出站头剥离判据识别 `proxy-authorization`，并遮蔽 `authorization` / `cookie` 及 Basic/Bearer 形态后截断到 200 字符；原始值只保留在 `cause` 供调用方继续判断，不得直接展示。
- 错误边界已通过 `RequestTerminal` 接入 HTTP / SOCKS / WebSocket 的请求终态：协议入口只负责记录已经发生的 completed/rejected/failed，分类、脱敏与公共事件发布统一复用本模块；不得在协议 catch 中恢复分散的 502/504 判断。

## 请求作用域值对象（`request-scope.ts`）

- `RequestScope` = `{ emit(e: PipeEvent): void; terminal: RequestTerminal; user?; requestId?; connectionId? }`，**纯值对象 + 一个 emit 闭包**：无状态、无配置依赖、无日志、无 IO。工厂 `createRequestScope({ ctx, terminal, context?, user? })` 返回**冻结**对象（`terminal` 仍是同一个引用，互斥抢占语义对全链唯一）。
- **⚠️ 同名不同物，别 import 错**：本文件的 `createRequestScope` 造的是 `RequestScope`（core 内部用，**不进 `src/index.ts`**）；`core/events/scope.ts` 里还有一个**同名**的 `createRequestScope(runtimeId, requestId?, connectionId?)` 造的是 `EventScope`，**那个才是库入口 `src/index.ts` 导出的**。两者参数形态完全不同（一个收对象、一个收位置参数），类型上不会互相 assign，但同名足以让人读错文档就写错 import。core 内一律经 `@/core/request-scope.js` 直引（层内引用，无跨目录调用方）。
- **本对象存在的唯一理由**：给「易变的逐请求数据」一个只经参数逐次传入的载体，使它在类型层面就无法被误存到共享实例上。**不要**把它扩成「请求的全部上下文袋」——`context` 形参只放**这一条请求的关联事实**（`protocol` / `client` / `target` / 关联 id），身份维度由工厂从它派生后叠加。
- **关联 id 的形参已删（同一个事实不许两个入口）**：`emit` 把 `identity` 合并进发布的 `context`，所以「id 在 `context` 里、却不算身份」是自相矛盾的形状。`RequestScopeOptions` 因此**只收 `{ ctx, terminal, context?, user? }`**，`identity` 里的 `requestId`/`connectionId` 从 `context.requestId`/`context.connectionId` 派生。SOCKS 的历史事实（pipe 事件不带 id）因此表达为「`context` 里就没有这两个键」，而**不是**「忘了传形参」。护栏：`tests/unit/inbound-dispatch.test.ts`（调用点唯一 + 入参形状一致）与 `tests/unit/dead-optionality-cleared.test.ts`。
- **身份注入只在这一处发生**（Phase 3 收敛的结果）：此前有 `ForwarderBase.emitWithUser`（把 user 贴到事件上）+ server 层的逐请求 sink 闭包（把 user/requestId/connectionId 贴到载荷与 context 上）两个注入口，现合并成 `createRequestScope` 一处。四个转发器只管 `scope.emit(e)`。`unit/forwarder-request-path-allocation.test.ts` 断言 `emitWithUser` 在 `forward/` 与 `server/` 归零。
- `emit` 带 `createEventEmitter` 容错包装（观察面抛错不得反噬协议收尾），省略的身份维度**不写键**（而不是写 `undefined`），与改造前逐请求 sink 的展开形态逐字一致。
- **调用点只有一处：`server/admission.ts:createInboundAdmission` 里的 `scopeFor(user?)`**（全仓唯一）。两条入站路径都经 `admission.scopeFor(...)` 拿到作用域——`server/http.ts:handleForward`（每个 http/tunnel/upgrade 请求一条，`context` = `{protocol, client, target, requestId, connectionId}`）与 `server/socks-base.ts:sessionHost` 透传的 `scopeFor`（每会话一条，`context` = `{protocol}`；握手阶段不带 user，鉴权后带）。**别在 `server/**` 的别处再调 `createRequestScope`**，那是身份注入的第二个入口。
- 回归护栏：`tests/integration/forwarder-instance-reuse.test.ts`（实例复用 + 身份不串号，两侧都已用变异测试验证会真的变红）、`tests/unit/forwarder-request-path-allocation.test.ts`（请求路径零 `new`）。

## 请求作用域标识（`scope-ids.ts`）

- `connectionIdFor(socket)`：按连接对象缓存复用（`WeakMap`，socket 回收即释放），keep-alive 下同一 TCP 连接共享；`newRequestId()`：每请求一个 UUID。
- **注入点仅两处**：`core/server/http.ts:handleForward`（`connectionId` 来自 socket、`requestId` 每请求新建，同步注入 `RequestTerminal` 上下文 + 逐请求 pipe 事件槽 + `AuthContext`）与 `core/server/socks-base.ts:onConn`（SOCKS 一连接一会话一请求，两者同值；经 `sessionHost` 的 `authorize` 包装注入）。
- **SOCKS 的 forwarder 是跨会话共享单例**，绝不在其上存会话态或闭包捕获 id（会串号）；id 一律经 `RequestScope`（每会话一条）/ `AuthContext` 逐会话传递。**Phase 3 起这条口头约定已由类型接管**：转发器入口签名里根本没有 `user` / `terminal` 形参，只有 `scope`。
- id 随**事件载荷**走（`PipeEventBase.requestId/connectionId`、`ProxyAuthEvent`、`AuthContext`）：1.3a 起 core **自己**把它们写进 `EventContext`（`request.started` / `auth.decided` / `pipe`），`runtime/bridge.ts` 只需从 pipe 载荷读出、补进它发布的 `access.*` / `route.selected`。使 `auth.decided` / `route.selected` / `request.started` 与 `request.completed` 终态可按 requestId 串联。缺失即不带（core 直构无入口注入时不臆造）。
- 回归护栏：`tests/unit/scope-ids.test.ts`、`tests/integration/request-scope-ids.test.ts`。

## 请求终态事件

- `request-terminal.ts:RequestTerminal` 是每个入站请求/连接的一次性终态守卫：`completed`、`rejected`、`failed` 首次 `claim` 成功后互斥且唯一；`complete` / `reject` / `fail` 在抢占后才发布，观察面异常不会反向改变协议收尾。
- **终态唯一来源原则**：每个请求终态**只由 `RequestTerminal` 抢占并发布一次**。`PipeEvent` 侧不得再单独为同一事实发一条公共拒绝/失败事件。典型：`target-unresolved` 的 `request.rejected(stage:"parse")/400` 由 `forward/channel/http.ts` 的 `requestTerminal.reject(...)` 发布，同一时刻发出的 `pipe: target-unresolved` **只服务日志面**（`[target-unresolved]` warn），`runtime/bridge.ts` 刻意不桥它（历史上桥过，靠反查是否已结算去重，那条去重通路已删）。新增任何 pipe 变体前先确认它没有已由终态 publisher 覆盖的公共形状。
- **publisher 注册表按 accessor 隔离**：`registerRequestTerminalPublisher` / `createRequestTerminal` 走模块级 `WeakMap<ConfigAccessor, Map<protocol, publisher>>`，隔离**只**建立在「每个 runtime 派生自己的 accessor 对象」（`runtime/bridge.ts` 的 `bindRuntimeContext` 每次 `Object.freeze` 造新对象）这个隐含约定上；同 protocol 下后注册的会顶掉前一个，前者终态将静默消失。退订函数幂等且**不误删他人** publisher（`current?.get(protocol) !== publisher` 保护）。护栏在 `tests/unit/proxy-runtime.test.ts`（共享同一 context 的两个 runtime 各自持有自己的 publisher）。
- **`requestTerminals` WeakMap 的职责是跨事件通道，不是去重**：Node `clientError` 事件**只给 socket、拿不到 req**，`server/http.ts` 的 clientError handler 靠 `requestTerminalFor(socket)` 判断该连接上是否已有在途请求、有则复用其 guard（避免 malformed 拒绝与请求自身终态互相抢抢占），没有才新建一个专用于该次拒绝。请求自身不需要反查——id 与 guard 都由入口经参数逐层传递。
- runtime `CoreEventBridge` 按 `ConfigAccessor + protocol` 注册内部 publisher：`rejected` / `failed` 经 `ErrorBoundary` 发布到公共 `EventHub`，`completed` 直接使用既有 `request.completed` 契约；CLI 的 `pipe` 日志面不新增 core 事件。
- HTTP 接入点：`HttpProxy.handleForward` 的客户端名单/鉴权/入口异常与 `clientError`；`HttpForwarder` 的目标解析/目标名单、响应 `finish`、上游 error/timeout/提前 close；CONNECT 在 200 建隧、解析/名单和拨号失败收尾；Upgrade 在 101、非 101、状态行等待及拨号失败收尾。
- SOCKS 接入点：`SocksProxyBase.onConn` 的客户端名单（经 `admission.admitClientIp`）与连接异常；`socks-session` 的非法握手，以及**经 `admission.authenticate` 的凭证判定**（握手解析失败那类仍由 `socks-session` 自己结算终态——它们不是凭证判定）；`SocksForwarder.connect` 的目标校验/名单、建隧成功与上游失败。所有 SOCKS reply 仍由原 `replySuccess` / `replyFail` 写字节。
- HTTP 状态码、ServerResponse 早失败、SOCKS 二进制 reply、CONNECT 200、Upgrade 101 等既有判定与写报文逻辑不改；事件只在其旁边记录已经发生的终态。
- **`request.started` 已加入**（原「暂不加入，公共契约以终态事实为最小观察面」的判断已撤销）：`handleForward` 在准入三关全过、委派 forwarder 之前**直接发布 `request.started`**（1.3a 起不经 bridge），`data` 只带 `kind`（`http`/`tunnel`/`upgrade`），身份维度（含 `method`）走 context。**这是公共事件面唯一的非终态请求级事件**——`auth.decided` 要开了鉴权才有、`route.selected` 要 client 模式才有，所以在 **server 模式直连 + 关闭鉴权**这个最常见部署下，加它之前一次请求只剩终态，慢上游/长连接无法判断卡在哪一步。终态三件套是**结果**，`started` 是**过程**，缺过程的结果不可诊断。
- **`ProxyForwardEvent` 的 `requestId` / `connectionId` 已随 1.3a 直接写进 `forward.request-headers` / `request.started` 的 `EventContext`**（core 直发，不再有 `ProxyForwardEvent` 载荷承载）：`request.started` 据此与同请求的 `request.completed|rejected|failed` 串成一条链；core 直构（无入口注入）时缺失即不带，桥接器不臆造 id。注意 `request.started` 与终态事件的 `context.target` **同源于 `getAuthority(req)`**（非 CONNECT 只认 Host 头），absolute-form 请求下它是客户端写来的代理自身 authority；**真实目标要看 `route.selected` 的 context**（那是解析后的 dest）。
- `handleForward` **只把 terminal 关联到 socket，不关联 req**：Node `clientError` 只给 socket、拿不到 req，这是跨事件通道取回 guard 的唯一路径。req 不必关联——`RequestScope` 已携带 terminal，四个 forwarder 入口自己会再关联一次。
- 回归护栏：`tests/unit/request-terminal.test.ts` 锁定互斥语义；`tests/integration/request-terminal-events.test.ts` 通过真实 `ProxyRuntime` 验证 HTTP/SOCKS 的 completed/rejected/failed 生产与唯一性。
